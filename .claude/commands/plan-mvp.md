## Использование

```
/plan-mvp
```

Без аргументов: контекст уже собран в рабочем каталоге (`.harness/`), команда
берёт его оттуда сама.

## Важно

**Неинтерактивность.** Навык writing-plans заканчивается вопросом человеку
(«план готов, как исполняем») — здесь спрашивать некого.

**Ничего не исполняй.** Результат — файл плана, и только он.

**Ожидаемый результат:** `.harness/plan.md`.

## Инструкция для LLM

### Этап 1: Контекст

Прочитай `.harness/context.md` — карту того, что где лежит и в каком порядке
читать, — и пройди по ней: открой файлы в названном ею порядке.

Карта называет только то, что реально собралось на этом прогоне. Отсутствие в
ней необязательного файла — не повод останавливаться:

- нет `requirements.md` — аналитики по задаче нет. Это штатный путь, а не
  отказ: работай от исходной постановки задачи (`.task.md` в корне рабочего
  каталога, если он там есть) вместо системных требований.
- нет `howtodemo.md` — зафиксированного сценария приёмки нет. Определяй
  границу MVP по собственному пониманию сути задачи (см. этап 2).

### Этап 2: План

Используй навык writing-plans, чтобы составить план работ. Три отступления от
навыка, обязательных здесь:

1. **Ничего не спрашивай.** Прогон неинтерактивный, отвечать некому. Место,
   где навык предлагает выбрать способ исполнения, пропусти.
2. **Ничего не исполняй.** Твой результат — файл плана, и только он.
3. **У каждой задачи заполни блок Interfaces.** `Consumes` — что задача берёт
   у предыдущих, назвав предмет: не «зависит от 1», а «читает version из
   состояния». Пустой `Consumes` означает, что задача независима, и это
   законный ответ.

Границей MVP считай сценарий приёмки, если он собрался (этап 1): задача
входит в план, только если без неё сценарий не пройдёт. Остальное перечисли в
конце файла разделом «Вне MVP».

### Этап 3: Сохранение

Запиши план в `.harness/plan.md`.
