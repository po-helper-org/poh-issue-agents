# Мониторинг аренды квартир во Вьетнаме

Раз в сутки обходит доски объявлений (Дананг, Нячанг, Вунгтау), фильтрует
по цене (12–18 млн ₫) и «не студия», ранжирует остальное скорингом,
скачивает фотографии и вшивает их в самодостаточную HTML-страницу.
Плюс короткая сводка в Telegram и ручной импорт постов из Facebook.

Исходная постановка — `PROMPT.md`. Этот README — про то, как это устроено
и что делать, когда что-то ломается.

## Архитектура

Один Render **Web Service** с постоянным диском вместо Cron Job + отдельного
хранилища:

- Render Cron Job **не может** примонтировать постоянный диск, а системе
  нужно хранить базу виденных объявлений, накопленный рейтинг и архив
  отчётов между прогонами.
- Free-план веб-сервиса засыпает после 15 минут простоя — внутренний
  планировщик (APScheduler) в таком случае не выстрелит по расписанию.

Поэтому: `render.yaml` — Blueprint на платном плане (`starter`) с диском на
`/data`, расписание живёт внутри процесса Flask/gunicorn.

```
app.py                веб-сервис: маршруты, Basic Auth, APScheduler
pipeline/
  config.py            конфигурация из env
  core.py              Listing, CRITERIA, сшивка с src/patch_v2.py
  layout.py            надстройка "спорно" над patch_v2.layout_verdict
  districts.py         нормализация района (обёртка над src/fb_import.py)
  parsing.py           обёртка над регулярками цены/площади из fb_import.py
  http.py              ретраи, User-Agent, троттлинг, детект капчи/челленджа
  fx.py                курс ЦБ (донг напрямую), кэш на диске
  photos.py            скачивание + ужатие + вшивание фото (data:-URL)
  storage.py            JSON-состояние на DATA_DIR
  report.py             сборка HTML через src/render_html.py + src/template.html
  telegram.py           сводка в Telegram
  importer.py            /import -> src/fb_import.py:parse_post()
  run.py                 оркестратор одного прогона
  scrapers/               по модулю на движок доски + реестр TARGETS
src/                   МОДУЛИ ПРОТОТИПА — переиспользуются, не переписаны:
  patch_v2.py            правила отбора: студии, районы, скоринг, giặt riêng
  fb_import.py            парсинг цены/площади/района, разбор постов Facebook
  render_html.py          серверный рендер таблицы (для progressive enhancement)
  template.html           вёрстка отчёта: фильтры, галерея, карточка владельца
  fetch_assets.py         (историческая версия) — логика скачивания фото,
                           перенесена в pipeline/photos.py и встроена в пайплайн
  build_report.py         (историческая версия) — сборка одного конкретного
                           прогона-примера прототипа, оставлена как референс
tests/                  pytest: парсеры, правила, no-JS проверка отчёта
```

`src/template.html` **не переписан с нуля** — только несколько демо-чисел,
зашитых в конкретный прогон прототипа (`178`, `6 источников`, бюджет
`25 000–50 000 ₽`, «≥ 40 м²»), заменены на плейсхолдеры (`__TITLE__`,
`__CRITERIA__`, `__COLLECTED__`, `__NSRC__`, `__NERR__`), чтобы шаблон
действительно можно было наполнять живыми данными. Анимации, progressive
enhancement (таблица — готовая разметка из Python, JS только улучшает),
галерея и карточка владельца — как были.

## Стоимость

Render `starter` веб-сервис + 5 ГБ диска — по актуальным ценам Render
(смотрите https://render.com/pricing, они меняются). План был выбран,
потому что free засыпает и там нет дисков; `starter` — минимальный платный
план с диском и без сна.

## Деплой

1. Залить репозиторий в Render (New → Blueprint, указать этот репозиторий).
   Render прочитает `render.yaml` и создаст веб-сервис с диском.
2. Задать секретные переменные окружения (Render не хранит их в
   `render.yaml`, `sync: false` — задаются в дашборде):
   `BASIC_AUTH_USER`, `BASIC_AUTH_PASS`, `RUN_TOKEN`, опционально
   `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`.
3. Без `BASIC_AUTH_USER`/`BASIC_AUTH_PASS` сервис отвечает 503 на всё,
   кроме `/healthz` — это осознанно: там телефоны и фото людей.
4. Первый прогон не ждёт расписания:
   `curl -X POST -H "X-Run-Token: $RUN_TOKEN" https://<сервис>.onrender.com/run`
   Отвечает `202` сразу же (прогон идёт в фоне, может занять несколько минут
   из-за пауз между запросами к одному хосту — см. "Вежливость к сайтам"
   ниже), результат смотрите на `/` через минуту-другую.

### Маршруты

| Маршрут | Метод | Доступ |
|---|---|---|
| `/` | GET | Basic Auth — последний отчёт |
| `/archive` | GET | Basic Auth — список прошлых прогонов |
| `/archive/<file>` | GET | Basic Auth — конкретный архивный отчёт |
| `/healthz` | GET | без авторизации — для healthcheck Render |
| `/run` | POST | заголовок `X-Run-Token` — ручной запуск прогона |
| `/import` | POST | заголовок `X-Run-Token` — импорт постов Facebook |

## Переменные окружения

См. `render.yaml` — там уже проставлены значения по умолчанию для всего,
кроме секретов. Единственное добавление сверх списка из `PROMPT.md`:
`PUBLIC_URL` (опционально) — ссылка на отчёт в сводке Telegram; если не
задать, берётся `RENDER_EXTERNAL_URL`, который Render сам прокидывает
в каждый сервис.

## Как крутить пороги

- `PRICE_MIN_VND` / `PRICE_MAX_VND` — вилка по цене, единственный жёсткий
  ценовой критерий.
- `STUDIO_AREA` (по умолчанию 45 м²) — порог, ниже которого «однушка» без
  подтверждения планировки помечается «вероятно студия» (не отсекается,
  минус 3 балла к score). См. `src/patch_v2.py::layout_verdict`.
- Веса скоринга — константы внутри `src/patch_v2.py::score_listing`
  (район, цена, площадь, техника, свет) и `pipeline/layout.py` (штраф за
  неподтверждённую/спорную планировку). Не вынесены в env осознанно: это
  тонкая настройка, которую крутят реже, чем ценовую вилку, и делать это
  проще прямо в коде рядом с комментариями, объясняющими вес.
- `pipeline/run.py::STALE_DAYS` (14 дней) — сколько времени объявление
  живёт в накопленном рейтинге без повторного подтверждения хотя бы одним
  прогоном, прежде чем выпасть (не из базы дедупа — только из отчёта).
- `pipeline/run.py::MAX_DETAIL_FETCHES_PER_TARGET` (40) — потолок на число
  заходов на страницу объявления за один прогон одного источника; защита
  от прогона длиной в час.

## Как чинить парсер при смене вёрстки

Каждый источник в `pipeline/scrapers/<engine>.py` возвращает
`SourceResult` с полями `found` (карточек получено) и `broken` (страница
получена, но 0 карточек — почти наверняка сменилась вёрстка). Это разное
состояние от «0 карточек прошло фильтр» (нормально — см. DotProperty:
там всё обычно дороже вилки). При `broken=True` источник логируется как
сломанный и попадает в сводку Telegram отдельной строкой.

1. Смотрите лог прогона (Render → Logs) — там `ИСТОЧНИК СЛОМАН: <имя> — <причина>`.
2. Открывайте `pipeline/scrapers/<engine>.py::parse_list` (или
   `parse_detail`) — там в докстринге написано, когда и с какой версии
   вёрстки сняты селекторы.
3. Скачайте свежую версию страницы (`curl -A "<UA из pipeline/http.py>" <url>`)
   и сравните структуру с `tests/fixtures/<engine>_list.html`.
4. Обновите селекторы и **обновите фикстуру** в `tests/fixtures/` —
   `pytest tests/test_scrapers.py` должен зафиксировать новую разметку.

### Известное ограничение: Cloudflare/капча

С сети, где собирался этот пайплайн, три источника из одиннадцати URL —
**batdongsan.com.vn**, **nhatot.com** (оба за Cloudflare-челленджем,
`Just a moment...`) и **alonhadat.com.vn** (за собственной капчей,
`Vui lòng xác minh không phải Robot`) — не отдают контент на обычный GET.
`pipeline/http.py::looks_blocked()` это распознаёт и превращает в
`BlockedError`, а не тихую пустую выдачу или падение прогона: источник
уходит в `broken=True` с понятной причиной. Проверить реальную разметку
карточек для этих трёх сайтов с этой сети не удалось — селекторы в
соответствующих модулях (`alonhadat.py`, `nhatot.py`, `batdongsan.py`)
это лучшее предположение по типовой структуре, с докстрингом, честно
объясняющим ограничение.

С IP Render (другая репутация, сингапурский регион) ситуация может быть
другой. Если после деплоя эти источники стабильно уходят в `broken` —
варианты: сервис вроде ScraperAPI/Bright Data для обхода Cloudflare, либо
headless-браузер (Playwright) вместо `requests` для этих трёх источников
конкретно — тяжелее по ресурсам, но такие защиты статическим HTTP не
пройти в принципе. `nhatot.py` уже написан с расчётом на JSON в
`__NEXT_DATA__`, что переживёт JS-рендер лучше, чем CSS-селекторы, если
однажды дойдёт до реального контента.

## Вежливость к сайтам

`pipeline/http.py`: экспоненциальные ретраи (до 4 попыток), пауза
2–3 секунды между запросами к одному хосту, реалистичный User-Agent,
`Referer` на страницу объявления при скачивании фото (многие хосты режут
хотлинк именно по нему — см. `pipeline/photos.py`).

## Facebook — почему не парсится напрямую

`robots.txt` запрещает `/marketplace/`, официального read-API на чужие
объявления не существует, скрейпинг куками пользователя рискует его
аккаунтом. Вместо этого — `POST /import` с телом `[{text, url, photos}]`:
собираете посты вручную (например, расширением Claude in Chrome) и
отправляете. Разбирает `src/fb_import.py::parse_post()` — теми же
правилами, что и остальные источники.

```
curl -X POST https://<сервис>.onrender.com/import \
  -H "X-Run-Token: $RUN_TOKEN" -H "Content-Type: application/json" \
  -d '[{"text":"Cho thuê CC Sơn Trà, 15tr/thang, 45m2, máy giặt riêng","url":"https://fb.com/...","photos":[]}]'
```

## Тесты

```
pip install -r requirements-dev.txt
pytest tests/
```

`tests/test_scrapers.py` — парсеры на зафиксированных HTML-фикстурах
(`tests/fixtures/`, сняты с живых страниц Mogi/FazWaz/DotProperty
12.08.2026). `tests/test_layout.py` — жёсткие критерии, студийные маркеры,
районная ловушка (`\b`-границы против substring), «giặt riêng» против
«máy giặt». `tests/test_report_nojs.py` — обязательная по PROMPT.md
проверка: собранный отчёт открывается в Playwright с
`javaScriptEnabled: false`, и `<tbody>` не пустой. `tests/test_run_integration.py`
— сквозной прогон `pipeline.run.run_once()` на фиктивном источнике (без
сети), ловит рассинхрон полей между модулями.

Если Chromium из `PLAYWRIGHT_BROWSERS_PATH` не совпадает по версии с
установленным пакетом `playwright` — тест сам подставляет
`executable_path` (см. `tests/test_report_nojs.py`), пересобирать браузер
через `playwright install` не нужно.

## Чего в системе сознательно нет

- Не обходит `robots.txt`, не скрейпит Facebook напрямую.
- Не отсекает по площади/технике/району — это влияет только на скоринг
  (см. `PROMPT.md`: с четырьмя жёсткими фильтрами подборка схлопывалась
  до трёх строк).
- Не требует JS для чтения отчёта.
