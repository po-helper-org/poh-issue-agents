# Харнесс БФТ — контур автономной проработки требований

Версия 0.2 · 2026-10-09 · статус: план, тикеты — метка `bft-harness`.

## Зачем

90% рутины PO-агента — БФТ (бизнес-функциональные требования). Цель — чтобы любой запрос проходил контур **сам**:
из Inbox до проработанных **БФТ**, а затем до **СТ** (системных требований), готовых к передаче в разработку.

## Порядок поставки (решение владельца 2026-10-09)

1. **Веха 1 — автономный сервис.** Контур работает без интерфейса: запрос попадает в Inbox (задача Gitea) → Temporal ведёт
   его по стадиям → на выходе в Gitea лежат проработанные БФТ и СТ, ход виден в комментариях задачи и в Temporal UI.
2. **Веха 2 — доска.** Kanban-доска харнесса на `https://browser.harness.aleksishmanov.ru/bft-harness/` (за TOTP-гейтом)
   и тот же экран виджетом Element (каталог менеджера, своя комната, MTS-WORK). Доска только показывает и подталкивает
   (заполнить поля, ответить, отменить) — вся логика в контуре.

## Где что хранится

| Что | Где |
|---|---|
| Карточки (issue), вводная и все последующие вводные (комментарии, ответы по почте), метки фаз | **Gitea** (self-hosted), org `bft`, repo `requests` |
| Артефакты (БФТ, СТ, письма, страницы ревью) — каждый шаг отдельным коммитом | **Gitea**, `bft/<N>/…` |
| Операционное состояние: какая стадия идёт, ожидания, таймеры, повторы, история выполнения | **Temporal** (`start-dev`, SQLite) |

## Как выглядит для PO (HowToDemo)

1. Любой запрос (вручную, ботом из Element, синхронизацией из Jira команды) падает в **Inbox** — задача в Gitea.
2. Карточка = вводная + всё, что пришло потом.
3. Для старта в карточке заполнены **email заказчика, email PO, email аналитика** и команда. Нет — карточка ждёт в Inbox,
   в ней написано, чего не хватает.
4. Дальше без PO: триаж → быстрый БФТ → вопросы CustDev **письмом заказчику** → разбор ответа → глубокий БФТ
   (problem → concept → debate → draft → validate) → **письмо аналитику на ревью** → **СТ** по методологии
   poh-sysreq-agent → отдача БФТ и СТ в источник команды (через PO-агента команды).
5. Человек нужен, только если истёк срок ответа после напоминания (`needs-human:*`) или стадия упала (`phase:failed` с причиной).
6. На доске `/bft-harness` видно, где каждая карточка, кого ждём и сколько.

## Архитектура

```
Inbox: задача Gitea  ◀── бот @bft (Element) · синхронизация Jira · вручную
        │ webhook (HMAC)
        ▼
webhook (FastAPI) ──signal-with-start──▶ Temporal (start-dev, SQLite) ──▶ worker
                                                                         ├─ GLM напрямую: гейты, fast, problem…validate, СТ
                                                                         ├─ Hermes A2A → PO-агент команды: context (чтение), отдача (запись)
                                                                         └─ mailbridge (под пользователем почтового шлюза): письма и ответы
        ▼
Gitea: комментарии, метки phase:*, коммиты артефактов   ──▶  доска /bft-harness (веха 2): Gitea + Temporal, только чтение и подталкивание
```

Нет на сервере: `claude -p` и любых продуктов Anthropic, Docker/Postgres для контура, OpenHands, github.com для данных.

## Фазы (`shared/bft_lifecycle.py`)

| Фаза | Ждём | Колонка доски |
|---|---|---|
| `inbox` | 3 email + команда | Inbox |
| `created` (триаж: prefilter, intake-gate, дубли) | агент | Триаж |
| `fast-done` | агент: быстрый БФТ + вопросы CustDev | Быстрый БФТ |
| `custdev` | EMAIL_REPLY от заказчика, 72 ч + напоминание | CustDev |
| `deep` | агент | Глубокий БФТ |
| `review` | EMAIL_REPLY от аналитика | Ревью БФТ |
| `sysreq` | агент: СТ по методологии poh-sysreq-agent | СТ |
| `delivering` | PO-агент команды (A2A) | Отдача |
| `delivered` (финал) | — | Готово к разработке |
| `spam`, `duplicate`, `failed`, `escalated`, `cancelled` | как сейчас | Остановлено |

## Почта (автономная — решение владельца)

- Мост `mailbridge/` работает под пользователем почтового шлюза, пароль контуру не виден. Сокет Unix для worker.
- Адресаты — только три email карточки и разрешённые домены; лимит частоты; при первом отказе пароля — стоп и алерт
  (предохранитель учётки блокирует после двух).
- Исходящие: `Message-ID <bft-N-r{round}-{nonce}@…>`, тема с `[BFT-N]`. Ответы: In-Reply-To/References → тег → отправитель;
  не сопоставилось — карантин и уведомление PO.
- Включение: `MAIL_MODE=shadow` (всё уходит только PO) → `live`.
