# Харнесс БФТ — контур автономной проработки требований

Версия 0.1 · 2026-10-09 · статус: план, тикеты — метка `bft-harness`.

## Зачем

90% рутины PO-агента — БФТ (бизнес-функциональные требования). Цель — чтобы требование от поступления до отдачи
команде проходило контур **само**, а PO видел воронку и вмешивался только там, где нужен человек.

## Как выглядит для PO (HowToDemo)

1. В Element (виджет «Управление требованиями» и бот `@bft`) видна воронка: **Inbox** всех запросов трёх команд и доска стадий.
2. Карточка = вводная + всё, что пришло потом (комментарии, ответы заказчика по почте, транскрипты).
3. Чтобы запустить проработку, в карточке заполнены **email заказчика, email PO, email аналитика** и команда.
   Без них карточка стоит в Inbox с подсказкой, чего не хватает.
4. Дальше без участия PO: триаж → быстрый БФТ → вопросы CustDev **письмом заказчику** → разбор ответа → глубокий БФТ
   (problem → concept → debate → draft → validate) → **письмо аналитику на ревью** → отдача в источник команды
   (комментарий и HTML в задаче Jira или страница Confluence — через PO-агента команды).
5. Человек нужен, только если истёк срок ответа после напоминания (`needs-human:custdev|review`) или контур упал
   (`phase:failed` с причиной).

## Архитектура

```
Element (виджет poh-widget-bft, бот @bft)  ← единственный интерфейс PO
        │ API Gitea
        ▼
Gitea 28 (self-hosted, SQLite)   org bft / repo requests: issue = карточка, метки phase:* team:*,
        │ webhook (HMAC)            артефакты — коммиты в bft/<slug>/
        ▼
webhook (FastAPI) ──signal-with-start──▶ Temporal (start-dev, SQLite) ──▶ worker
                                                                         ├─ GLM напрямую: гейты, fast, problem…validate
                                                                         ├─ Hermes A2A → PO-агент команды: context (чтение), отдача (запись)
                                                                         └─ mailbridge (под отдельным пользователем почты): письма и ответы
```

Нет на сервере: `claude -p` и любых продуктов Anthropic, Docker/Postgres для контура, OpenHands, github.com для данных.

## Фазы (`shared/bft_lifecycle.py`)

| Фаза | Ждём | Стадия виджета |
|---|---|---|
| `inbox` | PO: 3 email + команда | To Do |
| `created` (триаж: prefilter, intake-gate, дубли) | агент | To Do |
| `fast-done` | агент: быстрый БФТ + вопросы CustDev | FAST-DONE |
| `custdev` | EMAIL_REPLY от заказчика, 72 ч + напоминание | NEED-CUSTDEV |
| `deep` | агент | FAST-DONE |
| `review` | EMAIL_REPLY от аналитика | DEEP-REVIEW |
| `delivering` | PO-агент команды (A2A) | DEEP-REVIEW |
| `delivered` (финал) | — | DEEP-DONE |
| `spam`, `duplicate`, `failed`, `escalated`, `cancelled` | как сейчас | BFT-CANCELED для cancelled |

## Почта (автономная — решение владельца)

- Мост `mailbridge/` работает под пользователем почтового шлюза, пароль контуру не виден. Сокет Unix для worker.
- Адресаты — только три email карточки и разрешённые домены; лимит частоты; при первом отказе пароля — стоп и алерт
  (предохранитель учётки блокирует после двух).
- Исходящие: `Message-ID <bft-N-r{round}-{nonce}@…>`, тема с `[BFT-N]`. Ответы: In-Reply-To/References → тег → отправитель;
  не сопоставилось — карантин и уведомление PO.
- Включение: `MAIL_MODE=shadow` (всё уходит только PO) → `live`.
