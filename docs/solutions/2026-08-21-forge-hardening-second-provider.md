# Закалка под второго провайдера — чем GitLab отличается от GitHub

## Ситуация

Задача — вести проекты GitLab тем же контуром. Дизайн вскрыл четыре расхождения, которые
определили всё: у GitLab нет автоматических ретраев вебхуков (четыре провала подряд
отключают вебхук до суток — обработчик обязан не отдавать 5xx никогда); аналога GitHub
App нет; аналога Timeline `cross-referenced` нет (пересобирается из related/closed_by
и системных нот); метки меняются одним PUT с add/remove.

## Причина

GitHub-путь был единственным; его допущения (ретраи вебхуков, App-токены, постраничные
метки) были прошиты везде, где трогали API.

## Решение

По этапам: контракт транспорта (характеризующие тесты на метод/URL/тело), `RepoRef`
(пути глубже двух сегментов, URL-кодирование в одном месте), allowlist с масками подгрупп,
`set_labels(add, remove)` одной операцией (чинит и GitHub-путь: смена набора меток делала
до 20 DELETE), каталог меток с bootstrap-скриптом, вебхук без 5xx (`_handle_delivery`
внутри try, `.get()` вместо индексации). Затем приём вебхуков GitLab, клиент API с
поверхностью GitHub-клиента, подпись HMAC/plain с явным режимом. Живой прогон на GitLab
дошёл до проверки дублей и упал `KeyError: '_kind'`: клиент искал только задачи и не ставил
поле вида — расхождение формы дороже недостающей операции, оно уронило активность через
две стадии после опубликованного комментария. Отказ поиска одного вида больше не обнуляет
второй.

## Как проверить

Тесты контракта транспорта, устойчивости вебхука, клиента GitLab; живой прогон до MR.

## Уроки

Второй провайдер начинает с характеризующих тестов контракта, а не с клиента; обработчик
вебхука не имеет права на 5xx; форма ответа двух клиентов обязана совпадать поле в поле —
расхождение стреляет позже и в чужом коде.
