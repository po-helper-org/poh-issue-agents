# Оценка трудоёмкости — модель извлекает факты, считает код

## Ситуация

Нужна оценка трудоёмкости Issue по единому набору правил; прямой риск — модель
«угадывает» итоговое число, и оценка не воспроизводится и не оспаривается.

## Причина

Если LLM считает, результат зависит от настроения модели и не сверяется ничем.

## Решение

LLM возвращает только факты: единицы работы с часами, тип работы, флаги наличия данных,
ключи рисков — полей с итоговым числом и свободным множителем в схеме ответа нет,
подогнать результат структурно нельзя. Коэффициенты, PERT, Story Points считает чистый
Python (`worker/estimation.py`). Числа живут в `config/estimation-rules.toml`, тест
сверяет таблицы методики с конфигом, чтобы копии не разъехались. Три защиты сигнализируют,
но не правят: cross-check декомпозиции против Function Points (стоп при расхождении
больше 100%), коридоры реалистичности по типу артефакта, confidence и блок «что уточнить».
Оценка — отдельный воркфлоу с фиксированным id: повторная доставка вебхука не плодит
прогоны, новая команда — честно новый прогон.

## Как проверить

Тесты расчётного ядра (каждый коэффициент, арифметика PERT, остановка по cross-check);
команда `/estimate` в Issue → реакция → комментарий с оценкой и обоснованием.

## Уроки

Схемой ответа можно структурно запретить подгонку; числа — в конфиге, а не в промпте;
защиты сигнализируют человеку, но не тихо правят результат.
