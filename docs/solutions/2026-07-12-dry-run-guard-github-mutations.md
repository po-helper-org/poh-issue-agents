# Мутации GitHub за одним гейтом DRY_RUN

## Ситуация

Сервис должен прогнать триаж по открытому бэклогу чужого репозитория, а безопасного
стопа перед записью нет: скрипт обхода стартует по воркфлоу на каждый открытый Issue,
и любая ошибка классификации превращается в реальный комментарий или закрытие задачи.
Батчевый прогон на расплывчатых (VAGUE) задачах к тому же мог зависнуть — эскалации не было.

## Причина

Клиент GitHub писал в API напрямую, без единой точки контроля; неоткуда было включить
«сухой» режим и нечем было поймать сбой прогона по всему бэклогу.

## Решение

Все мутации сведены в `worker/github_client.py` с гвардом `_dry_run()` — HTTP-мутации
блокируются в одной точке, вызывающий код не решает. Добавлены: активность
`post_error_label` (метка `advisor:error` + комментарий при сбое прогона), backfill-скрипт
(воркфлоу на каждый открытый Issue, VAGUE без интерактива эскалируется человеку),
PAT-путь аутентификации, тесты и onboarding-инструменты. Ревью обратило внимание:
`bool(os.environ.get("DRY_RUN"))` считает `DRY_RUN=0` включённым режимом — правка этого
в досье не видна.

## Как проверить

`pytest` (в том числе `test_github_client_dryrun` — гвард блокирует мутации);
прогон backfill с `DRY_RUN=1` не меняет ничего в GitHub.

## Уроки

Гвард мутаций живёт в одном месте клиента, а не в каждом вызывающем; булевы флаги из
окружения надо парсить явно, иначе «0» ведёт себя как «да».
