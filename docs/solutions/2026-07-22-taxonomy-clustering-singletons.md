# Кластеризация бэклога вырождалась в синглтоны — сменили ось на зоны поставки

## Ситуация

Стадия консолидации ищет в бэклоге группы Issue, закрываемые одним решением. Живой
прогон: 54 синглтона на 75 Issue — обещание «одно решение закрывает 5–15 задач»
не выполнилось.

## Причина

Кластеризация шла по схожести механизма — неверная ось: задачи про разное технически
решаются вместе, если лежат в одной зоне поставки.

## Решение

Taxonomy-first: `derive_taxonomy` → `assign_zone` (по каждому Issue) → `slice_zone`
(нарезка на инкременты MVP) → синтез объединяющих Issue по инкременту. Дешёвый эксперимент
до внедрения: 8 зон доставки по 6–14 Issue. Консолидация только предлагает (ветка + PR),
Issue не мутирует, всё под DRY_RUN-гейтом. Тот же PR перевёл активности триажа на
синхронные `def` с пулом потоков (пропускная ~10×), снял автозакрытие дублей (только
метка) и снизил конкурентность 8 → 3 из-за 429 от провайдера.

## Как проверить

Тесты стадии консолидации (e2e воркфлоу, `other`-зона не теряется); живой прогон `consolidate`.

## Уроки

Ось кластеризации выбирают до алгоритма; дешёвый эксперимент на реальном бэклоге
дешевле внедрения неверной оси.
