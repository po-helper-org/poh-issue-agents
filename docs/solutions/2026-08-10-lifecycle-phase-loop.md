# Состояние Issue — цикл по таблице переходов, а не линейный сценарий

## Ситуация

Состояние Issue размазано по четырём независимым представлениям (метки, переменные
воркфлоу, комментарии, event history); ни одно не покрывало путь дальше приоритизации.
Боковой исход (спам, дубль, ответ) завершал воркфлоу — вернуть Issue в работу было
не у кого просить. Активный Issue жил неделями и упёрся бы в потолок истории
(~990 событий — реплей не укладывается в таймаут workflow task), уже словленный
консолидацией.

## Причина

Воркфлоу был линейным сценарием: прошли шаги — завершились; знание о допустимых путях
задачи нигде не было записано.

## Решение

`shared/lifecycle.py` — единственный источник правды: перечень фаз, таблица переходов,
инициатор каждого перехода, терминальность; чистый модуль без сети и Temporal. `IssueLifecycle.run()`
стал циклом: пока фаза не терминальна, прогон жив; боковые состояния — не тупики, сигнал
`reopen` ведёт назад первым допустимым переходом, ожидание ограничено сроком. По порогу
событий — `continue_as_new` в точке смены фазы, переносится компактное состояние, а не
история. Поколения разведены `workflow.patched`: припаркованные прогоны доигрывают по
старому коду — реплей их истории новым означал бы отказ по недетерминизму. Агенты
переведены на signal-with-start через лаунчер: цикл либо получает команду, либо
поднимается тем же вызовом; дорогие прогоны — дочерние воркфлоу с
`ParentClosePolicy.ABANDON`.

## Как проверить

Тесты фаз, цикла и лаунчера; в Temporal видны `generation` (число перезапусков) и query
`handles_agents`.

## Уроки

Долгоживущее состояние — таблица переходов плюс цикл; историю режут по порогу в точке
согласованного состояния; смену семантики воркфлоу разводят `workflow.patched`, иначе
платите недетерминизмом живых прогонов.
