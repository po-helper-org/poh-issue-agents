# Дорогие стадии — дочерние воркфлоу с идентификаторами и шагами-активностями

## Ситуация

Разработка агентом и круг правок исполнялись активностями внутри родительского
`IssueLifecycle`. Два следствия: у стадии нет своего идентификатора — операционная история
собиралась логами контейнера; ретрай одной активности повторял все внутренние шаги —
на живом прогоне падал только финальный `git push`, а заново шёл двадцатиминутный прогон
агента, и контур трижды объявлял о передаче задачи.

## Причина

Стадия с тремя свойствами — минуты работы, недетерминизм, денежная стоимость — не имела
права быть одной активностью.

## Решение

Правило: такая стадия исполняется дочерним воркфлоу с детерминированным id
(`develop-<repo>-<issue>` и т.п.), а её шаги — отдельными активностями со своими политиками
ретраев. Итог — три поверхности наблюдаемости: GitHub Issue (что просили), Temporal
(что и как делала система), GitHub PR (что получилось).

## Как проверить

`temporal workflow list` показывает каждую стадию своим прогоном; упавший пуш ретраится
без повторения прогона агента.

## Уроки

Долгая недетерминированная работа — дочерний воркфлоу; идентификатор — часть наблюдаемости;
гранулярность ретраев равна гранулярности шагов.
