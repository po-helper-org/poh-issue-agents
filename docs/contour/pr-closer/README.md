# po-helper-dev-closer (PR-Closer)

PR-Closer — агент, который включается **после** PR-Agent и доводит начатые изменения до финала.

PR-Agent умеет находить проблемы, но не умеет останавливаться. PR-Closer умеет останавливаться.

Сервис контура производства. Поддерживаемая версия
[протокола взаимодействия агентов](https://github.com/po-helper-org/.github/blob/main/AGENT-PROTOCOL.md) — **v1**.
Код по задаче PR-Closer не пишет: его правки ограничены файлами исходного диффа, лимитом кругов
и тестовым гейтом. Код пишет разработчик, агенты доводят написанное до качественного результата.

## Ключевой сценарий

```
Разработчик                PR-Agent                  PR-Closer
     |                         |                          |
     |-- код + открыл PR ----->|                          |
     |                         |-- замечания к коду ----->|
     |                         |                          |-- разбор + правки
     |                         |<-- push фиксов ----------|
     |                         |-- замечания round 2 ---->|
     |                         |                          |-- правки / стоп-слово
     |                         |                          |
     |<---------------- PR завершён --------------------- |
```

### HowToDemo

1. Я написал код и открыл PR.
2. PR-Agent проверил код и оставил замечания.
3. PR-Closer изучил замечания и исправил их.
4. PR завершён.

Шаги 2–3 — это цикл. **Цикл не должен длиться дольше 3 кругов.**

## Проблема: цикл не сходится сам

LLM-ревьюер на каждом круге находит новые замечания — потому что его об этом просят, а не потому,
что в коде есть проблема. К третьему кругу замечания вырождаются в микро-детали
(нейминг переменной, порядок импортов, «а если сюда придёт `null`, которого тут не бывает»).

Ценность правок падает, риск сломать рабочий код растёт. Нужен принудительный выход.

## Роль PR-Closer: разработчик + тестировщик

PR-Closer — это комбинация двух ролей, и обе обязательны:

| Роль | Задача | Что запрещено |
|------|--------|---------------|
| Разработчик | Довести начатую мысль до финала, закрыть замечания по существу | Начинать новую мысль, рефакторить соседний код |
| Тестировщик | Убедиться, что правка не сломала то, что работало | Принимать «выглядит правильно» вместо зелёного прогона |

Важное ограничение: **PR-Closer заведомо слабее первичного разработчика**
(Claude Code Opus писал код — GLM-5.1 в контейнере его правит).

Из этого следуют жёсткие рамки:

- правка — минимальный точечный патч, а не переписывание;
- нельзя менять файлы, которых нет в диффе исходного PR;
- нельзя менять публичные сигнатуры, схемы данных, миграции;
- любая правка проходит через прогон тестов **до** и **после**;
- если замечание требует архитектурного решения — оно не чинится, оно эскалируется.

## Классификация замечаний

Замечания раскладываются по трём корзинам. Дальше цикл управляется только корзиной `blocker`.

**Классифицирует PR-Agent, не PR-Closer.** Разметку ставит тот, кто уже держит контекст ревью
и видел код целиком. PR-Closer читает готовый класс и не переоценивает его — иначе слабая модель
начнёт повышать `nit` до `major`, и лимит кругов будет расходоваться на неймингах.
Задача на разметку: [poh-pr-agents#11](https://github.com/po-helper-org/poh-pr-agents/issues/11).
До её реализации PR-Closer классифицирует сам, по этой же таблице — как временный fallback.

| Класс | Что это | Действие |
|-------|---------|----------|
| `blocker` | Падает сборка/тесты, дыра в безопасности, потеря данных, явно неверная логика | Чинить обязательно |
| `major` | Реальный дефект без риска для прода: необработанная ошибка, утечка ресурса, пропущенный кейс | Чинить, пока есть круги |
| `nit` | Стиль, нейминг, форматирование, «можно короче», гипотетические кейсы | Не чинить. Записать в тело PR |

`nit` никогда не продлевает цикл. Круг с одними `nit` — это условие выхода, а не повод для round 4.

## Контракт с PR-Agent

### Триггер

Цикл стартует по событию GitHub `pull_request_review` со состоянием `changes_requested`,
автор — учётная запись PR-Agent.

Отдельные `issue_comment` цикл не запускают: ревью приходит частями, и только событие review
означает, что оно завершено. Иначе PR-Closer начнёт чинить первое замечание, пока ревьюер
пишет пятое.

### Авторство замечаний

В работу берутся только замечания от учётной записи PR-Agent (логин в конфигурации).

Комментарии людей PR-Closer **не чинит** и в `comment_digest` не включает. Человек не участвует
в цикле трёх кругов — его замечания адресованы автору PR, а не агенту. В итоговый комментарий
круга они попадают отдельным списком, чтобы не потерялись.

### Граница круга

Круг = `[ревью получено] → [правки] → [один push] → [PR-Agent перепроверил] → [новое ревью]`.

Перепроверку инициирует push в ветку PR — тот же триггер, что и для обычного разработчика.
Отдельно дёргать PR-Agent не нужно. Поэтому push делается **один раз в конце круга**, всеми
коммитами разом: два push = два ревью = сбитый счётчик кругов.

Если после push новое ревью не пришло за `REVIEW_TIMEOUT` (по умолчанию 30 минут) — цикл
завершается по текущему состоянию: открытых `blocker`/`major` нет → `SUCCESS`, есть → `ESCALATED`.
Молчание ревьюера не считается одобрением при открытых блокерах.

### Глушение после стоп-слова

Инвариант «после стоп-слова ни один агент не пишет коммит в эту ветку» держится на метке,
а не на тексте комментария:

- при любом терминальном исходе PR-Closer ставит на PR метку `pr-closer:closed`;
- PR-Agent обязан проверять эту метку до запуска и не запускаться, если она есть
  ([poh-pr-agents#12](https://github.com/po-helper-org/poh-pr-agents/issues/12));
- PR-Closer проверяет её на входе воркфлоу: сессия, стартовавшая на помеченном PR,
  немедленно завершается исходом `ALREADY_CLOSED`.

Комментарий-маркер остаётся, но он для человека. Машины читают метку.

### Рубильник `agents:off`

Метка `agents:off` — способ человека забрать PR у агентов одним действием, не разбираясь,
кто из трёх сейчас работает. Уважают все сервисы контура.

Проверяется **до любой работы**, включая обращения к LLM: смысл в том, чтобы не тратить бюджет
на PR, который человек уже взял себе. В воркфлоу проверка стоит рядом с `pr-closer:closed`,
на самом входе.

### Сквозной ключ `root-issue`

`root-issue` — номер исходного Issue, из которого выросла задача. Извлекается из `Closes #N`
в теле PR и проносится дальше: в follow-up Issue, в метрики, в Temporal search attributes.

Отсутствие ссылки на Issue допустимо. Тогда `root-issue` неизвестен, PR-Closer работает как
обычно, но follow-up вешается на PR, а не на задачу.

## Логика выхода

### Состояние

PR-Closer держит состояние между кругами — это поля Temporal-workflow, а не внешнее хранилище
(см. «Исполнение: всё на Temporal»):

```
root_issue       : номер исходного Issue из `Closes #N`, либо None
round            : 0..3          круги, потраченные на правки
open_blockers    : список нерешённых blocker/major
attempts         : comment_id -> int   попытки починки на замечание
prev_digest      : отпечаток набора открытых замечаний прошлого круга
file_scope       : множество файлов исходного диффа PR — правки только внутри него
head_sha         : голова ветки PR на начало круга (оптимистичная блокировка)
diff_budget      : лимит роста патча, относительный (см. ниже)
test_baseline    : множество идентификаторов упавших тестов ДО первой правки
```

### Про `diff_budget`

Абсолютный лимит строк здесь не работает. Код в репозитории пишут ИИ-агенты, размер PR
не нормирован: один PR — 40 строк, другой — 4000 строк нейрослопа. Одна и та же цифра
будет одновременно и слишком жёсткой, и бессмысленно мягкой.

Поэтому бюджет — **относительный**, а основной барьер — вообще не строки:

| Барьер | Правило | Почему работает |
|--------|---------|-----------------|
| `file_scope` (основной) | Правка только в файлах, уже присутствующих в диффе PR | Бинарный, не требует калибровки. Слабая модель ломает код именно через расползание на соседние файлы |
| `diff_budget` (вторичный) | Суммарный патч PR-Closer ≤ 30% строк исходного диффа, но не менее 20 строк | Масштабируется вместе с PR. Нижняя граница спасает крошечные PR |
| `hunk_limit` | Одно замечание = один hunk. Больше — значит замечание архитектурное | Ловит «починку», которая на деле переписывание |

Проценты — стартовая гипотеза, а не измеренное значение. Реальности пока нет.

**Поэтому первая фаза — soft mode.** `diff_budget` и `hunk_limit` только логируются,
`ROLLBACK` по ним не срабатывает. Жёстко работает только `file_scope`. После 20–30 закрытых PR
в логе будет распределение реальных значений — и порог ставится по данным, а не по догадке
(см. «Наблюдаемость и калибровка»).

Исключение: в репозитории без тестов soft mode не применяется — см. «Тестовый гейт».

### Условия выхода

Условия делятся на два уровня, и это принципиально: **круговые** проверяются один раз за круг,
до начала правок; **попыточные** — внутри круга, на каждую правку, и терминальными не являются.

Круговые (в этом порядке):

| # | Условие | Исход |
|---|---------|-------|
| 1 | `open_blockers` пуст, остались только `nit` | ✅ `SUCCESS` — PR готов |
| 2 | Отпечаток набора замечаний совпал с прошлым кругом | 🔁 `LOOP-DETECTED` — ревьюер ходит по кругу |
| 3 | `round` уже равен `MAX_ROUNDS` (3), а замечания остались | 🛑 `FORCED-CLOSE` — стоп-слово |

Порядок не косметический. Проверка зацикливания стоит **перед** лимитом кругов: если ревьюер
третий раз повторяет то же самое, полезнее сказать «ревьюер зациклился», чем «кончились круги».
Диагноз разный, действие человека разное.

Попыточные (внутри круга, на каждое замечание):

| # | Условие | Действие |
|---|---------|----------|
| 4 | Прогон тестов дал регрессию | ⏪ откат правки, попытка не засчитана как успешная |
| 5 | Патч вышел за `file_scope`, deny-list или (после soft mode) за `diff_budget` | ⏪ откат правки |
| 6 | Замечание требует решения, которого нет в контексте PR, либо файл в deny-list | 📤 `escalate` — замечание помечено и снято с работы |

Исчерпание `MAX_ATTEMPTS` (2) по условиям 4–5 переводит замечание в `escalate`: оно больше
не берётся в работу в этом PR и уходит в follow-up.

`ROLLBACK` **не является исходом сессии.** Это откат одной правки. Сессия заканчивается только
круговым условием либо `ESCALATED` по дедлайну ожидания человека.

### Отпечаток набора замечаний (детекция зацикливания)

Условие 2 ловит зацикливание раньше лимита кругов и потому нуждается в точном алгоритме.
Побайтовый хэш текста здесь бесполезен: LLM переформулирует то же замечание другими словами,
и совпадение не случится ни разу.

1. **Состав.** Только открытые `blocker` и `major`. `nit` исключены — стилевой шум иначе
   ломает сравнение каждый круг.
2. **Ключ замечания.** `(путь к файлу, якорь, класс)`. Якорь — нормализованный фрагмент кода,
   к которому привязано замечание, а **не номер строки**: строки едут после каждой правки.
   Когда PR-Agent начнёт отдавать стабильные идентификаторы
   ([poh-pr-agents#11](https://github.com/po-helper-org/poh-pr-agents/issues/11)), ключом
   становится идентификатор, и пункт 3 отпадает.
3. **Нормализация текста** (fallback до стабильных ID): нижний регистр, схлопывание пробелов,
   удаление номеров строк, имён переменных в кавычках и вводных оборотов. Результат — множество ключей.
4. **Порог.** Совпадением считается коэффициент Жаккара двух множеств ≥ `LOOP_THRESHOLD` (0.8).
   Точное равенство слишком строгое: одно новое замечание из пяти сбросило бы детектор,
   а ревьюер именно так и добавляет по мелочи каждый круг.
5. **Первый круг.** `prev_digest` пуст — условие 2 не проверяется.

## Терминальные действия над PR

| Исход | `open_blockers` | Действие над PR | Дальше |
|-------|-----------------|-----------------|--------|
| `SUCCESS` | пуст | approve + merge способом, настроенным в репозитории | — |
| `SUCCESS` (merge заблокирован branch protection) | пуст | метка `pr-closer:ready`, комментарий «готов к слиянию» | Мержит человек |
| `FORCED-CLOSE` / `LOOP-DETECTED` | пуст | как `SUCCESS` | — |
| `FORCED-CLOSE` / `LOOP-DETECTED` | не пуст | PR остаётся открытым, метки `needs-human:pr` + `pr-closer:closed`, назначается автор PR | Решает человек |
| `ESCALATED` (дедлайн ожидания истёк) | любой | то же, что строкой выше | Решает человек |
| `ALREADY_CLOSED` (метка `pr-closer:closed` или `agents:off`) | — | ничего | — |

Префикс `needs-human:*` общий для контура: одна выборка показывает всю очередь к людям
по организации, независимо от того, какой агент её сформировал.

**Инвариант: PR никогда не вливается с непустым `open_blockers`.** Стоп-слово останавливает
работу агента, а не отменяет требования к коду.

Branch protection агент не обходит. Required checks, required reviews, запрет самослияния —
если merge недоступен, это нормальное финальное состояние «готов к слиянию», а не ошибка.

### follow-up Issue

Создаётся в том же репозитории при любом терминальном исходе, если есть что переносить.

- Заголовок детерминированный: `PR-Closer follow-up: #<номер PR>`.
- Тело: незакрытые `major`, все `nit`, эскалированные замечания — каждое с файлом, классом
  и текстом; ссылка на PR и на итоговые комментарии кругов.
- Дедупликация: перед созданием ищется Issue с тем же заголовком. Найден — тело перезаписывается,
  второй Issue не создаётся.
- Пустой список — Issue не создаётся вовсе.

**Провенанс обязателен.** Issue помечается `origin:agent` и несёт в теле `root-issue: #N`
и глубину цепочки. Без этого Issue-Agent не отличит его от человеческого запроса и прогонит
полный триаж с advisor-ответом на замечание, которое уже классифицировано.

Глубина — защита контура от самоусиления. Контур замкнут: PR-Closer создаёт Issue, Issue-Agent
их триажит, разработчик делает PR, PR-Closer создаёт следующий follow-up. follow-up второго
уровня в триаж не идёт — сразу к человеку.

### Итог круга

Каждый круг PR-Closer оставляет один комментарий фиксированного формата — чтобы человек
мог оценить сходимость, не читая дифф:

```
round 2/3
fixed      : 3 blocker, 1 major
skipped    : 4 nit (см. список ниже)
escalated  : 1 (файл в deny-list: .github/workflows/ci.yml)
tests      : 128 passed, упавших 0 (baseline 0) — регрессий нет
diff       : +41 / -12, файлов 3/3 в scope (бюджет 30% от +380 = 114, soft)
next       : 1 major открыт, идём в round 3
```

## Тестовый гейт

Роль тестировщика — половина смысла PR-Closer, поэтому гейт задан явно.

### Откуда берётся команда

1. `.pr-closer.toml` в корне репозитория, ключ `test_command` — приоритетный источник.
2. Fallback-эвристика, если ключа нет: цель `test` в `Makefile` → `make test`; иначе по
   экосистеме (`pytest`, `npm test`, `go test ./...`).
3. Ничего не найдено → режим `NO_TESTS`.

### Критерий регрессии

`test_baseline` — **множество идентификаторов упавших тестов**, а не их количество. Сравнение
по числу даёт ложный зелёный: один тест починился, другой сломался, счётчик тот же.

Регрессия = в новом прогоне появился идентификатор, которого не было в `test_baseline`.
Починившиеся тесты регрессию не компенсируют.

### Красный baseline

Допустим. PR-Closer не обязан чинить то, что было сломано до него. Цель гейта — не ухудшить,
а не привести к зелёному.

### Нестабильные прогоны

Падение по сети, лимитам или таймауту — не вердикт о коде. Прогон повторяется один раз;
если множество упавших тестов между двумя прогонами различается, прогон признаётся
нестабильным, вердикт по этой правке не выносится, замечание уходит в `escalate`.

### Режим `NO_TESTS`

Тестов нет — страховки нет, и роль тестировщика вырождается. Компенсация:

- `diff_budget` и `hunk_limit` работают **жёстко с первого круга**, soft mode не применяется;
- чинятся только `blocker`; `major` эскалируются без попытки правки;
- в итоговом комментарии круга это указано явно.

### Таймаут

Activity `run_tests`: `start_to_close_timeout` из конфигурации, по умолчанию 20 минут,
`RetryPolicy(maximum_attempts=1)`. Повтор при подозрении на нестабильность делает сам гейт
осознанно, а не Temporal вслепую.

## Механика правки и отката

### Гранулярность

**Один фикс = один коммит.** Сообщение коммита ссылается на замечание:

```
fix(pr-closer): обработать ошибку чтения конфига

closes-comment: <id замечания>
```

Это делает откат адресным и делает историю ветки читаемой человеком. Один коммит на круг
не годится: неудачную правку нельзя было бы откатить, не потеряв удачные.

### Порядок операций внутри попытки

```
снимок head_sha
  → патч в рабочее дерево
  → проверка границ (file_scope, deny-list, diff_budget, hunk_limit)
  → прогон тестов
  → коммит          (только если границы соблюдены и регрессий нет)
     иначе          → откат рабочего дерева, попытка не засчитана
```

Коммит только после зелёного прогона: в ветку не попадает ничего непроверенного.

Push — один раз в конце круга, всеми коммитами разом (см. «Граница круга»).

### Откат

- Правка **не запушена** — сброс рабочего дерева. Коммита не было, откатывать нечего.
- Правка **уже в ветке** (проблема вскрылась на следующем круге) — `git revert <sha>`,
  новый коммит поверх.

`git push --force` и `rebase` запрещены: ветка PR публична, её историю переписывать нельзя.
Откат — всегда добавление коммита, никогда не переписывание.

### Счётчик попыток

`attempts[comment_id]`, порог `MAX_ATTEMPTS` = 2. Исчерпан — замечание помечается `unfixable`,
уходит в `escalate` и в follow-up, в этом PR больше не берётся.

## Границы записи

PR-Closer — слабая модель с правом записи в ветку. `file_scope` и бюджет диффа этого не покрывают.

### `DRY_RUN`

Обязательный режим для демо, первых прогонов на живом репозитории и набора данных для калибровки.

| Подавляется | Не подавляется |
|-------------|----------------|
| push, комментарии, метки, merge, создание follow-up Issue | клон, применение патча в рабочее дерево, прогон тестов, все измерения, запись метрик и лог |

Прогон в `DRY_RUN` даёт полные данные для калибровки и не меняет в GitHub ничего.

### Deny-list путей

Действует **поверх** `file_scope`: даже если файл присутствует в диффе PR, править его нельзя.

```
.github/**            CI, права воркфлоу
Dockerfile*           образ сборки
docker-compose*.yml   топология стенда
*.lock                зависимости
**/migrations/**      схема данных
.env*                 конфигурация секретов
```

Замечание к файлу из deny-list не чинится — сразу `escalate`. Список расширяется через
`.pr-closer.toml`.

### Конкурентность

Автор PR может запушить в ветку, пока идёт круг правок.

`head_sha` фиксируется в начале круга и сверяется перед push. Расхождение → push отменяется,
круг перечитывает состояние PR заново и применяет правки к новой голове. **`round` при этом
не инкрементируется**: чужой push не должен отнимать круг у агента.

### Права токена

Только репозиторий этого PR. Запрещены: `--force`, любые операции с base-веткой,
изменение настроек репозитория, закрытие чужих Issue.

## Псевдокод цикла

Весь цикл — тело `@workflow.run`. Всё, что ходит наружу (GitHub, тесты, LLM), — activity.

```python
@workflow.run
async def run(pr: PullRequestInput) -> CloserOutcome:
    if await has_any_label(pr, "pr-closer:closed", "agents:off"):
        return CloserOutcome.ALREADY_CLOSED         # до любого обращения к LLM

    root_issue    = parse_closes_reference(pr)      # номер Issue или None
    workflow.upsert_search_attributes({"RootIssue": root_issue, "Repo": pr.repo})

    file_scope    = await fetch_file_scope(pr)      # файлы исходного диффа
    test_baseline = await run_tests(pr)             # множество упавших
    head_sha      = await fetch_head_sha(pr)
    round, prev_digest, attempts = 0, None, {}
    open_blockers = []

    while True:
        review = await wait_for_review(pr, timeout=REVIEW_TIMEOUT)
        if review is None:                                   # ревьюер молчит
            return await finish(SUCCESS if not open_blockers else ESCALATED)

        comments      = classify(review)                     # класс от PR-Agent, иначе fallback
        open_blockers = [c for c in comments if c.cls in (BLOCKER, MAJOR)]

        if not open_blockers:                                # условие 1
            return await finish(SUCCESS)

        digest = comment_digest(open_blockers)
        if prev_digest and jaccard(digest, prev_digest) >= LOOP_THRESHOLD:
            return await finish(LOOP_DETECTED)               # условие 2
        prev_digest = digest

        if round >= MAX_ROUNDS:                              # условие 3
            return await finish(FORCED_CLOSE)
        round += 1

        for c in open_blockers:
            if in_deny_list(c.file) or needs_architecture(c):
                escalate(c)                                  # условие 6
                continue
            while attempts.get(c.id, 0) < MAX_ATTEMPTS:
                attempts[c.id] = attempts.get(c.id, 0) + 1
                patch = await produce_patch(c, file_scope)
                if not within_bounds(patch, file_scope, diff_budget):
                    rollback(patch)                          # условие 5
                    continue
                if regressions(await run_tests(pr), test_baseline):
                    rollback(patch)                          # условие 4
                    continue
                await commit(patch, c)
                break
            else:
                escalate(c)                                  # попытки исчерпаны

        if await fetch_head_sha(pr) != head_sha:             # чужой push
            head_sha = await fetch_head_sha(pr)
            round -= 1                                       # круг не засчитан
            continue
        await push_round(pr)
        await publish_round_summary(pr, round)
```

`finish(outcome)` выполняет терминальные действия из соответствующей таблицы: метки, merge
либо назначение человека, follow-up Issue, итоговый комментарий.

Соответствие «шаг цикла — activity» держится намеренно: получить ревью, классифицировать,
получить патч, применить, прогнать тесты, проверить границы, закоммитить, запушить,
опубликовать итог. Тогда история Temporal читается как журнал сессии.

## Схема данных

Контракт между workflow, activity и вебхуком. Живёт в одном месте — как `shared/workflow_types.py`
в [poh-issue-agents](https://github.com/po-helper-org/poh-issue-agents).

```
ReviewComment
    id            стабильный идентификатор от PR-Agent (fallback: хэш ключа)
    file          путь
    anchor        нормализованный фрагмент кода — привязка, устойчивая к сдвигу строк
    line_hint     номер строки на момент ревью (для человека, не для сравнения)
    cls           BLOCKER | MAJOR | NIT
    text          текст замечания
    author        логин автора

FixAttempt
    comment_id    к какому замечанию
    attempt       номер попытки (1..MAX_ATTEMPTS)
    commit_sha    коммит либо None, если откат
    bounds        OK | OUT_OF_SCOPE | OVER_BUDGET | DENY_LIST
    tests         PASSED | REGRESSION | UNSTABLE | NO_TESTS

RoundResult
    round         номер круга
    fixed         список comment_id
    skipped       nit
    escalated     список (comment_id, причина)
    tests         сводка прогона
    diff_stats    добавлено/удалено, файлов, hunk
    decision      CONTINUE | исход

CloserOutcome
    SUCCESS | FORCED_CLOSE | LOOP_DETECTED | ESCALATED | ALREADY_CLOSED

FollowUpIssue
    root_issue    номер исходного Issue либо None
    source_pr     номер PR
    depth         глубина цепочки: 1 — из PR по человеческой задаче, 2 — из PR по follow-up
    items         незакрытые major, nit, эскалированные — с файлом, классом и текстом
```

`ROLLBACK` в `CloserOutcome` отсутствует намеренно: это результат попытки (`FixAttempt`),
а не сессии.

## Исполнение: всё на Temporal

Цикл ревью — это долгоживущий процесс с состоянием, с паузами по несколько часов, с внешними
событиями и с дорогими необратимыми шагами. Такое нельзя строить на цепочке GitHub Actions:
после падения джобы не остаётся ни состояния, ни ответа на вопрос «на каком круге и почему всё встало».

**Поэтому PR-Closer — Temporal-workflow, а не набор скриптов.** Референс реализации —
[poh-issue-agents](https://github.com/po-helper-org/poh-issue-agents): там обработка Issue уже
живёт как durable workflow, и те же приёмы переносятся сюда один в один.

### Что это даёт

| Возможность | Механизм Temporal | Зачем в PR-Closer |
|-------------|-------------------|-------------------|
| Видеть, что происходило | История workflow | Полный журнал сессии: какие замечания пришли на каждом круге, что было починено, почему сработал выход. Без grep по логам контейнера |
| Состояние цикла | Поля workflow | `round`, `open_blockers`, `attempts`, `prev_digest`, `test_baseline` живут в workflow. Внешняя БД не нужна, состояние переживает рестарт воркера |
| Спросить у живой сессии | `@workflow.query` | «На каком круге PR #42 и что у него открыто» — ответ от идущего процесса, без побочных эффектов |
| Ручной контроль | `@workflow.signal` | Стоп-слово можно прислать снаружи: человек шлёт `force_close`, не дожидаясь round 3. Туда же `pause`, `author_replied` |
| Диалоги ожидания | `wait_condition` + сигнал | `escalate` — это не «упасть с ошибкой», а припарковаться и ждать ответа автора PR. Workflow стоит и не ест ресурсы |
| Зависшие сессии | `start_to_close_timeout` на каждую activity | Застрявшая стадия падает по своему таймауту, а не вешает весь прогон. Терминировать/перезапустить — из UI Temporal |
| Идемпотентность | Детерминированный workflow-id | `pr-closer-<repo>-<pr_number>`: повторная доставка вебхука упирается в `REJECT_DUPLICATE`, а не запускает вторую сессию правок в ту же ветку. Осознанный перепрогон — через суффикс в id |
| Сшивка с соседними агентами | Search attributes `RootIssue`, `Repo` | Одна лента на всю цепочку задачи: триаж Issue, ревью, доведение PR. Главный аргумент за централизованный кластер |
| Не ретраить дорогое вслепую | `RetryPolicy(maximum_attempts=1)` | Прогон агента-правщика меняет код. Слепой ретрай после таймаута даст второй набор коммитов |

Детерминированный workflow-id даёт и второе свойство: **на один PR существует ровно одна сессия**,
поэтому конкурирующих правок в одну ветку от самого PR-Closer быть не может by design.

### Сигналы и запросы

| Имя | Тип | Смысл |
|-----|-----|-------|
| `force_close` | signal | Человек останавливает цикл немедленно, не дожидаясь лимита кругов |
| `pause` / `resume` | signal | Заморозить сессию, не теряя состояние |
| `author_replied` | signal | Автор PR ответил на эскалацию — снять паузу |
| `status` | query | `round`, открытые замечания, последний исход попытки, режим (`DRY_RUN`, soft/hard) |

### Temporal внутренний или централизованный

Обе схемы поддерживаются, выбор — вопрос конфигурации, не кода:

| Схема | Temporal | Когда |
|-------|----------|-------|
| Внутренний | Поднимается в том же `docker-compose` | Локальная отладка, автономный контур, демо |
| Централизованный | Внешний кластер, адрес в `.env` | Общий кластер организации: все агенты в одном UI, единая точка наблюдения |

Точка подключения одна, конфигурация из окружения — `TEMPORAL_ADDRESS`, `TEMPORAL_NAMESPACE`,
`TEMPORAL_TLS`. Код workflow про эту разницу не знает. Как в issue-agents: отдельные compose-файлы
под «только приложение» и «полный стек со встроенным Temporal».

Для централизованного кластера включается TLS: через workflow и activity ходит содержимое PR
и диффов — трафик шифруется в транзите, сервер аутентифицируется по сертификату.

## Эскалация и дедлайн

Эскалация — не ошибка, а передача решения человеку. Но парковка без дедлайна создаёт ровно ту
проблему, ради которой брали Temporal: вечно живую сессию в списке зависших.

| Аспект | Решение |
|--------|---------|
| Форма вопроса | Комментарий в PR с конкретным замечанием и причиной + метка `pr-closer:waiting` + назначение автора PR |
| Что снимает паузу | Сигнал `author_replied` из вебхука: комментарий автора PR либо снятие метки `pr-closer:waiting` |
| Дедлайн | `ESCALATION_DEADLINE`, по умолчанию 72 часа |
| По истечении дедлайна | Метки `needs-human:pr` + `pr-closer:closed`, follow-up Issue, исход `ESCALATED`, workflow завершается |
| `round` во время паузы | Не растёт. Ожидание человека не съедает лимит кругов |
| `force_close` во время паузы | Работает |

Ни один сценарий не оставляет workflow в состоянии, из которого нет выхода ни по времени,
ни по сигналу.

## Наблюдаемость и калибровка

Soft mode имеет смысл, только если замеры где-то накапливаются. Иначе это просто выключенные
ограничения.

### Что замеряется на круг

Размер исходного диффа PR, размер патча круга, число hunk на замечание, класс замечания,
исход каждой попытки, число кругов до выхода, какое именно условие сработало, режим
(soft/hard, `DRY_RUN`), длительность стадий.

### Где хранится

История Temporal — источник истины, но она не предназначена для агрегации по сотне PR.
Поэтому activity `record_metrics` дополнительно пишет строку JSONL в том воркера
(или в таблицу, если стенд централизованный). Пишется **всегда**, включая `DRY_RUN` —
именно сухие прогоны дают самые дешёвые данные.

### Как из этого получается порог

`scripts/calibrate.py` читает накопленное и показывает распределение отношения
`размер патча / размер исходного диффа` и числа hunk на замечание, с перцентилями.
Порог предлагается по p90 успешных кругов: правки, которые прошли тесты и не потребовали отката.

Переход soft → hard — **вручную**, после ≥30 PR, отдельным изменением конфигурации.
Автоматического переключения нет: порог должен пройти через человека.

## Исполнитель правок

| Аспект | Решение |
|--------|---------|
| Модель и вызов | GLM-5.1 через z.ai, из контейнера воркера — по образцу [poh-issue-agents](https://github.com/po-helper-org/poh-issue-agents) |
| Вход | Текст замечания, его класс, содержимое затронутых файлов, список `file_scope`. **Дифф PR целиком не даётся** — у слабой модели это провоцирует переписывание вместо точечной правки |
| Выход | Unified diff против рабочего дерева. Не «модель сама записала файл»: иначе границы нечем измерять, а откат нечего откатывать |
| Таймаут | Activity `produce_patch`, `start_to_close_timeout` 15 минут |
| Ретраи | `RetryPolicy(maximum_attempts=1)` — правка меняет код, слепой ретрай даст второй набор коммитов |
| Параллелизм | `max_concurrent_activities` с оглядкой на rate-limit провайдера. Один PR = один workflow, конкуренции за ветку нет |

`.pr-closer.toml` в корне обрабатываемого репозитория:

| Ключ | По умолчанию | Смысл |

## Запуск

### Быстрый старт

```bash
make setup      # venv, зависимости, .env из примера
make test       # 160 тестов
make up-local   # полный стек со встроенным Temporal, UI на localhost:8080
make smoke      # проверить связность
```

`DRY_RUN=1` включён по умолчанию. В сухом режиме PR-Closer делает всё: клонирует, читает
ревью, получает патчи, применяет их, гоняет тесты, считает границы и пишет замеры — и не
делает ни одной записи в GitHub. Сухой прогон даёт те же данные для калибровки, что и боевой.

Боевой режим — отдельным действием:

```bash
make go-live    # выключить DRY_RUN и перезапустить воркер
```

### Три режима запуска

PR-Closer собран для контура, где замечания приходят от PR-Agent, но не зависит от него.
Ручной запуск одной сессии — `scripts/run_once.py`:

```bash
# 1. PR на GitHub, замечания от PR-Agent — штатный контур без вебхука
scripts/run_once.py --repo org/repo --pr 42

# 2. PR на GitHub, ревьюер — человек: логин не задан, берутся любые замечания
scripts/run_once.py --repo org/repo --pr 42 --any-reviewer

# 3. Локальная рабочая копия и список задач из файла:
#    ни PR-Agent, ни Issue-Agent, ни GitHub вообще
scripts/run_once.py --workspace ~/code/проект --tasks задачи.json --wait
```

Третий режим — не отладочный костыль. Это ответ на вопрос, работает ли closer сам по себе:
цикл, границы, тестовый гейт и стоп-слово не зависят ни от одного соседнего агента.
В нём же удобно давать агенту список правок напрямую: «вот что поправить, вот рабочая копия».

Формат файла задач минимальный — ровно то, что нужно циклу:

```json
[
  {"file": "app.py", "text": "обработать деление на ноль", "class": "blocker"},
  {"file": "app.py", "text": "переименовать переменную", "class": "nit"}
]
```

`class` можно опустить — сработает та же классификация, что и для неразмеченного ревью.

В автономном режиме цикл не ждёт сигналов: ревьюера нет, ждать нечего. Он завершается сам,
когда чинить станет нечего либо когда попытки исчерпаны.

### Что нужно заполнить в `.env`

| Переменная | Зачем |
|------------|-------|
| `GITHUB_TOKEN` | Чтение PR, метки, комментарии, merge. Только репозиторий этого PR |
| `ZAI_API_KEY` | Исполнитель правок |
| `TEMPORAL_ADDRESS` | Только для внешнего кластера; в `up-local` подставляется сам |
| `GITHUB_WEBHOOK_SECRET` | Проверка подписи вебхука. Пусто — проверка отключена |

### GitHub App

Автостарт цикла требует регистрации приложения — это действие владельца организации:

1. Создать GitHub App в настройках организации.
2. Права: **Contents** (запись — коммиты в ветку PR), **Pull requests** (запись — метки,
   комментарии, merge), **Issues** (запись — follow-up).
3. События: `Pull request review`, `Issue comment`, `Pull request`.
4. Webhook URL — адрес сервиса `webhook`, secret — в `GITHUB_WEBHOOK_SECRET`.
5. Установить приложение на нужные репозитории.

До регистрации цикл запускается вручную скриптом — этого достаточно для отладки и демо.

### Search attributes

Сшивают ленты Issue-Agent, PR-Agent и PR-Closer по одной задаче. Требуют регистрации
в кластере **до** первого запуска:

```bash
make register-search-attributes
```

Незарегистрированный атрибут не игнорируется — он валит задачу воркфлоу в бесконечный
ретрай. Поэтому это осознанный флаг запускающей стороны, а не значение по умолчанию.
Без регистрации `root-issue` всё равно виден: он пишется в memo, которое регистрации
не требует.

### Калибровка `diff_budget`

```bash
make calibrate
```

Скрипт откажется предлагать порог на выборке меньше 30 закрытых PR. Переключение
`soft` → `hard` делается вручную: порог должен пройти через человека.

## Что считается успешным финалом

PR завершён, если выполнены оба условия:

1. `blocker` пуст (либо разобран, либо явно эскалирован автору);
2. тесты не хуже `test_baseline` — ни одного нового упавшего идентификатора.

Незакрытые `major` и `nit` не блокируют финал. Они уходят в follow-up.
Открытый PR стоит дороже, чем открытая задача.

## Принятые допущения

Решения, принятые при доведении спецификации до реализуемости. Каждое можно пересмотреть,
но реализация опирается на них:

| # | Допущение | Почему так |
|---|-----------|------------|
| A1 | «Принудительно закрыть PR» = завершить работу агента над PR, а не отклонить изменения. При непустом `open_blockers` PR остаётся открытым и передаётся человеку | Выбрасывать готовый PR из-за того, что ревьюер начал придираться, — потеря работы. Но и вливать с известным блокером нельзя |
| A2 | Исполнитель правок — GLM-5.1 через z.ai в контейнере воркера | Прямо следует из требования «PR-Closer слабее первичного разработчика» и из готовой обвязки в poh-issue-agents |
| A3 | Числовые пороги: 3 круга, 2 попытки, 30 мин ожидания ревью, 72 ч эскалации, 0.8 порог совпадения | Круги заданы требованием, остальное — стартовые значения, вынесенные в конфигурацию и подлежащие калибровке |
| A4 | Человеческие замечания в цикле не чинятся | Цикл трёх кругов — про диалог двух агентов. Замечание человека адресовано автору PR |
| A5 | Merge выполняет агент, если branch protection это позволяет | Иначе «PR завершён» из HowToDemo не достигается автоматически |
