# Статус GitLab-интеграции

## Обзор

Контур `poh-issue-agents` поддерживает работу с GitLab-репозиториями параллельно с GitHub. Основная инфраструктура реализована и протестирована.

## Реализованные компоненты

### 1. Вебхук-эндпоинт (`/gitlab/webhook`)
- **Местоположение:** `webhook/main.py:442-510`
- **Функциональность:**
  - Приём вебхуков GitLab для всех типов событий
  - Проверка подписи (HMAC для GitLab 19.0+ и plain token для старых версий)
  - Нормализация событий в общую внутреннюю форму
  - Маршрутизация в общие обработчики delivery
  - Отсутствие 5xx ошибок (критично для GitLab без авто-ретраев)

### 2. GitLab-клиент (`worker/gitlab_client.py`)
- **Функциональность:**
  - Полный интерфейс API GitLab (комментарии, метки, файлы, MR)
  - Аутентификация через PAT/Project Access Token/Group Access Token
  - Git-операции (клонирование, коммиты, ветки)
  - Поддержка проектов во вложенных группах (кодирование путей)
  - DRY_RUN режим

### 3. Нормализация событий (`shared/gitlab_events.py`)
- **Функциональность:**
  - Перевод GitLab-событий в общую внутреннюю форму
  - Расчёт дельты меток (добавленные/удалённые)
  - Определение типа события (issues/issue_comment/pull_request)
  - Обработка различий в полях (iid vs number, title vs name)

### 4. Проверка подписи (`shared/gitlab_signature.py`)
- **Функциональность:**
  - Два режима: HMAC (GitLab 19.0+) и token (все версии)
  - Проверка времени доставки (защита от replay-атак)
  - Поддержка ротации ключей (несколько подписей)
  - Корректная обработка base64-кодированных ключей

### 5. Диспетчер провайдеров (`worker/forge.py`)
- **Функциональность:**
  - Автоматический выбор провайдера по репозиторию
  - Поддержка смешанного режима (часть репозиториев на GitLab, часть на GitHub)
  - Единый интерфейс для всех операций (через `__getattr__`)

### 6. Тестовое покрытие
- `test_gitlab_client.py` - 26 тестов для клиента
- `test_gitlab_events.py` - 18 тестов нормализации
- `test_gitlab_signature.py` - 16 тестов подписи
- `test_gitlab_webhook_endpoint.py` - 10 тестов вебхука
- `test_gitlab_webhook_resilience.py` - 16 тестов устойчивости

## Конфигурация окружения

### Обязательные переменные
```bash
# GitLab-аутентификация
GITLAB_TOKEN=                           # PAT/Project/Group Access Token
GITLAB_URL=https://gitlab.com           # Базовый URL (пусто → gitlab.com)

# Вебхук
GITLAB_WEBHOOK_SECRET=                  # Секрет вебхука
GITLAB_SIGNATURE_MODE=hmac              # hmac или token
GITLAB_BOT_LOGIN=                       # Логин сервисного аккаунта

# Маршрутизация
GITLAB_REPOS=                           # Список GitLab-репозиториев
```

### Схема работы
1. Пустой `GITLAB_REPOS` → все репозитории используют GitHub-драйвер
2. Непустой `GITLAB_REPOS` → репозитории из списка используют GitLab-драйвер
3. Репозитории не в `GITLAB_REPOS` и не в `ISSUE_AGENT_REPOS` → отклоняются

## Что работает

### Критерии приёмки (из .task.md)

| Критерий | Статус | Заметки |
|----------|--------|---------|
| 1. Открываю Issue | ✅ | Webhook принимает Issue Hook, стартует воркфлоу |
| 2. Квалификация | ✅ | post_comment, set_labels работают, duplicate_check через search_candidates |
| 3-5. Аналитика, БФТ, СТ | ⚠️ | Git-операции реализованы, нужна проверка живым прогоном |
| 6. Отзывы и комментарии | ✅ | Note Hook нормализуется, реакции работают |
| 7. Обрывы и нестабильность | ✅ | Никаких 5xx, обработки ошибок нет |
| 8. Develop получает задачу | ✅ | Метки обрабатываются через labels_added |
| 9. Develop исполняет | ⚠️ | Git-клиент работает, нужна проверка локального раннера |
| 10. Develop открывает PR | ✅ | open_change_request реализован с проверкой дубликатов |
| 11. PR-агент проводит ревью | ❌ | Отдельный сервис `poh-pr-agents` требует порта |
| 12. PR и Develop отлаживают код | ⚠️ | review_text работает, но без Review API GitLab |

## Ограничения и различия с GitHub

### Архитектурные различия
- **Нет GitHub App:** Используется статический токен вместо installation-токенов
- **Нет Timeline API:** Связь Issue↔MR собирается из `related_merge_requests` и `closed_by`
- **Нет сущности Review:** approvals (бинарно) + заметки (текст) вместо состояний APPROVED/CHANGES_REQUESTED
- **Нет user.type:** Боты различаются по логину сервисного аккаунта

### Семантические различия
- **Создание/обновление файлов:** POST для создания, PUT для обновления (GitHub — только PUT)
- **Конкурентная запись:** По `last_commit_id` (commit SHA), а не по blob SHA
- **Пути проектов:** Полный кодирование включая слэши (для вложенных групп)
- **Нет workflow_dispatch:** Стадия разработки идёт локальным раннером

## Следующие шаги

### Для проверки (сухой прогон)
1. Настроить переменные окружения для тестового GitLab-проекта
2. Создать вебхук в GitLab на `/gitlab/webhook`
3. Прогнать сценарий из `.task.md` (Роль 1: имитация пользователя)
4. Проверить логи Temporal и отсутствие ошибок (Роль 2: наблюдатель)

### Для production
1. Порт `poh-pr-agents` под GitLab (критерии 11-12)
2. Интеграция с GitLab CI для автотестов (если требуется)
3. Мониторинг специфичных метрик GitLab (rate limits, webhook disabled events)

### Для документации
1. Обновить `README.md` с разделом по GitLab-развертыванию
2. Добавить примеры конфигурации для разных сценариев
3. Документировать процесс настройки webhook в GitLab

## Поддержка

### Где править при проблемах
- **Вебхук не принимает доставку:** `webhook/main.py:gitlab_webhook`
- **События не нормализуются:** `shared/gitlab_events.py:normalize`
- **API-вызовы не работают:** `worker/gitlab_client.py`
- **Неправильный провайдер:** `worker/forge.py:provider_for`
- **Подпись не проходит:** `shared/gitlab_signature.py:verify`

### Логирование
- Вебхук: логгер `webhook` (уровень INFO для нормальных событий, WARNING для проблем)
- Клиент: логгер `gitlab_client` (INFO для DRY_RUN, WARNING для API-ошибок)
- Диспетчер: логгер `forge` (DEBUG для выбора провайдера)

## Заключение

Основная GitLab-инфраструктура реализована и протестирована. Контур может:
- Принимать вебхуки GitLab
- Обрабатывать задачи и комментарии
- Работать с метками и файлами
- Создавать Merge Requests

Для полного соответствия протоколу приёмки (все 12 критериев) нужен порт `poh-pr-agents` и проверка живым прогоном на реальном GitLab-проекте.
