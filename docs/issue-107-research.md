# Исследование #107: Централизованный репозиторий стандартов написания кода для AI-агентов

> **Дата:** 2026-08-23
> **Тип:** Исследование (не реализация)
> **Статус:** Завершено

---

## Executive Summary

Проведено систематическое исследование проблемы фрагментации стандартов написания кода между AI-агентами в IT-ландшафте организации. Анализ текущего состояния `poh-issue-agents` и существующих паттернов работы с AI-агентами показывает:

**Главная находка:** Система уже содержит зачатки централизованного управления стандартами через `AGENTS.md`, `.claude/skills/`, и продуманную архитектуру доставки контекста, но эти решения не систематизированы и не вынесены в отдельный репозиторий.

**Ключевая проблема:** Каждый репозиторий импровизирует свои стандарты (PR #97/#105 — обход декларативных паттернов хардкодом), что ведёт к архитектурной непоследовательности.

**Рекомендация:** Создать отдельный репозиторий `poh-coding-standards` с гибридным механизмом доставки (git-submodule + локальные расширения) и MCP-сервером для поиска по правилам.

## 1. Текущее состояние и анализ проблемы

### 1.1 Свидетельства проблемы (из контекста репозитория)

**Архитектурная непоследовательность (PR #97/#105):**
- Обход декларативных паттернов хардкодом вместо каноничного источника истины
- Отсутствие единого источника правил для архитектурных решений
- Разные агенты применяют разные подходы к одним и тем же задачам

**Существующие фрагментированные решения:**
- `AGENTS.md` — правила репозитория, дублируются между проектами
- `.claude/skills/` — 21+ скилл с пересекающимися паттернами
- `docs/ARCHITECTURE.md` — архитектурные принципы специфичные для сервиса
- Разные промпты в `prompts/` для похожих задач

### 1.2 Анализ текущих механизмов контекста в `poh-issue-agents`

**Существующие паттерны доставки контекста:**

| Механизм | Где используется | Преимущества | Недостатки |
|----------|----------------|---------------|------------|
| `AGENTS.md` | Корень репозитория, загружается как skill | Единый файл, человекочитаемый | Жёстко привязан к репозиторию |
| `.claude/skills/` | Монтируется в воркер как volume | Гибкость, модульность | Дублируется между репозиториями |
| `prompts/` directory | Монтируется в воркер как volume | Разделение по задачам | Нет версионирования |
| Docker volume mapping | `docker-compose.yml` | Простота Dev-окружения | Не подходит для продакшена |

**Анализ доставки скиллов (из `worker/Dockerfile` и `docker-compose.yml`):**

```dockerfile
# Из worker/Dockerfile
COPY .claude/skills /root/.claude/skills
RUN chmod -R +x /root/.claude/skills
```

```yaml
# Из docker-compose.yml
volumes:
  - ./.claude/skills:/app/.claude/skills:ro
```

**Вывод:** Система уже использует паттерн read-only volume для доставки контекста, что является хорошей основой для централизации.

## 2. Анализ механизмов подключения к репозиториям-потребителям

### 2.1 Критерии оценки механизмов

1. **Версионная детерминированность** — агент должен видеть ту же версию правил, что и при разработке
2. **Скорость обновления** — возможность быстрого распространения исправлений
3. **Независимость релизных циклов** — стандарты не должны быть привязаны к релизам сервисов
4. **Простота Dev-опыта** — минимальные усилия для подключения нового репозитория
5. **Совместимость с CI/CD** — автоматизация проверки и применения

### 2.2 Сравнительный анализ механизмов

#### Механизм 1: Git Submodule (Рекомендуемый базовый вариант)

**Как работает:**
```bash
# В репозитории-потребителе
git submodule add https://github.com/po-helper-org/poh-coding-standards.git .standards
git commit -m "Add centralized coding standards"
```

**Преимущества:**
- ✅ Чёткая фиксация версии через commit hash
- ✅ Независимый релизный цикл
- ✅ Единый механизм обновления (`git submodule update`)
- ✅ Встроенный в git, не требует дополнительной инфраструктуры
- ✅ История изменений правил видна в parent repo

**Недостатки:**
- ❌ Требует явного действия разработчика при обновлении
- ❌ Сложности с shallow clones в CI
- ❌ Возможны конфликты при merge, если не следить за обновлениями

**Детерминизм:**
```bash
# Фиксация конкретной версии
cd .standards
git checkout <specific-commit-hash>
cd ..
git add .standards
git commit -m "Pin standards to version abc123"
```

#### Механизм 2: Git Subtree (Альтернатива)

**Как работает:**
```bash
git subtree add --prefix=.standards https://github.com/po-helper-org/poh-coding-standards.git main --squash
```

**Преимущества:**
- ✅ Нет отдельной метадаты (.gitmodules)
- ✅ Проще для новичков
- ✅ Автоматически включается в clone

**Недостатки:**
- ❌ Сложнее обновлять (`git subtree pull`)
- ❌ История изменений смешивается
- ❌ Большие репозитории при частых обновлениях

#### Механизм 3: CI-синхронизация (Только для продакшена)

**Как работает:**
```yaml
# .github/workflows/sync-standards.yml
- name: Sync coding standards
  run: |
    curl -L https://raw.githubusercontent.com/po-helper-org/poh-coding-standards/main/.standards.tar.gz | tar xz
```

**Преимущества:**
- ✅ Всегда свежая версия (если нужно)
- ✅ Не требует действий разработчиков
- ✅ Контролируется через CI

**Недостатки:**
- ❌ Недетерминированность (плавающая версия)
- ❌ Сетевая зависимость в CI
- ❌ Невозможность отката к конкретной версии без tag

#### Механизм 4: Package Manager (Для очень больших стандартов)

**Как работает:**
```json
// package.json
{
  "devDependencies": {
    "@po-helper/coding-standards": "^1.2.3"
  }
}
```

**Преимущества:**
- ✅ Стандартный механизм зависимостей
- ✅ Семантическое версионирование
- ✅ Легкая установка и обновление

**Недостатки:**
- ❌ Требует поддержки package registry
- ❌ Сложнее для не-JS проектов
- ❌ Дополнительный уровень абстракции

### 2.3 Рекомендация: Git Submodule + CI-проверка

**Гибридный подход:**

1. **Основной механизм:** Git Submodule для детерминированности
2. **CI-валидация:** Проверка актуальности версии в CI
3. **Dev-фолбэк:** Локальная копия при проблемах с сетью

```yaml
# .github/workflows/standards-check.yml
- name: Check standards version
  run: |
    cd .standards
    CURRENT_VERSION=$(git rev-parse HEAD)
    LATEST_VERSION=$(git ls-remote origin main | cut -f1)
    if [ "$CURRENT_VERSION" != "$LATEST_VERSION" ]; then
      echo "⚠️ Standards are outdated: $CURRENT_VERSION vs $LATEST_VERSION"
      # Не блокируем, но предупреждаем
    fi
```

## 3. Механизм локального уточнения стандартов

### 3.1 Требования к механизму расширения

1. **Возможность переопределения** — репозиторий может менять/дополнять правила
2. **Явность конфликтов** — должно быть понятно, что и где переопределяется
3. **Приоритетизация** — понятный порядок применения правил
4. **Обратная совместимость** — отсутствие локальных файлов не должно ломать базовые правила

### 3.2 Анализ вариантов

#### Вариант 1: Локальный файл overrides.md (Рекомендуемый)

**Структура:**
```
.standards/                    # Центральные правила (submodule)
  ├── python/                  # Язык-специфичные
  │   ├── naming.md
  │   └── architecture.md
  └── security/
      └── authentication.md

.standards.local.md            # Локальные расширения (gitignored)
  ├── overrides:
  │   python/naming:           # Путь к правилу
  │     - "Использовать snake_case для локальных переменных"
  │     - "Классы называть с суффиксом Impl"
  ├── additions:
  │   - "Специфичные для проекта паттерны..."
  └── disabled_rules:
      - "python/architecture:prefer-composition-over-inheritance"
```

**Преимущества:**
- ✅ Явная структура, легко читать
- ✅ Понятный приоритет (локальный > центральный)
- ✅ Легко version control'ить (но не коммитить секреты)
- ✅ Совместимость с существующими инструментами

**Недостатки:**
- ❌ Требует парсинга YAML/JSON
- ❌ Сложнее для не-технических пользователей

#### Вариант 2: Директория .standards.overrides/

**Структура:**
```
.standards.overrides/
  ├── python/
  │   └── naming.local.md      # Полностью заменяет python/naming.md
  └── project-specific.md     # Новые правила
```

**Преимущества:**
- ✅ Естественная файловая структура
- ✅ Каждый файл — отдельное правило
- ✅ Легко диффить и мерджить

**Недостатки:**
- ❌ Неявный приоритет (перезапись по пути файла)
- ❌ Сложнее понять, какие правила активны

#### Вариант 3: Конфигурационный файл в корне

**Структура:**
```toml
# .standards-config.toml
[standards]
source = ".standards"
version = "abc123"

[overrides.python.naming]
enabled_rules = ["snake_case", "PascalCase"]
disabled_rules = ["camelCase"]
custom_rules = """
- Локальные переменные: snake_case
- Константы: UPPER_SNAKE_CASE
"""
```

**Преимущества:**
- ✅ Компактный конфиг
- ✅ Легко парсить
- ✅ Понятная структура

**Недостатки:**
- ❌ Сложнее для больших правил
- ❌ Теряется человекочитаемость markdown

### 3.3 Рекомендация: Гибридный подход

**Комбинация вариантов 1 и 2:**

1. **Базовые правила:** Из `.standards/` (submodule)
2. **Переопределения:** `.standards.overrides/` (директория)
3. **Конфигурация:** `.standards-config.toml` (метаданные и включения/выключения)

**Алгоритм применения правил:**

```python
def load_standards():
    # 1. Загружаем базовые правила
    base_rules = load_from_directory(".standards/")
    
    # 2. Применяем локальные переопределения
    override_rules = load_from_directory(".standards.overrides/")
    
    # 3. Применяем конфигурацию
    config = load_config(".standards-config.toml")
    
    # 4. Мерджим с приоритетом: overrides > base
    final_rules = merge_rules(base_rules, override_rules, config)
    
    return final_rules
```

## 4. Механизм подключения контекста во время работы агента

### 4.1 Требования к механизму подключения

1. **Производительность** — не должно замедлять работу агента
2. **Надёжность** — отсутствие сети не должно блокировать работу
3. **Актуальность** — агент должен видеть актуальные правила
4. **Гибкость** — поддержка разных типов агентов (Claude, OpenHands, другие)

### 4.2 Анализ вариантов

#### Вариант 1: Инъекция в системный промпт (Самый простой)

**Как работает:**
```python
system_prompt = f"""
Ты — AI-агент для разработки. Следуй этим стандартам:

{load_standards_content()}

Контекст задачи:
{task_context}
"""
```

**Преимущества:**
- ✅ Простота реализации
- ✅ Работает с любым агентом
- ✅ Понятно для разработчиков

**Недостатки:**
- ❌ Ограничение по длине промпта
- ❌ Контекст загружается целиком, даже если не нужен
- ❌ Сложно обновлять без перезапуска

#### Вариант 2: MCP-сервер с поиском (Рекомендуемый для продакшена)

**Как работает:**
```python
# MCP-server (Model Context Protocol)
@app.mcp_tool("search_standards")
def search_standards(query: str, language: str = None) -> List[str]:
    """Поиск по стандартам кодирования"""
    return vector_search(query, language=language)

@app.mcp_tool("get_standard")
def get_standard(rule_id: str) -> str:
    """Получить конкретное правило"""
    return load_standard(rule_id)
```

**Преимущества:**
- ✅ Эффективный поиск по релевантности
- ✅ Не перегружает контекст
- ✅ Масштабируется на большие наборы правил
- ✅ Возможность кэширования

**Недостатки:**
- ❌ Требует развёртывания MCP-сервера
- ❌ Дополнительная инфраструктура
- ❌ Зависимость от MCP-поддержки в агентах

#### Вариант 3: Файл CLAUDE.md с явными ссылками (Текущий подход)

**Как работает:**
```markdown
# CLAUDE.md

Этот проект следует стандартам из `poh-coding-standards`.

Основные правила:
- Архитектура: см. `.standards/architecture/`
- Python: см. `.standards/python/`
- Безопасность: см. `.standards/security/`

При возникновении вопросов обращайся к центральным правилам.
```

**Преимущества:**
- ✅ Понятно для разработчиков
- ✅ Работает с текущими инструментами
- ✅ Минимальные изменения

**Недостатки:**
- ❌ Требует ручного обновления ссылок
- ❌ Агент может не следовать ссылкам
- ❌ Нет гарантии применения правил

#### Вариант 4: Комбинация: Файл + MCP-сервер (Оптимальный)

**Двухуровневый подход:**

1. **Базовый уровень:** `CLAUDE.md` с ключевыми правилами и ссылками
2. **Продвинутый уровень:** MCP-сервер для глубокого поиска

```markdown
# CLAUDE.md

## Ключевые принципы (кратко)
1. Единый источник истины для конфигурации
2. Декларативные паттерны优于 хардкод
3. Безопасность по умолчанию

## Подробные правила
- Полные стандарты: `.standards/`
- Поиск по правилам: используй MCP-tool `search_standards`
- Конкретное правило: MCP-tool `get_standard("<rule-id>")`
```

### 4.3 Рекомендация: Пошаговый подход

**Этап 1 (MVP):** Инъекция в системный промпт
- Самый быстрый способ начать
- Подходит для прототипирования

**Этап 2 (Production):** MCP-сервер
- Для продакшена и больших проектов
- Эффективный поиск и кэширование

**Этап 3 (Hybrid):** Комбинация подходов
- Ключевые правила в промпте
- Глубокий поиск через MCP

## 5. Механизм валидации контента

### 5.1 Требования к валидации

1. **Качество контента** — понятность, непротиворечивость, полнота
2. **Актуальность** - правила соответствуют текущим практикам
3. **Применимость** - правила можно реально использовать
4. **Обратная связь** - механизм сбора отзывов

### 5.2 Анализ вариантов валидации

#### Вариант 1: Ревью человеком (Базовый)

**Процесс:**
1. Автор создаёт pull request в `poh-coding-standards`
2. Один или несколько ревьюеров проверяют:
   - Понятность формулировок
   - Отсутствие противоречий
   - Соответствие практике
3. После approvals PR мёржится

**Преимущества:**
- ✅ Высокое качество контента
- ✅ Человеческий контроль
- ✅ Обучение через ревью

**Недостатки:**
- ❌ Требует времени ревьюеров
- ❌ Субъективность оценки
- ❌ Масштабируется сложно

#### Вариант 2: Self-improvement контур (Рекомендуемый)

**По аналогии с MetaReviewer (#92):**

```python
# self_validation_workflow.py
def validate_standard(rule_content: str) -> ValidationResult:
    """Проверка качества правила с помощью LLM"""
    
    # 1. Проверка на двусмысленность
    ambiguity_check = llm.check_ambiguity(rule_content)
    
    # 2. Проверка на противоречия с существующими правилами
    contradiction_check = llm.check_contradictions(rule_content, existing_rules)
    
    # 3. Проверка на применимость
    applicability_check = llm.check_applicability(rule_content)
    
    return ValidationResult(
        is_valid=all([ambiguity_check.passed, 
                      contradiction_check.passed,
                      applicability_check.passed]),
        issues=[ambiguity_check.issues, 
                contradiction_check.issues,
                applicability_check.issues]
    )
```

**Преимущества:**
- ✅ Автоматизация рутинных проверок
- ✅ Последовательность критериев
- ✅ Масштабируемость
- ✅ Обучение на предыдущих правилах

**Недостатки:**
- ❌ Требует настройки LLM
- ❌ Возможны ложные срабатывания
- ❌ Всё равно needs human review

#### Вариант 3: Комбинированный подход (Оптимальный)

**Двухуровневая валидация:**

1. **Автоматическая валидация (LLM):**
   - Проверка на двусмысленность
   - Проверка на противоречия
   - Проверка на полноту

2. **Человеческое ревью:**
   - Фокус на содержании и применимости
   - Обсуждение edge cases
   - Одобрение публикации

**Процесс:**
```yaml
# .github/workflows/validate-standard.yml
name: Validate Coding Standard

on:
  pull_request:
    paths:
      - '.standards/**'

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Run automatic validation
        run: |
          python scripts/validate_standards.py --path .standards
      - name: Check for human review
        if: failure()
        run: |
          echo "⚠️ Automatic validation failed, requires human review"
```

### 5.3 Рекомендация: Комбинированный подход

**Структура процесса валидации:**

1. **Pre-commit хуки:**
   - Базовая проверка форматирования
   - Проверка на минимальную длину
   - Проверка на запрещённые слова

2. **CI-валидация (LLM):**
   - Проверка на двусмысленность
   - Проверка на противоречия
   - Генерация резюме для ревьюера

3. **Human review:**
   - Проверка содержательной части
   - Обсуждение с автором
   - Final approval

## 6. Формат файлов и структура

### 6.1 Требования к формату

1. **Человекочитаемость** — разработчики должны понимать правила
2. **Машинная обрабатываемость** — агенты должны уметь извлекать правила
3. **Модульность** — возможность комбинировать правила
4. **Версионирование** — отслеживание изменений

### 6.2 Анализ вариантов форматов

#### Вариант 1: Чистый Markdown (Самый простой)

**Пример:**
```markdown
# Python: Naming Conventions

## Переменные
Используйте `snake_case` для локальных переменных и функций.

## Классы
Используйте `PascalCase` для классов.

## Константы
Используйте `UPPER_SNAKE_CASE` для констант.
```

**Преимущества:**

## Заключение

Исследование показало, что централизованный репозиторий стандартов написания кода для AI-агентов — это не просто возможное решение, а **необходимый компонент** инфраструктуры для поддержания качества кода в организации, где активно используются AI-агенты.

**Ключевые выводы:**

1. **Проблема реальна и уже проявляется** (PR #97/#105)
2. **Техническое решение существует** — комбинация git-submodule + MCP-сервер
3. **Организационный процесс критически важен** — валидация и обратная связь
4. **Постепенное внедрение** — от простого к сложному

**Рекомендуемый подход:** Начать с простого (файлы + инъекция в промпт), постепенно усложняя до полноценного MCP-сервера с валидацией и поиском.

Это решение позволит решить текущие проблемы inconsistency в коде и создаст фундамент для масштабирования использования AI-агентов в организации.
