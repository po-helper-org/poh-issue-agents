# Delivery-Agent: как контур отгружает одобренные PR

Релиз-менеджер контура. Код живёт в отдельном репозитории
[`po-helper-org/poh-delivery-agent`](https://github.com/po-helper-org/poh-delivery-agent)
и ставится в образ воркера пакетом; здесь — только точка подключения
(`worker/delivery_bridge.py`) и маршрут команды в вебхуке.

Зона ответственности одна: **довести одобренные PR до прода и убедиться, что
система ведёт себя так, как описано**. Всё, что до одобрения, — не его работа.

## Запуск

| Триггер | Где | Что делает |
|---|---|---|
| комментарий `/release` | любой Issue или PR наблюдаемого репозитория | запускает релиз ВСЕГО репозитория |
| метка `run:release` | Issue репозитория | то же самое, в два тапа с телефона |

Релиз — команда репозитория, а не задачи: агент сам смотрит все открытые PR.
Issue, из которого позвали, служит адресом для ответа, и только им.

Id воркфлоу — `delivery-<owner>/<repo>`, **один релиз на репозиторий за раз**.
Вторая команда при идущем релизе упирается в `WorkflowAlreadyStarted`: два плана,
мержащие в одну ветку, не смогли бы честно сказать, что они выкатили.

## Кто попадает в релиз

Вердикт по каждому открытому PR (`poh_delivery/rules.py`), порядок проверок —
порядок дешевизны отказа:

| Вердикт | Когда | Что дальше |
|---|---|---|
| `draft` | черновик | пропуск |
| `not-approved` | нет `APPROVED`-ревью и нет метки `ready-to-ship` / `approved-to-merge`; либо `mergeable_state=blocked` | пропуск: одобряет человек, защиту ветки агент не обходит |
| `conflict` | `mergeable=false` или `mergeable_state=dirty` | **делегируется агенту разработки**, затем пересъём фактов |
| `checks-red` | сводка проверок головного коммита — `failure` | пропуск |
| `checks-pending` | проверки идут; `mergeable_state=unstable`; GitHub ещё считает мержабельность | пропуск: неизвестность — не разрешение |
| `eligible` | одобрен, конфликта нет, проверки зелёные | в очередь |

`behind` (ветка отстала) конфликтом не считается: GitHub вливает такой PR сам, а
то, что проверки в нём гонялись не на текущей базе, ловит проверка после мержа —
не планировщик.

## Конфликты: делегирование, а не догадка

Конфликтующий PR уходит активности `delivery_fix_conflicts` на очереди
`issue-lifecycle` — это Harness, тот же OpenHands, что пишет код по задачам.
Второй машинерии для разрешения конфликтов не заводится.

1. Полный клон ветки PR + история базы.
2. `git merge origin/<base>`. Свёлся сам — пуш, и агент не звался вовсе:
   изрядная часть «конфликтов» это расхождение, которое git разводит без чужой
   помощи.
3. Не свёлся — постановка в `.task.md` (список конфликтных файлов, требование
   сохранить обе функциональности, запрет на посторонние правки) и одноразовый
   контейнер агента.
4. Остались маркеры конфликта — `merge --abort` и честный отказ. Иначе в ветку
   уехал бы полуразрешённый мерж.
5. Успех — коммит, пуш, комментарий в PR, пересъём фактов и повторный вердикт.

Круг ровно один на PR за релиз: если первый заход не развёл конфликт, второй на
том же входе даст то же самое.

## Очередь

Порядок считает код, а не модель: по одному снимку состояния план обязан
собираться дважды одинаково, иначе разбор неудачной выкатки упирается в «модель
так решила».

- **Риск по возрастанию.** `high` — от 6 файлов или 200 строк правки,
  `medium` — от 3 файлов или 50 строк, иначе `low`. Дешёвая правка уезжает
  первой и проверяет весь тракт (мерж → выкатка → проверки → откат) до того, как
  через него поедет дорогая.
- **При равном риске — номер PR**, то есть порядок появления.
- **Общие файлы дают зависимость**: PR, трогающий тот же файл, что сосед выше по
  очереди, идёт строго после него, и это записано в плане. Иначе второй мерж
  принёс бы конфликт, которого в плане не было.

## Оформление релиза

Релиз создаётся **черновиком до первого мержа**: ссылка нужна в PR раньше
выкатки, а опубликованный релиз до отгрузки означал бы «уже отгружено».
Тег — `release-<YYYY-MM-DD>.<N>`, дата берётся из детерминированного времени
воркфлоу.

Черновик несёт: репозиторий и базовый SHA, id воркфлоу и RunID, таблицу очереди
(шаг, PR, риск, обоснование места, зависимости), список проверок с источником
требования, порядок выкатки одного шага, отданное разработчику и не вошедшее с
причинами. Ссылка на релиз публикуется комментарием **во всех входящих PR**.

После выкатки в тот же релиз дописывается отчёт — что влито и каким SHA, что
изменилось для пользователей (с задачей, которую закрывает PR), таблица проверок
по шагам, что пошло не так и что откачено, взаимосвязанные изменения и ссылка на
историю Temporal. После этого релиз публикуется; пустая очередь оставляет его
черновиком.

## Шаг выкатки и проверки

```
пересъём фактов PR → мерж (squash) → выкатка базы на прод-контур → проверки живого сервиса
```

Пересъём перед каждым шагом обязателен: между планом и шагом состояние успевает
измениться — влитый сосед делает ветку `behind`, ревью снимает одобрение.
Разошлось — шаг пропускается с причиной, релиз продолжается.

**Прод-контур** — контейнер на хосте воркера, поднятый из состояния базовой ветки
на общем томе (`poh-dev-workspace`). Каталог именуется SHA и не переиспользуется:
откат — это возврат к уже разложенному каталогу, а не повторный клон, который в
момент аварии может не собраться.

**Что проверять, решает целевой репозиторий** файлом `.delivery/checks.json`:

```json
{
  "service": { "port": 8080, "start": "node src/server.mjs", "health_path": "/healthz" },
  "checks": [
    { "name": "quote-base", "method": "POST", "path": "/quote",
      "body": { "items": [{ "sku": "a", "price": 1000, "qty": 2 }] },
      "expect_json": { "goods": 2000, "delivery": 300, "total": 2300 },
      "source": "README, раздел «Сервис»" }
  ]
}
```

Ожидания — подмножество ответа, поэтому новые поля проверок не ломают. Поле
`source` тянет проверку к требованию (БФТ, README, пункт HowToDemo): проверка без
источника — это мнение агента о том, как должно быть.

Нет файла — релиз идёт, но в плане честно написано, что подтверждать поведение
нечем, кроме факта запуска сервиса.

## Откат

Провал любой проверки или мёртвая выкатка:

1. `git revert` мерж-коммита в базовой ветке — откат обязан быть виден в
   репозитории, а не только в логах агента.
2. Возврат прода на получившееся состояние базы.
3. Комментарий в PR с причиной и **остановка очереди**: остаток шагов не едет.

Откат не удался — это говорится прямым текстом («нужна рука человека»), а не
прячется в статус.

## Конфигурация

| Переменная | Умолчание | Зачем |
|---|---|---|
| `DELIVERY_TASK_QUEUE` | `delivery` | очередь воркера релиза |
| `DELIVERY_WORKSPACE_VOLUME` / `_MOUNT` | `poh-dev-workspace` / `/workspaces` | том, общий с раннером |
| `DELIVERY_PROD_CONTAINER` | `poh-delivery-prod` | имя контейнера прод-контура |
| `DELIVERY_RUNTIME_IMAGE` | `node:22-slim` | образ, если репозиторий не задал свой |
| `DELIVERY_PROD_NETWORK` | сеть воркера | куда ставить прод-контейнер |
| `DELIVERY_READY_TIMEOUT` | `90` | сколько ждать, пока сервис ответит |
| `DRY_RUN` | пусто | мутации GitHub и docker только логируются |

## Границы

Агент не одобряет PR за человека, не обходит защиту ветки, не переписывает чужой
код (кроме разрешения конфликтов руками агента разработки) и не решает, что
считать правильным поведением сервиса — это описывает репозиторий.
