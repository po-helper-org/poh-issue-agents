# Хвост цикла: честная запись исхода — план реализации

**Goal:** Задача, доведённая до `main`, записывается как влитая, а не как снятая
с обработки, и разрыв канала доклада перестаёт быть невидимым.

**Задачи:** #308 (эта работа), #309 (фазы `testing`/`released` — решение
человека, кодом здесь не трогается), #103 (канал доклада — настройка стенда).

**Architecture:** Правка идёт в трёх местах и ровно по одному разу в каждом.
Модель фаз (`shared/lifecycle.py`) получает недостающий переход; решение
воркфлоу, которое этим переходом пользуется, идёт под своим маркером
`workflow.patched`; вебхук получает запись об отказе подписи. Ни новых сущностей,
ни новых зависимостей: всё три точки уже существуют и покрыты тестами.

**Tech Stack:** Python 3.12, Temporal Python SDK, pytest, FastAPI (вебхук).

## Global Constraints

- Тесты гонять командой репозитория: `python -m pytest -q`. Порог покрытия — 83%.
- **Раскладка:** `worker/` и `webhook/` НЕ пакеты. Внутри воркера — `import
  activities`, `import workflows`. Общий код — только `shared/`.
- **Правка решения воркфлоу требует `workflow.patched(...)`.** Прогоны
  `IssueLifecycle` живут неделями; ветка, которую прогон уже выбрал, записана в
  его историю, и новый код на реплее выберет другую. Это не теория: разбор #263 и
  гвард `scripts/deploy_guard.py --replay` заведены ровно по этому поводу.
- Гвард реплея `tests/test_workflow_replay.py` обязан оставаться зелёным.
- Секрет и тело доклада не попадают в лог ни при каком отказе.

## Что уже есть

- `lifecycle.TRANSITIONS[PR_OPEN]` — четыре внешних перехода (`pr-review`,
  `in-development`, `failed`, `escalated`) и `cancelled` от человека. Перехода в
  `merged` нет.
- `IssueLifecycle._phase_on_close` (`worker/workflows.py:961`) — спрашивает у
  GitHub `pr_is_merged` и возвращает `merged` либо `cancelled`. Вопрос задаётся
  ТОЛЬКО если `lifecycle.can(фаза, merged)`; иначе `cancelled` без вопроса.
- Маркер `issue-lifecycle-merged-on-close` (`worker/workflows.py:1231`) — вся
  ветка закрытия уже под ним.
- `tests/test_workflow_closed_by_merge.py` — три проверки: влитый PR даёт
  `merged` (из `pr-review`), невлитый — `cancelled`, без PR вопрос не задаётся.
- `verify_agent_signature` (`webhook/main.py:286`) — три пути отказа, ни одной
  записи в лог.
- `tests/test_agent_event_endpoint.py` — проверки отказа по статусу ответа.

## Task 1: переход `pr-open → merged` в модели

- [x] `shared/lifecycle.py`: в `TRANSITIONS[PR_OPEN]` добавить
      `Transition(MERGED, EXTERNAL, "PR влит")`. Инициатор `external`, потому что
      факт слияния приносит GitHub, а не стадия контура.
- [x] `tests/test_lifecycle_phases.py`: `can('pr-open', 'merged')` истинно, и
      `pr-review → merged` не сломан.

**Почему переход, а не обход проверки в воркфлоу.** Таблица объявлена
единственным источником правды о пути задачи. Обойти её в одном вызове — значит
завести второй, невидимый источник: путь, которого в таблице нет, а в жизни есть.

**Почему `pr-open`, а не любая фаза.** Из `in-development` номер PR циклу
неизвестен (он запоминается при открытии PR, и тогда же фаза становится
`pr-open`), а `_phase_on_close` без номера вопроса не задаёт вовсе. Расширять
дальше нечего.

## Task 3: видимый след отвергнутого доклада

- [x] `webhook/main.py::verify_agent_signature`: каждый из трёх отказов пишет
      предупреждение в логгер `webhook` с причиной (нет секрета / нет подписи /
      подпись не совпала). Ни секрета, ни тела, ни самой подписи в записи нет.
- [x] `tests/test_agent_event_endpoint.py`: три проверки через `caplog` — запись
      появляется, и в ней нет ни секрета, ни тела.

**Почему лог, а не Sentry.** Отказ подписи означает разошедшуюся настройку
соседнего сервиса, а не сбой прогона: разбирать его будет тот, кто смотрит на
стенд, и первым делом в логе вебхука. Событие Sentry на каждый чужой запрос к
публичному эндпоинту — это ещё и шум от сканеров.

## Границы

- Фазы `testing` и `released` эта работа не трогает: их не докладывает никто, и
  выбор между «завести докладчика» и «сократить модель» — за человеком (#309).
- Канал доклада ревью здесь не чинится: он выключен настройкой стенда (#103).
  Правка Task 1-2 нужна независимо от него — она о том, что записано об исходе,
  а не о том, кто об этом доложил.
