# Полный путь Issue: Research, декомпозиция, Develop

Дата: 2026-08-17. Статус: дизайн согласован, реализация не начата.

## Задача

Сегодня цикл доводит Issue до `classified` и парковки в ожидании человека, а
дальше путь обрывается: аналитика идёт одним прогоном без приёмки, подзадачи не
заводятся вовсе, разработка упирается в `trigger_openhands_resolver`. Нужен весь
путь от запроса на GitHub до закрытия Issue, с двумя ключевыми активностями
контура:

- **Research** — превратить запрос в продуктовое исследование, БФТ, системные
  требования и декомпозицию на подзадачи;
- **Develop** — взять подготовленный Issue, автономно разработать, открыть PR,
  довести его до слияния.

## Решения по открытым вопросам

Приняты владельцем 2026-08-17.

| Вопрос | Решение | Отвергнутая альтернатива и почему |
|---|---|---|
| Владение SubIssue | Плоско: каждая подзадача — самостоятельный root-прогон `IssueLifecycle`. Родитель завершается сразу после декомпозиции | Child-прогоны дали бы дерево в UI и каскадную отмену, но вернули бы долгоживущего родителя и рост истории — ровно то, от чего уходим |
| Закрытие родителя | `ParentRollup` — короткий прогон без состояния, считает готовность из GitHub | Долгоживущий родитель с агрегатом в памяти (см. выше); человек руками (родители копились бы открытыми) |
| Гранулярность Research | Прогон на документ + парковка на приёмку между документами | Один прогон на всю цепочку: правка в БФТ требовала бы повторить всё, включая оплаченные LLM-минуты |
| Владение PR-частью | Фазы того же цикла, работу ведёт внешний агент, факты приходят событиями | Прогон на попытку/на PR: события коррелируются по `Closes #N` и ветке, то есть адресованы Issue — ребёнку их пришлось бы перекидывать |

## Единицы владения

| Прогон | Workflow ID | Время жизни | Ответственность |
|---|---|---|---|
| `IssueLifecycle` | `issue-<repo>-<n>` | от `issues.opened` до терминальной фазы | владелец состояния одного Issue любого уровня |
| Research-прогон | `research-<repo>-<n>-<doc>` | минуты | ровно один документ: `product`, `bft`, `sysreq`, `decompose` |
| `ParentRollup` | `rollup-<repo>-<n>` | секунды | пересчёт готовности родителя, закрытие |
| Develop | своих прогонов нет | — | activity `dispatch_workflow`, дальше фазы двигают события |

Один и тот же код цикла обслуживает родителя и подзадачу: SubIssue — это Issue,
у него свой `issues.opened`, свой прогон, свой путь. Рекурсия бесплатна, потолок
глубины уже есть (`ProtocolState.depth_exceeded`, ключ `root-issue: #N`).

## Карта фаз

```
created
  | триаж: префильтр, intake gate, классификация, дедуп, приоритет
classified
  | research-me / run:analyze
product-research --approved--> bft --approved--> system-requirements --approved-->
  |                                                                    |
  |                                    нужна декомпозиция? --> decomposition --> decomposed
  |                                    лист?                --> ready-for-dev
  | build-me (или develop_autostart)
in-development --> pr-open --> pr-review --> merged --> testing --> released
                                  |
                                  +-- changes requested --> in-development (попытка N+1)
```

### Что добавляется в `shared/lifecycle.py`

Новые фазы: `product-research`, `bft`, `decomposition`, `decomposed`.

`business-analysis` остаётся в таблице **как устаревшая**: метка
`phase:business-analysis` висит на живых Issue, и прогоны в этой фазе идут прямо
сейчас. Код в неё больше не входит, но переход из неё в `bft` обязан быть
допустимым — иначе первый же возврат такого Issue в работу упрётся в
`InvalidTransition`.

Новые переходы (сокращённо):

- `classified -> product-research` (HUMAN: research-me / run:analyze)
- `product-research -> bft`, `bft -> system-requirements` (AGENT: документ принят)
- любой research-фазы `-> сама в себя` не бывает: доработка документа — это
  повторный прогон внутри той же фазы, фаза не меняется
- `system-requirements -> decomposition` (AGENT: решение о декомпозиции)
- `decomposition -> decomposed` (AGENT: подзадачи заведены)
- `decomposed -> cancelled` (HUMAN/AGENT: родитель закрыт), `decomposed -> classified` (HUMAN: вернуть в работу)
- из каждой research-фазы: `-> escalated` (дедлайн приёмки истёк), `-> failed` (прогон сорвался), `-> cancelled` (agents:off)

## Приёмка документов

Каждый документ публикуется в ветку `research/issue-<n>` и комментарием в Issue,
после чего цикл паркуется: `Awaiting(kind=APPROVAL)` — этот вид ожидания уже
есть в `shared/awaiting.py`, со сроком 72 ч по таблице.

Управление метками, а не командами: два тапа в мобильном GitHub против набора
текста, и это уже принятый в контуре способ (`run:*`, `research-me`).

| Метка | Что делает |
|---|---|
| `approved` | документ принят, цикл идёт к следующей фазе |
| `rework` | вернуть на доработку: тот же документ, новый прогон, входом идут комментарии человека, добавленные после публикации |

Метку ставит человек, снимает цикл при переходе — правило «одна метка, один
писатель» соблюдено: writer у `approved`/`rework` один (человек), очищает их тот
же цикл, что и ставит `phase:*`.

Потолок доработок одного документа — `MAX_REWORK_ROUNDS = 3`. Дальше `escalated`
с причиной: три круга правок означают, что расходится постановка, а не текст.

Срок приёмки истёк — `escalated`, как и на всех прочих парковках (единое правило
R3: действие по истечении одно — передать человеку).

### Режим без человека

Поле `Deadlines.research_auto_approve: bool = False` (переменная
`RESEARCH_AUTO_APPROVE`). True — цикл не паркуется на приёмку и идёт по цепочке
насквозь. Ровно тем же приёмом, что и `develop_autostart`: значение едет через
activity и лежит в истории, поэтому переключение тумблера посреди прогона не
уронит реплей недетерминизмом.

## Декомпозиция

Решение «нужна ли декомпозиция» принимает прогон `research-...-decompose` на
основании системных требований, а не эвристика в коде цикла.

Заведение подзадач — activity: для каждой позиции создаётся Issue с телом
(`root-issue: #N`, ссылка на артефакты), меткой `origin:agent`, и связью
parent/child через sub-issues API. Дальше подзадачу подхватывает обычный
`issues.opened`.

Ограничения:

- `MAX_SUBISSUES = 20` на один родительский Issue: больше — признак того, что
  декомпозиция ушла в задачи-однострочники, тут нужен человек, а не цикл;
- глубина не больше 2 (`depth_exceeded` из протокола): внук уже не создаётся;
- подзадача помечена `origin:agent`, поэтому её триаж сокращённый, а путь
  начинается с `system-requirements` — продуктовое исследование и БФТ для неё
  уже сделаны на уровне родителя.

Идемпотентность: перед созданием activity ищет среди существующих подзадач
родителя ту же позицию по заголовку. Повторный прогон декомпозиции (rework) не
плодит дубли, а дописывает недостающее.

## Develop

`ready-for-dev` паркуется в ожидании `build-me` (или проходит насквозь при
`develop_autostart`). Затем:

1. activity `trigger_openhands_resolver` делает `workflow_dispatch` в
   репозитории-цели (`shared/develop.py` — контракт уже написан);
2. цикл переходит в `in-development` и паркуется на `Awaiting(EXTERNAL_AGENT)`;
3. внешние агенты (OpenHands, PR-Agent, PR-Closer, CI) шлют факты в
   `POST /agent-event`; корреляция по `Closes #N` и ветке `research/issue-N`
   доводит их до нужного цикла;
4. фазы `pr-open`, `pr-review`, `merged`, `testing`, `released` двигаются этими
   фактами, идемпотентность — по ключу `ref:phase:status`.

Доработка (`pr-review` запросило изменения) возвращает фазу в `in-development` и
увеличивает счётчик попыток в состоянии цикла. Потолок `MAX_PR_REWORK_ROUNDS = 3`,
дальше `escalated` с `needs-human:pr`: если три круга ревью не сошлись, дело не в
коде.

## ParentRollup

Триггер: `issues.closed` по Issue, у которого есть родитель.

Вебхук стартует `rollup-<repo>-<parent>`. Прогон:

1. ждёт 30 с (debounce): подзадачи закрываются пачкой, и одно чтение после всей
   пачки дешевле и честнее пяти чтений вперемешку с закрытиями;
2. читает sub-issues API родителя;
3. все закрыты — закрывает родителя с итоговым комментарием (список подзадач и
   их PR); не все — обновляет комментарий прогресса и выходит.

Гонки: id один на родителя. Если прогон уже идёт, вебхук шлёт ему сигнал
`recheck`, продлевающий debounce, вместо старта второго. Состояние нигде не
хранится — оно всегда пересчитывается из GitHub, поэтому потерянное событие
самолечится следующим закрытием, а лишнее событие безвредно.

## Сбои

| Отказ | Поведение |
|---|---|
| Research-прогон сорвался | фаза `failed`, комментарий с причиной, `Awaiting(FAILURE_RECOVERY)` 168 ч |
| `workflow_dispatch` не принят | `failed` немедленно: соврать про запуск хуже, чем не запустить |
| Внешний агент молчит | дедлайн `EXTERNAL_AGENT` 24 ч, дальше `escalated` |
| Дедлайн приёмки истёк | `escalated`, метка `needs-human:triage` |
| Issue закрыт руками | сигнал `issue_closed`, фаза `cancelled`, цикл завершается (уже реализовано) |
| Потолок кругов правок | `escalated` с причиной, где именно круг не сошёлся |

## Миграция

Порядок раскатки — каждый шаг отдельно проверяем в проде:

1. выкатить текущий `main` (прод отстал на три коммита; это чинит самоподдув
   дедлайнов и подпись под комментариями);
2. фазы Research и приёмка — под `workflow.patched("issue-lifecycle-research-docs")`:
   припаркованные прогоны продолжают идти по старому коду;
3. декомпозиция и `ParentRollup` — новый прогон и новая activity, старых историй
   не касаются;
4. Develop autostart — тумблером, после того как ручной `build-me` отработал.

## Тестирование

- таблица переходов — свойствами (`test_lifecycle_phases`): каждая новая фаза
  достижима, из каждой есть путь в терминал, `business-analysis` не тупик;
- приёмка и доработка — time-skipping окружение: `approved` двигает фазу,
  `rework` запускает тот же документ заново, четвёртый круг эскалирует, истёкший
  срок эскалирует;
- декомпозиция — activity с фейковым GitHub: потолок 20, идемпотентность по
  заголовку, `root-issue` и `origin:agent` в теле;
- `ParentRollup` — чистая функция «все ли дети закрыты» отдельно от activity,
  плюс тест на debounce и повторный сигнал;
- Develop — событие каждого вида двигает фазу ровно один раз, повтор не двигает.

## Что не входит

- собственный прогон на PR (`PRLifecycle`) — ответственность `poh-pr-agents`;
- груминг как обязательный шаг: `groomed` остаётся возможностью, не условием;
- возврат родителя в работу после `decomposed` автоматом — только явным
  действием человека.
