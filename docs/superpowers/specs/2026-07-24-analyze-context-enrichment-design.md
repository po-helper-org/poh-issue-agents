# Обогащение контекста `/analyze`: комментарии + связанные PR

- **Дата:** 2026-07-24
- **Статус:** одобрено к реализации
- **Область:** `worker/activities.py`, `worker/github_client.py`, тесты

## Проблема

Пайплайн `/analyze` (`run_analysis_pipeline`) кормит FNR-цепочку только
`title + issue.body` плюс repomix дефолтной ветки. Аудит issue
[po-helper-org/poh-pr-agents#1](https://github.com/po-helper-org/poh-pr-agents/issues/1)
показал: тело issue — статичный трекинг-снимок (все чекбоксы пусты), а живое
состояние задачи (зафиксированные решения, готовые артефакты, прогресс по фазам,
найденные ревью-риски) целиком лежит в **17 комментариях и 4 связанных PR**,
которых пайплайн не видит. Итог: анализ переспрашивает уже решённое и предлагает
делать уже сделанное.

Замысел «исключить команды из треда, уходящего в модель» уже зафиксирован в
докстринге `shared/commands.py` — но тред в модель никогда не собирался. Эта
доработка его реализует.

## Цель

Собирать в `description`, уходящий в `/fnr-new-task`, живой контекст issue:
**комментарии обсуждения** (с фильтром командного шума) и **связанные PR**.

### Не-цели (сознательно вне области)

- Стиринг через текст командного коммента (`/analyze разбери фазу 2`) — отдельный тир.
- Лейблы issue.
- Явные указатели claude на дизайн-доки (комментарии и так их называют; repomix их и так пакует).
- Отдельная Temporal-activity под fetch — контекст не должен идти в event history.

## Архитектура

Обогащение живёт **внутри `run_analysis_pipeline`** (подход A). Причины:
контекст остаётся в воркере и не сериализуется в Temporal history (нет роста
payload); ложится на уже принятый дизайн «одна activity = клон + repomix +
claude + push» (обоснован в докстринге функции) и на текущие тесты
(monkeypatch `github_client`). Изоляцию и тестируемость даёт выделенный хелпер
плюс отдельная функция клиента — не отдельная activity.

### Компоненты

**1. `github_client.list_linked_prs(repo, issue_number, limit=20) -> list[dict]`** — новый.

- Дёргает Timeline API: `GET /repos/{repo}/issues/{n}/timeline`
  с заголовком `Accept: application/vnd.github.mockingbird-preview+json`.
- Фильтр: события `event == "cross-referenced"`, где `source.issue`
  содержит ключ `pull_request` (кросс-ссылка именно на PR, не на issue).
- Возврат: `[{number, title, state, url}]`, дедуп по `number`, максимум `limit`.
- Это read-операция: `_dry_run()` её не трогает (dry-run гейтит только мутации).
- Сбой HTTP → поднимает исключение (ловит вызывающий хелпер, см. деградацию).

**2. `activities._build_task_context(analyze: AnalyzeInput) -> str`** — новый.

Заменяет строку `description = f"{analyze.title}\n\n{analyze.body}"`
(`activities.py:487`). Собирает многосекционный markdown-бриф.

### Поток данных

1. **База (всегда):** `# {title}\n\n{body}`.
2. **Комментарии:** `github_client.list_comments(repo, n, limit=50)`.
   - **Фильтр шума:** выкинуть комментарии, где
     `shared.commands.parse_command(body) is not None` — уносит голые `/analyze`
     и `/analyze …` (командные комментарии-триггеры).
   - Взять **последние 20** оставшихся (самые свежие = самое актуальное
     состояние), каждый обрезать до **1500 символов** (с маркером `…[обрезано]`),
     префикс `@{user.login} ({created_at:ГГГГ-ММ-ДД}):`.
   - Секция `## Обсуждение`.
3. **Связанные PR:** `list_linked_prs(repo, n)` → секция `## Связанные PR`,
   строки `- #{number} {title} [{state}] {url}`.
4. **Общий потолок 16 000 символов:** `title + body` не режутся никогда; если
   бриф превышает потолок — отбрасывать комментарии от **самых старых к свежим**,
   пока влезает. PR-секция компактна, идёт после комментариев.

### Обработка ошибок — деградация

Каждый внешний вызов (`list_comments`, `list_linked_prs`) в отдельном
`try/except`. Исключение → `logging.warning`, секция пропускается, сборка
продолжается. **Прогон не падает никогда**: пол = текущее поведение
(`title + body`). Хелпер вызывается перед сборкой `description` внутри
существующего `try` в `run_analysis_pipeline`; локальные `except` не дают
ошибке fetch уйти во внешний обработчик и уронить анализ.

### Формат для FNR

`description` (многосекционный markdown) уходит инлайн в
`/fnr-new-task {description}` — это элемент argv (`subprocess`-список, не shell),
инъекции нет. Префикс `/fnr-new-task` сохраняется, поэтому `prompt.split()[0]`
в существующих тестах не ломается. Контекст кладём в промпт, а не в файл с
указателем: tool-calling GLM ненадёжен (см. `docs/spikes/2026-07-22-claude-p-zai-tool-calling.md`),
рассчитывать на то, что claude сам прочитает файл, рискованно.

## Тестирование

**`_build_task_context` (monkeypatch `list_comments` + `list_linked_prs`):**
- тела и авторы комментариев попадают в бриф;
- комментарий с голым `/analyze` (и `/analyze текст`) выкинут;
- длинный комментарий обрезан до лимита с маркером;
- превышение потолка 16 КБ → старые комментарии отброшены, `title/body` целы;
- PR перечислены с `#number`, `[state]`, `url`;
- **fetch кидает исключение → возврат body-only, без проброса ошибки.**

**`list_linked_prs` (monkeypatch `requests.get` timeline-фикстурой):**
- отбираются только `cross-referenced` с `pull_request`;
- обычные cross-ref на issue отфильтрованы;
- дедуп по `number`; соблюдён `limit`.

**Регрессия `test_analysis_pipeline.py` (фикстура `wired`):**
- застабить `activities.github_client.list_comments` и `list_linked_prs`
  (вернуть `[]`), иначе пайплайн полезет в реальный HTTP;
- существующие проверки порядка стадий и `prompt.split()[0]` остаются зелёными.

## Числовые дефолты

| Параметр | Значение |
|---|---|
| комментариев в бриф | последние 20 |
| обрезка комментария | 1500 символов |
| связанных PR | 20 |
| потолок брифа | 16 000 символов |

Вынести константами модуля рядом с `CLAUDE_STAGE_TIMEOUT_SEC` — двигаются без
правки логики.

## Риски

- **Rate-limit GitHub** при частых `/analyze`: +2 read-запроса на прогон. Прогон
  редкий (ручная команда), деградация покрывает 403/429 — не критично.
- **Приватность токена:** новые вызовы идут через `_auth_headers()`, токен в URL
  не попадает (как и в остальном клиенте).
- **Prompt-injection (расширение поверхности):** обогащённый `description` теперь
  несёт тела чужих комментариев и заголовки PR в `/fnr-new-task {description}`,
  который исполняет `claude -p`. Shell-инъекция исключена (argv-список, не shell),
  но *LLM*-инъекция — нет: автор комментария может встроить инструкции для модели.
  Риск низкий и во многом pre-existing (`title + body` от автора issue и так шли
  в `claude -p`); фича расширяет набор инъекторов с «автор issue» до «любой, кто
  может комментировать». Инструмент запускается вручную, вывод (артефакты FNR)
  проходит ревью человеком. Митигация при росте важности: помечать блок
  обсуждения как недоверенные данные в промпте FNR-команды.
