# Входной гейт критерия приёмки

Дата: 2026-08-28
Состояние: принято к реализации

## Откуда задача

Живой прогон Issue `po-helper-org/poh-demo-checkout#163` 28 августа 2026 года.
Задача была заведена человеком с разделом `## Как принимаем`, внутри — два
блока `curl` в форме «было / должно работать»: `GET /quote` отвечает
`404 {"error":"не найдено"}`, а должен отвечать `405` с заголовком
`Allow: POST`.

Контур отработал задачу целиком: разобрал, назначил приоритет P3, построил план
на 306 строк, поднял агента разработки, получил правку в шесть строк и сорок
строк тестов, открыл PR #164, провёл круг правок, получил зелёные проверки.
PR влит, Issue закрыт по `Closes #163`.

Приёмка при этом ответила: «В Issue #163 нет раздела HowToDemo… Проверять
приёмку нечем», поставила метку `demo:no-scenario` — и это не помешало ни
разработке, ни мержу, ни закрытию.

## Что оказалось причиной

Распознаватель сценария `_HOWTODEMO_START` (`worker/activities.py:1193`)
принимает четыре формы, все английские:

```
## HowToDemo      ### How to demo      **How to demo:**      How to demo:
```

Раздел `## Как принимаем` под них не подходит. Сценарий в теле был, гейт его не
увидел.

Два других наблюдения того же прогона причинами **не** являются:

- **`.harness/` собрался наполовину** — доехал только `context.md`, ни
  `requirements.md`, ни `howtodemo.md` не появились. Это следствие: по
  `shared/task_context.py:39` `REQUIREMENTS` обязателен только при наличии ветки
  аналитики (её не было — штатный путь «работай от тела Issue»), а `HOWTODEMO`
  пишется только когда сценарий найден. Сценарий не найден — файла нет.
- **Приёмка ничего не задержала** — это описанное поведение, а не поломка.
  `docs/HOWTODEMO.md` прямо говорит: «Фазу приёмка **не двигает**», фаза
  `testing` объявлена в модели, но ни одним переходом в код не входит. Приёмка
  ставит метки и на этом всё.

Настоящий дефект один: **задача уехала в разработку, не имея прочитанного
критерия готовности**, и никто этого не заметил до самого конца.

## Что решаем

Задача без критерия приёмки — задача без определения «сделано». Разработка по
ней всегда лотерея, и её результат нечем принять. Гейт переносится **на вход**:
дорогая стадия не начинается, пока критерий не прочитан и не утверждён
человеком.

## Как это работает

```
opened
  → разбор, приоритет, метки                      (идут как раньше)
  → попытка уехать в разработку
      ├─ сценарий распознан  → разработка, howtodemo.md в .harness/
      └─ сценария нет
            → контур публикует 2–3 варианта в форме «было / стало»
            → метка ожидания, разработка не начинается
            → человек отвечает КОМАНДОЙ /harness-answer
                  ├─ номером        → вариант пишется в тело, разработка идёт
                  └─ своим текстом  → контур показывает, что понял,
                                       ждёт второго /harness-answer
```

Всё, что не начинается с команды, — обсуждение. Контур молчит и продолжает
ждать.

## Требования

### Гейт

**R1.** Разработка не начинается без критерия приёмки. Проверка стоит в той же
точке, где сегодня начинается разработка, — не раньше: разбор, приоритет и
метки дёшевы и полезны сами по себе.

**R2.** Гейт применяется ко всем задачам без исключений по дате создания и по
происхождению. Задачи, заведённые контуром (`origin:agent`), исключением не
являются.

**R3.** Гейт ленивый: срабатывает только на попытке уехать в разработку.
Массовой рассылки по уже открытым задачам нет и быть не должно — это ровно тот
шум, ради устранения которого делается вся работа.

**R4.** Пока ждём ответа, на задаче висит метка `needs-human:howtodemo` — по
существующему уклону `needs-human:*` (`needs-human:triage` уже в ходу). Снимается,
когда критерий получен.

### Распознавание существующего сценария

**R5.** Список принимаемых заголовков пополняется русскими формами:
`## Как принимаем`, `## Как проверяем`, `## Приёмка`, `## Как демонстрируем` —
наравне с четырьмя существующими английскими. Уровни `##` и `###`, как сейчас.

**R6.** Распознаватель остаётся **одним местом** для входного гейта и для
приёмщика. Два потребителя, один источник — расходиться им нечем.

**R7.** Заголовок есть, содержимое под ним пустое — считается отсутствием
сценария. Пустой критерий хуже никакого: он создаёт видимость приёмки.

**R8.** Заголовок внутри забора кода сценарием не считается (существующее
поведение `_mask_code_fences`, сохраняется).

### Вопрос человеку

**R9.** Сценарий не распознан — контур публикует **один** комментарий с 2–3
вариантами критерия, построенными из тела задачи. Форма варианта — «было /
стало», конкретными наблюдаемыми признаками, а не пересказом задачи.

**R10.** Комментарий обязан **дословно называть команду ответа** и прямо
предупреждать, что обычный комментарий не читается. Формулировка вида «добавьте
раздел» без указания команды — недопустима: сегодняшний отказ был именно таким
и стоил впустую потраченного прогона.

**R11.** Один вопрос на задачу. Повторные проверки гейта комментарии не плодят.

**R12.** Вызов модели для построения вариантов отказал — задача остаётся на
гейте, а комментарий говорит прямо: варианты предложить не смог, напишите
критерий сами командой. Отказ модели не роняет цикл и не пропускает задачу в
разработку.

### Ответ

**R13.** Ответ принимается **только** командой `/harness-answer`. Комментарий
без команды ответом не считается ни при каких условиях.

**R14.** Команда общая, не привязана к приёмке: тем же способом контур будет
задавать другие вопросы (границы MVP, выбор из вариантов плана, спорное решение
в разработке). Один способ ответа на любой заданный вопрос.

**R15.** Хвост команды забирается многострочно — как у `/bft-deep`. Сценарий в
одну строку не пишут.

**R16.** Цитата командой не считается (существующее поведение
`shared/commands.py:parse_command`, сохраняется).

**R17.** Комментарии самого контура (маркер `<!-- issue-agent -->`) ответом не
считаются.

**R18.** Ответ **номером варианта** — разработка начинается немедленно, без
подтверждения. Человек утвердил текст, который прочитал дословно; толкования не
было.

**R19.** Ответ **свободным текстом** — контур одним комментарием показывает,
какой критерий он записал, и ждёт второго `/harness-answer` с подтверждением.
Толкование появилось заново, и оно должно быть предъявлено до того, как за него
заплатят прогоном.

**R20.** `/harness-answer` на задаче, которой вопрос не задавали, — контур
отвечает одной строкой, что вопросов сейчас нет. Молчание здесь недопустимо:
человек не отличит его от проглоченной команды.

**R21.** `/harness-answer` не запускает дорогую стадию, и меток `run:*`,
`done:*`, `failed:*` у неё быть не должно. `shared/label_catalog.py` выводит эти
метки из списка команд автоматически — реализация обязана это учесть, иначе на
задачах появится бессмысленное `run:harness-answer`.

### Куда попадает результат

**R22.** Утверждённый критерий живёт **в теле задачи размеченным блоком**
`HOWTODEMO` — механизмом `shared/issue_blocks.py`, тем же, что несёт `MVP_PLAN` и
`GROW`; блок добавляется в `_ALL_BLOCKS`, поэтому порча тела и вложенные маркеры
дают громкую ошибку, а не тихую перезапись. Не
комментарием: комментарий теряется в ленте, а критерий должен быть виден в
задаче всегда.

**R23.** Приёмка читает этот блок как источник сценария — наравне с разделом,
написанным человеком вручную.

**R24.** Блок переживает повторные прогоны: второй проход гейта видит его и
вопрос не задаёт.

## Пограничные случаи

| Случай | Поведение |
|---|---|
| Заголовок есть, под ним пусто | Сценария нет (R7) |
| Заголовок процитирован в примере кода | Сценария нет (R8) |
| Комментарий человека без команды | Обсуждение, контур молчит (R13) |
| `/harness-answer` без вопроса | Одна строка «вопросов нет» (R20) |
| `/harness-answer 7` при трёх вариантах | Ответ вне списка — трактуется как свободный текст, идёт по пути R19 |
| Второй `/harness-answer` при ожидании подтверждения | Подтверждение; расхождение с показанным — новый круг R19 |
| Модель не ответила | Задача стоит, честный комментарий (R12) |
| Задача уже несёт блок критерия | Вопрос не задаётся (R24) |

## Чем проверяется

- Каждая форма заголовка, русская и английская, на обоих уровнях — распознаётся.
- Заголовок с пустым содержимым — не распознаётся.
- Заголовок в заборе кода — не распознаётся.
- Комментарий без команды при задаче на гейте — цикл не двигается.
- Цитата с командой — не команда.
- Комментарий контура с текстом команды — не ответ.
- Ответ номером — критерий в теле, разработка стартовала, второго вопроса нет.
- Ответ свободным текстом — показан разбор, разработка **не** стартовала.
- Второй ответ — разработка стартовала.
- Повторный проход гейта на задаче с блоком — комментария нет.
- Отказ модели — задача на гейте, комментарий честный, разработка не началась.
- `/harness-answer` не породила меток `run:*` / `done:*` / `failed:*`.
- Сквозной: задача без сценария → вопрос → ответ номером → разработка →
  `howtodemo.md` лежит в `.harness/`. Это ровно тот путь, который развалился на
  #163.

## Вне границ

- **Превращение приёмки в гейт мержа.** Сегодня приёмка фазу не двигает, и это
  описанное поведение. Менять его — отдельная работа с отдельным решением.
- **Обработка `issues.edited`.** Раз ответ идёт командой в комментарии, а
  комментарии цикл уже будят, обработчик правки тела не нужен.
- **Ретроспективная рассылка по открытым задачам.** Запрещена явно (R3).
- **Возврат фазы `testing`.** Не входит.
