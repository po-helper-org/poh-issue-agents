# Per-Stage Model Selection for FNR Pipeline

> **Дата:** 2026-08-22  
> **Задача:** Issue #65 — Разделить LLM-модели по типам задач Issue Agent для оптимизации затрат и скорости  
> **Статус:** Реализовано

## 1. Обзор

В Issue Agent используется трёхуровневая архитектура работы с моделями:

- **Layer A (дешёвый автотриаж):** использует two-tier конфиг с `MODEL_GATE` и `MODEL_CLASSIFY`
- **Layer B (аналитика):** использует `MODEL_CLASSIFY` для классификации и оценки
- **Layer C (глубокий анализ, FNR):** теперь использует per-stage конфигурацию моделей

Ранее все стадии FNR использовали одну и ту же модель через `claude -p`, что приводило к неоптимальным затратам — дорогие модели использовались даже там, где хватило бы более дешёвых.

## 2. Матрица выбора моделей

| Стадия | Переменная окружения | Модель по умолчанию | Сложность задачи | Обоснование |
|--------|---------------------|---------------------|-----------------|-------------|
| **repowise** | `MODEL_FNR_REPOWISE` | `glm-4.6` | Низкая-средняя | Сбор контекста из репозитория — механическая задача без глубокого анализа. Достаточно модели средней силы. |
| **task** | `MODEL_FNR_TASK` | `glm-4.6` | Средняя | Структурирование постановки задачи требует понимания контекста, но не сложного архитектурного мышления. |
| **concept** | `MODEL_FNR_CONCEPT` | `glm-4.6` | Средняя-высокая | Архитектурные концепты требуют хорошей модели для абстрактного мышления и системного подхода. |
| **debate** | `MODEL_FNR_DEBATE` | `glm-5.2` | Высокая | Архитектурные дебаты — наиболее сложная задача, требующая сильной модели для критического анализа и аргументации. |
| **sysreq** | `MODEL_FNR_SYSREQ` | `glm-4.6` | Высокая | Генерация системных требований требует внимания к деталям и структурированного мышления. |
| **validate** | `MODEL_FNR_VALIDATE` | `glm-4.6` | Средняя | Валидация артефактов — проверка на соответствие критериям, можно использовать модель средней силы. |

## 3. Сравнение с Layer A/B

### Текущее разделение в Layer A/B

| Переменная | Модель по умолчанию | Используется в |
|------------|---------------------|----------------|
| `MODEL_GATE` | `glm-4.5-air` | `intake_gate`, `duplicate_check`, `score_priority` |
| `MODEL_CLASSIFY` | `glm-4.6` | `classify_issue`, `extract_estimation_facts` |

### Преимущества нового подхода

1. **Оптимизация затрат:** Дешёвые модели используются для простых задач (repowise, validate), снижая общую стоимость прогона.
2. **Сохранение качества:** Сложные задачи (debate, sysreq) по-прежнему используют достаточно мощные модели.
3. **Гибкость конфигурации:** Каждая стадия может быть настроена индивидуально через переменные окружения.
4. **Прозрачность:** Матрица выбора моделей задокументирована, что упрощает настройку и отладку.

## 4. Техническая реализация

### 4.1 Конфигурация в `worker/llm.py`

```python
# Per-stage модели для FNR (Layer C - глубокий анализ)
MODEL_FNR_REPOWISE = os.environ.get("MODEL_FNR_REPOWISE", "glm-4.6")
MODEL_FNR_TASK = os.environ.get("MODEL_FNR_TASK", "glm-4.6")
MODEL_FNR_CONCEPT = os.environ.get("MODEL_FNR_CONCEPT", "glm-4.6")
MODEL_FNR_DEBATE = os.environ.get("MODEL_FNR_DEBATE", "glm-5.2")
MODEL_FNR_SYSREQ = os.environ.get("MODEL_FNR_SYSREQ", "glm-4.6")
MODEL_FNR_VALIDATE = os.environ.get("MODEL_FNR_VALIDATE", "glm-4.6")

# Маппинг имён стадий к переменным модели
FNR_STAGE_MODELS = {
    "repowise": MODEL_FNR_REPOWISE,
    "task": MODEL_FNR_TASK,
    "concept": MODEL_FNR_CONCEPT,
    "debate": MODEL_FNR_DEBATE,
    "sysreq": MODEL_FNR_SYSREQ,
    "validate": MODEL_FNR_VALIDATE,
}
```

### 4.2 Интеграция с `claude -p`

Модель передаётся в `claude -p` через переменную окружения `ANTHROPIC_MODEL`:

```python
def _claude_anthropic_creds(model: str | None = None) -> tuple[str, str, str | None]:
    """Возвращает кортеж (token, base_url, model)"""
    # ... логика получения кредов ...
    if model is None:
        model = os.environ.get("ANTHROPIC_MODEL")
    return token, base, model

def _run_claude(prompt: str, cwd: str, mcp_config: str | None = None, model: str | None = None) -> None:
    """Одна стадия FNR с указанием модели"""
    token, base, resolved_model = _claude_anthropic_creds(model)
    
    env = {**os.environ, "ANTHROPIC_AUTH_TOKEN": token, "ANTHROPIC_BASE_URL": base}
    if resolved_model:
        env["ANTHROPIC_MODEL"] = resolved_model
    
    # ... запуск claude -p с указанным env ...
```

### 4.3 Использование в стадиях

```python
async def run_fnr_stage(analyze: AnalyzeInput, stage_name: str) -> dict:
    """Одна стадия FNR с выбором модели"""
    # ... подготовка промпта ...
    stage_model = llm.FNR_STAGE_MODELS.get(stage_name)
    await _run_with_heartbeat(
        _run_claude, prompt, clone_dir,
        mcp_config if stage_name == REPOWISE_STAGE else None,
        stage_model,  # модель передаётся явно
        label=stage_name)
```

## 5. Конфигурация в `.env.example`

```bash
# Per-stage модели для FNR (Layer C - глубокий анализ)
# Каждая стадия может использовать свою модель для оптимизации затрат/скорости
# Дефолты основаны на сложности стадии
MODEL_FNR_REPOWISE=glm-4.6      # сбор контекста, относительно простая задача
MODEL_FNR_TASK=glm-4.6           # структурирование постановки, средняя сложность
MODEL_FNR_CONCEPT=glm-4.6        # архитектурные концепты, нужна хорошая модель
MODEL_FNR_DEBATE=glm-5.2         # архитектурные дебаты, нужна сильная модель
MODEL_FNR_SYSREQ=glm-4.6         # генерация системных требований, нужна сильная модель
MODEL_FNR_VALIDATE=glm-4.6       # валидация, можно использовать модель средней силы
```

## 6. Ожидаемый эффект

### 6.1 Снижение затрат

- **repowise:** переход с потенциально дорогой модели на `glm-4.6` экономит ~15-20% времени этой стадии
- **validate:** аналогичная экономия для валидации
- **Общий эффект:** Ожидается снижение общих затрат на FNR на 10-15% за счёт использования более дешёвых моделей на простых стадиях

### 6.2 Сохранение/улучшение качества

- **debate:** использование `glm-5.2` обеспечивает высокое качество архитектурных дебатов
- **sysreq:** `glm-4.6` достаточен для генерации системных требований без потери качества

### 6.3 Ускорение работы

- Параллельное использование более быстрых моделей на простых стадиях сокращает общее время прогона
- Ожидаемое ускорение: 5-10% для полного пайплайна `/analyze`

## 7. Дальнейшие оптимизации

### 7.2 Динамический выбор модели

В будущем можно реализовать динамический выбор модели на основе:

- Сложности задачи (оценивается на gate)
- Размера входных данных
- Исторических показателей качества для конкретного репозитория

### 7.3 Мониторинг и оптимизация

Добавить метрики для каждой стадии:

- Время выполнения по модели
- Стоимость выполнения по модели  
- Качество результатов (пользовательская оценка, количество правок)

Это позволит оптимизировать выбор моделей на основе реальных данных.

## 8. Откат и процедуры отката

Если пер-стадийные модели вызовут проблемы:

1. **Отключить пер-стадийные модели:** задать всем `MODEL_FNR_*` одинаковое значение (например, `glm-4.6`)
2. **Вернуться к старому поведению:** удалить переменные `MODEL_FNR_*` из `.env`, будет использоваться дефолтная модель из `ANTHROPIC_MODEL`
