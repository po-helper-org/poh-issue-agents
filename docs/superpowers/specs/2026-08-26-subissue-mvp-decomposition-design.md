# Декомпозиция MVP через под-задачи: спека

**Дата:** 2026-08-26
**Состояние:** согласовано, план исполнения не написан
**Цель:** одна законченная итерация — один Issue. Под-задача становится инструментом деления, а не единицей учёта.

## 1. Задача

Контур плодит задачи быстрее, чем их можно осмыслить.

Замер 2026-08-26:

| Репозиторий | Открытых Issue | Из них с `root-issue: #N` |
|---|---|---|
| `poh-issue-agents` | 157 | 128 |
| `poh-demo-checkout` | 87 | 71 |
| `poh-delivery-agent` | 23 | 22 |
| **Итого** | **267** | **221** |

То есть **83% открытых задач завёл сам контур**. Прирост около 30 в сутки.

### Образцовый случай

Issue `poh-demo-checkout#151` — «Эндпоинт GET /version с версией сервиса из package.json». Одна ручка. Контур завёл под неё **девять** открытых Issue:

| № | Метки | Заголовок |
|---|---|---|
| 152 | `release:mvp` P1 | Добавить импорт версии из package |
| 153 | `release:mvp` P1 | Реализовать обработчик маршрута GET /version |
| 154 | `release:mvp` P1 | Написать функциональные тесты для /version |
| 158 | `release:mvp` P0 | Загрузить версию из package при старте |
| 160 | `release:mvp` P0 | Реализовать ответ 405 для не-GET методов |
| 159 | `release:mvp` **`duplicate`** | Реализовать ответ 200 для GET /version |
| 155 | `release:grow` | Протестировать поведение при повреждении package |
| 161 | `release:grow` | Добавить тесты для эндпоинта /version |
| 162 | `release:support` | Вывести версию в лог при старте сервиса |

Каждая — с приоритетом, фазой, **своим вечным `IssueLifecycle`**. Одна из девяти — дубликат другой. Сам родитель при этом в фазе `failed`.

### Два источника

1. **Декомпозиция** (`publish_decomposition`, `worker/activities.py`) — Issue на каждый пункт плана.
2. **Находки** (`collect_dev_followups`) — Issue на каждую запись из `.followups.md`.

### Цена

- **Токены.** Подзадача проходит триаж (вызов модели на приоритет). Находка, не будучи подзадачей плана, при автостарте гоняет **полную цепочку FNR — шесть стадий `claude -p`**.
- **Внимание.** Девять веток ревью вместо одной. Дубликаты внутри одного плана доживают до человека.
- **Состояние.** 124 живых воркфлоу на стенде, где свободно 199 МБ памяти.

## 2. Образ результата

Каждый Issue — **законченная итерация разработки** с понятным эффектом: фича, оптимизация, техническое изменение или устранение дефекта.

Под-задача — **инструмент деления**, чтобы планировать итерации запуска агентов. Она живёт часы, закрывается вместе со своим шагом и в общий список не попадает.

MVP сфокусирован на ядре, подтверждающем концепт. Всё, что не нужно для прохождения сценария приёмки, ждёт своей очереди за гейтом.

## 3. Требования

| № | Требование |
|---|---|
| **R1** | Одна законченная итерация — **один** Issue в общем списке. Под-задачи в него не попадают |
| **R2** | План MVP существует в двух согласованных видах: чеклист в теле родителя (рабочая поверхность) и `.harness/plan-issue-N.md` в ветке задачи (след в git). Оба пишутся из одного источника |
| **R3** | План разворачивается в под-задачи, **только если между задачами плана есть настоящая зависимость**. Граф без рёбер — одна итерация, под-задач ноль |
| **R4** | Под-задача — **нативная** (`sub_issues` GitHub), заводится в момент старта шага, закрывается по его завершении |
| **R5** | Под-задача **не проходит триаж** и **не поднимает свой `IssueLifecycle`** |
| **R6** | Находка агента: нужна для прохождения HowToDemo — исполняется в этой же сессии; не нужна — уходит в секцию GROW тела родителя. Issue не заводится ни в одном случае |
| **R7** | Правило фокуса живёт правилом организации в `harness-memory-base/rules/develop`, а не в промпте контура |
| **R8** | GROW открывается **только вердиктом HowToDemo**. Контур публикует кандидатов, Issue заводятся по отметке человека |
| **R9** | Любая правка решения воркфлоу — маркер `workflow.patched` + фикстура истории + прогон корпуса живых прогонов до выкладки |
| **R10** | Измеряется до и после: Issue на фичу, вызовы модели на фичу, живых `IssueLifecycle`, доля находок, ставших Issue |
| **R11** | Документы готовятся практиками superpowers до передачи исполнителю. Исполнитель получает спеку и план, а не задание «разберись» |
| **R12** | Порядок старшинства источников инструкций: **свои правила старше импортированных практик**. superpowers задаёт как делать, `harness-memory-base` — что считать сделанным и чего не делать |
| **R13** | Обязательные части процесса исполняются **шагами конвейера**, а не доверяются скиллу. Скилл даёт качество формулировок, шаг даёт гарантию исполнения |
| **R14** | Исполнитель выбирается конфигом (`DEVELOP_RUNNER=openhands\|claude`). Обе ветки живут одновременно, выбор между ними — по сигналам слоя, а не мнением |
| **R15** | Тяжёлые прогоны планируются вне пикового окна z.ai (09:00–13:00 MSK) |
| **R16** | Модель разработки поднимается с `glm-4.6` до текущей линейки 5.x |
| **R17** | Многоагентное исполнение (глубина 3) включается конфигом, когда снимется ограничение по ключу |

## 4. Конвейер документов

| Стадия | Чем делается | Артефакт |
|---|---|---|
| Требования | цепочка FNR (есть): `claude -p` со скиллами `problem-analyst`, `solution-designer`, `system-analyst-sysreq` | `sa_documentation/FNR/FNR_1/system_requirements.md` в ветке `research/issue-N` |
| План работ | **новая команда** `.claude/commands/plan-mvp.md` → скилл `writing-plans` | `.harness/plan-issue-N.md` в ветке задачи |
| Исполнение | по `DEVELOP_RUNNER`: OpenHands по готовому плану либо Claude Code со скиллами | код, PR |
| Проверка до PR | `claude -p` со скиллом `verification-before-completion` | вывод команд |

`brainstorming` в конвейер не входит: он интерактивен и требует человека. Его роль играет цепочка FNR (`task → concept → debate → sysreq`).

### Почему `writing-plans` подходит

Скилл декларирует, что план пишется **в расчёте на исполнителя с нулевым контекстом**: точные пути файлов, полный код каждого шага, команда запуска и ожидаемый вывод. Заглушки вроде «добавить обработку ошибок» объявлены дефектом плана. Это ровно то, что нужно OpenHands — он исполняет, а не додумывает.

### Оговорка неинтерактивного прогона

`writing-plans` заканчивается вопросом человеку («план готов, как исполняем»). В неинтерактивном прогоне спрашивать некого. Команда `plan-mvp` обязана явно сказать: выход — файл, исполнение не запускать, к человеку не обращаться. Иначе стадия ждёт того, чего не будет.

## 5. Правило деления

### Определение шага

Задачи плана superpowers несут блок **Interfaces — Consumes / Produces**. Это и есть объявленная зависимость.

**Ребро графа = непустой `Consumes`.**

- рёбер нет → под-задачи не заводятся, весь план идёт **одним прогоном**;
- рёбра есть → под-задача на задачу плана, порядок по готовности.

Отдельный вызов модели на декомпозицию становится не нужен: промпт `system_decompose_issue.md` уходит.

### Честность рёбер

Зависимость обязана **называть, что даёт следующему шагу**: «зависит от 1: читает `version` из состояния». Формулировка без предмета отвергается на `validate` — тем же механизмом, которым сегодня отвергаются циклы.

### Потолок

Остаётся 6 (`decomposition.MVP_SOFT_CAP`), но **это число из головы, и так и записано**. Обосновать его нечем: эпизод слоя хранит `pr_merged`, `line_survival`, `fix_rounds`, `human_rewrite`, `tests_passed` — про итерацию, но не про её размер.

Поэтому: **добавить в запись эпизода признак размера** (число задач плана, было ли деление), накопить, потом ставить порог по данным.

### Eval на правило

Риск: модель выдумывает зависимость, чтобы план «выглядел планом». Проверка на графе этого не увидит — рёбра формально есть.

Основание для истины берётся из истории GitHub, а не из суждения:

- «делили — и зря»: все под-задачи родителя закрыты одним PR либо закрыты без единого коммита;
- «не делили — и зря»: одна задача породила три и более круга правок либо переоткрывалась.

Набор из 20–50 таких случаев гоняется в CI при изменении промптов планирования. Порог берётся оттуда же.

## 6. Устройство

### `MvpDelivery` — отдельный воркфлоу

**Почему не фаза `IssueLifecycle`:** свой `workflow list` и своя история для разбора; шаги переживают рестарт воркера; ошибка в логике шагов правится без риска для живых прогонов цикла Issue. Тот же приём, что у `IssueDevelopment`, `IssuePrFix`, `DeliveryRelease`.

**Что делает:**

1. Читает план из `.harness/plan-issue-N.md`.
2. Считает граф по `Consumes`. Рёбер нет — один дочерний прогон на весь план.
3. Рёбра есть — по шагам в порядке готовности: завести нативную под-задачу → дочерний прогон исполнения → закрыть под-задачу → отметить пункт чеклиста.
4. Собирает находки шагов в секцию GROW тела родителя.
5. Чеклист закрыт — отдаёт исход «MVP собран».

**Чего не делает:** не ревьюит, не мержит, не выкатывает, не заводит GROW-Issue.

### Точка сопряжения

Одна, как у Delivery-Agent: `IssueLifecycle` передаёт `IssueInput`, получает исход. Обратной зависимости нет.

В `IssueLifecycle` меняется **одно место**: фаза `ready-for-dev` запускает `MvpDelivery` вместо `IssueDevelopment`. Это правка решения — обязателен маркер и фикстура (R9).

### Граница с приёмкой

`MvpDelivery` завершается — родительский цикл переходит в `testing` и запускает HowToDemo-Agent. Это оживляет мёртвые фазы `testing`/`released` (H-04 в `research.md`) — здесь по необходимости, а не отдельной задачей.

## 7. Форматы

### Тело родительского Issue

Контур правит **только** размеченные блоки. Правка — заменой блока целиком.

```markdown
<!-- harness:mvp-plan:start -->
## План MVP

- [x] 1. Загрузить версию из package.json при старте
- [ ] 2. Обработчик маршрута GET /version — зависит от 1: читает `version` из состояния
- [ ] 3. Функциональные тесты на /version — зависит от 2: вызывает маршрут

Деление: 3 задачи, 2 зависимости. План файлом — `.harness/plan-issue-151.md`.
<!-- harness:mvp-plan:end -->

<!-- harness:grow:start -->
## GROW — после прохождения HowToDemo

- [ ] Поведение при повреждённом package.json — `src/version.mjs:14` _(шаг 1)_
- [ ] 405 для не-GET методов — сценарий приёмки не требует _(шаг 2)_
<!-- harness:grow:end -->
```

Разметка комментариями несёт смысл: тело правят и человек, и контур; без границ они затрут друг друга.

### Файл плана

`.harness/plan-issue-N.md` — формат `writing-plans`: заголовок с целью и архитектурой, Global Constraints, File Structure, задачи с шагами, кодом, командами и ожидаемым выводом. Плюс контурная шапка:

```markdown
Источник требований: sa_documentation/FNR/FNR_1/system_requirements.md @ research/issue-151
Сценарий приёмки: блок HowToDemo тела Issue, редакция 2026-08-26T09:14Z (sha256:a3f1…)
```

### Тело под-задачи

```markdown
Шаг 2 плана MVP родителя #151.

Зависит от шага 1 — читает `version` из состояния.
План целиком: `.harness/plan-issue-151.md`

Заводится контуром на старте шага, закрывается по завершении.
Своего триажа и своего цикла у неё нет.
```

### Правило организации

`harness-memory-base/rules/develop/D-011.md`:

```markdown
---
id: D-011
agent: develop
title: Находка вне сценария приёмки не берётся в работу
tags: [фокус, качество]
source: переделка SubIssue, 2026-08-26
---

Нашёл по дороге то, без чего сценарий приёмки всё равно пройдёт, — запиши и
иди дальше. Нужно для прохождения сценария — сделай здесь же, отдельной задачи
не заводи.

Граница не на вкус: критерий один — пройдёт ли сценарий без этого.

Причина в стоимости внимания. Ветка, где сделано лишнее, ревьюится дольше и
откатывается целиком. Работа, которой не хватило для сценария, возвращается
кругом правок и стоит второго прогона.
```

### Кто что правит

| Носитель | Пишет | Читает |
|---|---|---|
| Чеклист в теле | `MvpDelivery` | человек, `MvpDelivery` |
| Секция GROW | `MvpDelivery` из находок шагов | человек на гейте |
| `plan-issue-N.md` | `claude -p` со скиллом `writing-plans` | исполнитель, ревью, люди позже |
| Под-задача | `MvpDelivery` | человек в интерфейсе GitHub |
| `.followups.md` | агент разработки | `MvpDelivery`, дальше снимается |

## 8. Исполнитель

### Граница, которую нельзя двигать

Воркер работает от root и держит токен GitHub и ключ модели. Агент разработки живёт в отдельном одноразовом контейнере от uid 10001, потому что **исполняет код чужого репозитория**.

Стадии документов эту границу не переходят: читают репозиторий, пишут markdown. Поэтому `claude -p` для FNR в воркере законен.

Но superpowers для разработки — это TDD, а TDD означает прогон тестов. Значит полноценный цикл обязан жить в одноразовом контейнере.

### Три глубины

| Глубина | Что | Состояние |
|---|---|---|
| **1. Документы** | `writing-plans` и `verification-before-completion` в воркере, OpenHands исполняет план | берём сразу |
| **2. Исполнитель на Claude Code** | новый образ раннера: Claude Code + скиллы, uid 10001, одноразовый; внутри `executing-plans` | целевая для этой спеки |
| **3. Полный `subagent-driven-development`** | контроллер диспатчит субагента на задачу и ревьюера после неё | по R17, конфигом |

### Что проверено

| Вопрос | Ответ | Как проверено |
|---|---|---|
| Работает ли `--permission-mode acceptEdits` от непривилегированного пользователя | **да**, код возврата 0, файл создан | прогон от uid 501 |
| Доступен ли `Task` в неинтерактивном режиме | **да**, субагент отработал | `claude -p … --allowedTools Task` |

Обе проверки — против Anthropic. Способность CLI от модели не зависит; способность **модели** вести цикл — отдельный вопрос, он закрывается A/B по R14.

### Что известно про GLM

| Показатель | Значение |
|---|---|
| GLM-5, SWE-bench | 77.8% |
| GLM-5.1, SWE-Bench Pro | 58.4 — выше GPT-5.4 (57.7) и Claude Opus 4.6 (57.3) |
| GLM-5.2, Terminal-Bench 2.1 | 81.0 |
| GLM-5.2, SWE-bench Pro | 62.1 |
| GLM-5, Vending-Bench 2 | первое место среди open-source, вплотную к Opus 4.5 |

Ограничение, названное авторами прямо: **существенная деградация при контексте свыше 100k токенов** при обученном окне 202 752.

Это довод **за** субагентов, а не против: изолированный контекст удерживает работу в рабочей половине окна. Для модели с таким порогом многоагентная схема полезнее, чем для Claude.

### Ограничение ресурса

z.ai рекомендует по тарифам числом проектов: Lite — один за раз, Pro — один-два, Max — два и более. Недельные квоты 10k / 60k / 140k кредитов. Потолка два одновременно: пятичасовое скользящее окно (число не публикуется) и недельная квота. Пик — 14:00–18:00 UTC+8 (09:00–13:00 MSK); вне пика точки дешевле вдвое и конкурентность выше.

Контур делит один ключ между аналитикой, разработкой, ревью, релизом и приёмкой. Отсюда R15 и R17.

Источники: [GLM-5: from Vibe Coding to Agentic Engineering](https://arxiv.org/html/2602.15763v1), [GLM Coding Plan rate limits](https://moclaw.ai/blog/glm-coding-plan-rate-limits), [GLM-5.1](https://www.analyticsvidhya.com/blog/2026/04/glm-5-1/), [GLM 5.2](https://machine-learning-made-simple.medium.com/understanding-glm-5-2-beyond-the-headlines-3a4e654c9542).

## 9. Приёмка

Сценарий проверяется на демо-репозитории задачей, повторяющей #151.

### Шаг 1. Завести Issue

| Как было | Как стало |
|---|---|
| Через минуты в трекере девять новых Issue | Один новый Issue — сам родитель |
| План — перечень ссылок в комментарии | План — чеклист в теле, ни строки в трекере |

Проверка: прирост по выборке `is:open -is:sub-issue` равен **1**.

### Шаг 2. Первый шаг разработки

| Как было | Как стало |
|---|---|
| Подзадача — обычный Issue со своим триажом и вечным циклом | Нативная под-задача, заводится на старте шага |
| Триаж каждой подзадачи — вызов модели | Триажа у под-задачи нет |
| Девять `IssueLifecycle` в `workflow list` | Один цикл родителя плюс один `MvpDelivery` |

Проверка: `sub_issues` непусты, в общем списке их нет.

### Шаг 3. Конец MVP

| Как было | Как стало |
|---|---|
| Подзадачи остаются открытыми | Под-задача закрывается вместе со своим шагом |
| Дубликаты внутри плана (#159 против #153) доживают до человека | Дубликат невозможен: шаги берутся из плана по одному |

Проверка: `sub_issues_summary.percent_completed == 100`.

### Шаг 4. Фокус агента

| Как было | Как стало |
|---|---|
| Находка любого рода становилась Issue | Нужна для сценария — сделана в этой же сессии; не нужна — строка в секции GROW |
| Агент отвлекался на то, что не проверяется приёмкой | Критерий один и проверяемый: пройдёт ли сценарий без этого |

Проверка: прирост Issue от находок **ноль**; в секции GROW строки со ссылкой на шаг.

### Шаг 5. Случай «делить не надо»

| Как было | Как стало |
|---|---|
| План на 9 пунктов на любой размер задачи | Граф без рёбер — под-задач ноль, один прогон |

Проверка: задача, чей план не содержит `Consumes`, проходит без единой под-задачи.

## 13. Разбиение на планы исполнения

Спека покрывает **две независимые работы**. Каждая даёт работающий результат сама по себе, и смешивать их в один план нельзя: провал одной не должен тянуть вторую.

### План 1 — декомпозиция и гейт

Требования: **R1–R10, R12, R13**.

Меняет: `shared/decomposition.py`, `worker/github_client.py`, новый `MvpDelivery`, одну точку в `worker/workflows.py`, `shared/lifecycle.py`, `collect_dev_followups`, `AGENTS.md`, правило `D-011`, новую команду `plan-mvp`.

Результат: одна фича — один Issue, под-задачи нативные и временные, GROW за гейтом приёмки. Исполнителем остаётся OpenHands (глубина 1).

Идёт первым: он один закрывает заявленную цель — перестать плодить задачи.

### План 2 — исполнитель на Claude Code

Требования: **R11 (глубина 2), R14, R15, R16, R17**.

Меняет: образ раннера, выбор исполнителя конфигом, расписание тяжёлых прогонов, версию модели.

Результат: практики superpowers работают там, где пишется код; выбор между исполнителями делается по сигналам слоя.

Идёт вторым и **зависит от того, чтобы слой саморефлексии работал** — иначе A/B нечем измерить (открытый вопрос 3).

### Что общего

Оба плана обязаны соблюдать R9: правка решения воркфлоу — маркер, фикстура, прогон корпуса живых историй до выкладки.
