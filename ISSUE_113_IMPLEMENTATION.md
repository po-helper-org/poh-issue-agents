# Реализация ISSUE-113: сохранение контекста при передаче в разработку

## Проблема

Контекст, который контур Issue-Agent породил вокруг Issue, частично теряется при передаче агенту разработки:

1. **План декомпозиции и подзадачи не доезжают** — создаются но не видны агенту
2. **Обсуждение Issue не доезжает** — агент не видит комментарии
3. **Два артефакта FNR отбрасываются** — `repowise-dialog.md` и `validation.md` теряются
4. **Ветка родителя теряется у подзадачи** — баг: подзадача теряет контекст родителя
5. **Тело Issue — устаревший снимок** — создается при вебхуке и не обновляется
6. **Размер постановки не ограничен** — нет потолка, можно получить мегабайт текста
7. **Superpowers не работают** — но это вне scope правки

## Решение

### 1. Новые константы (worker/activities.py:775-778)

```python
# Потолок размера постановки для агента разработки (ISSUE-113)
DEV_TASK_MAX_CHARS = 50000      # общий размер .task.md
DEV_ARTIFACT_MAX_CHARS = 10000  # отдельный артефакт FNR
DEV_COMMENT_CHARS = 1000        # обрезка одного комментария для разработки
```

### 2. Новые функции контекста

#### `_truncate(text: str, limit: int) -> str`
Обрезает текст по лимиту с маркером "…[обрезано]"

#### `_fetch_decomposition_plan(issue: IssueInput) -> str`
Ищет комментарий с маркером "🧩 Декомпозиция" и возвращает его текст

#### `_fetch_subtasks(issue: IssueInput) -> list[dict]`
Получает подзадачи плана из открытых Issue с метками `release:*` и ссылкой на родителя

#### `_fetch_dev_comments(issue: IssueInput) -> list[str]`
Получает свежие комментарии Issue (до 10) без командного шума

#### `_refresh_issue_body(issue: IssueInput) -> str`
Перечитывает тело Issue из GitHub вместо устаревшего снимка

#### `_apply_size_limit(parts: list[str], limit: int, priority_order: list[int] | None = None) -> list[str]`
Обрезает части постановки по лимиту с учётом приоритетов (сначала непроритетные)

### 3. Обновление `_dev_prepare` (worker/activities.py:1575-1698)

**Добавлено:**
1. Свежее тело Issue вместо устаревшего снимка (`_refresh_issue_body`)
2. План декомпозиции и подзадачи с телами
3. Все пять артефактов FNR (включая отброшенные):
   - `system_requirements.md`, `task.md`, `concept.md` (были)
   - `repowise-dialog.md`, `validation.md` (новые)
4. Обсуждение Issue (комментарии)
5. Применение потолка размера с усечением по приоритету

**Приоритет усечения:**
1. Заголовок и тело Issue (максимальный приоритет)
2. План декомпозиции 
3. Артефакты FNR
4. Обсуждение
5. Правила репозитория (минимальный приоритет)

### 4. Обновление `trigger_openhands_resolver` (worker/activities.py:1914-1944)

**Добавлены параметры:**
- `root_issue: int | None = None` — номер родительской задачи (для подзадач)
- `branch: str | None = None` — готовая ветка (вычисленная в workflow)

**Логика:**
- Если передана готовая ветка, используется она
- Иначе вычисляется от `root_issue` (если есть) или от собственного номера

### 5. Обновление `_start_development` (worker/workflows.py:1606-1641)

**Добавлено:**
- Вычисление ветки так же, как в `_phase_handoff` (с учётом `self._root_issue`)
- Передача `self._root_issue` и вычисленной ветки в `trigger_openhands_resolver`

Это решает проблему #4: подзадача плана получает ветку родителя вместо несуществующей своей ветки.

## Нерешённые вопросы

1. **Superpowers у агента разработки** — это смена агента на `claude`, а не настройка
2. **Применимость скиллов у аналитики** — требует проверки вывода `claude -p` (вне scope)
3. **Индексация для поиска подзадач** — текущий `list_open_issues` медленен на больших бэклогах

- Деградация работает (если что-то не получается — используем старое поведение)
- Новые параметры имеют значения по умолчанию

- Размер `.task.md` ограничен (был безлимитным)

- Увеличение токенов на каждый прогон разработки (но теперь там весь контекст)
- Зависимость от GitHub API при обновлении тела Issue (с деградацией к старому снимку)
- Медленная загрузка подзадач через `list_open_issues` (но только при наличии декомпозиции)
