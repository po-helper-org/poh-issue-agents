# Концепты решений — FNR-5

> **Задача:** Контекст репозитория пересобирается в каждом прогоне; постоянного источника знаний о коде у агентов нет
> **Дата:** 2026-08-19
> **Статус:** Концепты сгенерированы (ожидает `/fnr-debate`)

---

## Резюме проблемы

Контекст о коде существует в контуре только как производная прогона: `_build_workspace` (`worker/activities.py:697-703`) сносит каталог, клонирует репозиторий и гонит `repomix` заново при каждом запуске, а `_dev_prepare` (`worker/activities.py:1056`) повторяет тот же приём для разработки. Единственная форма контекста — плоский XML-дамп, которому нельзя задать вопрос, и который стадия получает целиком либо не стартует вовсе (`worker/activities.py:706-712`). Знание не накапливается между прогонами и не переживает их.

**Допущения, принятые при генерации** (не подтверждены на момент написания):

- Пакет `repowise` версии 0.36.0 работает без учётной записи в облаке Repowise. Команды `login` / `logout` / `whoami` в CLI присутствуют — если авторизация окажется обязательной для `mcp` или `serve`, концепты A, B и D теряют основание в равной степени.
- Ключ z.ai, приведённый к протоколу Anthropic (`_claude_anthropic_creds`, `worker/activities.py:762`), пригоден как провайдер модели для repowise. Эмбеддер под вопросом отдельно.

## Концепт A: Repowise отдельным сервисом с MCP-прокси и журналом сессий [Категория: Правильное]

**Суть:** Repowise поднимается самостоятельным сервисом со своим хранилищем индекса, своим расписанием обновления и своей веб-админкой. Агенты обращаются к нему по MCP через тонкий прокси, который журналирует каждый вызов и ответ и рендерит из журнала артефакт диалога. Контекст становится объектом с собственным жизненным циклом, а не производной прогона.

**Что менять:**

| Компонент | Изменение | Файл |
|-----------|----------|------|
| Новый compose сервиса | Контейнеры MCP на два workspace, `serve`, индексатор, прокси, вход с basic_auth | `../poh-infra/repowise/docker-compose.yml` (другой репозиторий) |
| Индексатор | Периодический `git fetch` + `workspace scan -y` + `repowise update -w`; режим первичной индексации | `../poh-infra/repowise/` (другой репозиторий) |
| Прокси | Маршрут по workspace, обязательный `session`, bearer-токен, журнал вызовов, рендер артефакта | `../poh-infra/repowise/` (другой репозиторий) |
| `_fnr_stages` | Новая стадия `repowise` первой в цепочке, до `task` | `worker/activities.py:648-660` |
| `_FNR_STAGE_REQUIRES` | Вход стадии `task` — артефакт диалога | `worker/activities.py:668` |
| `FNR_STAGE_NAMES` | Пополнение перечня | `worker/activities.py:664` |
| `ARTIFACT_FILES` | Пополнение набора собираемых артефактов | `worker/activities.py:635` |
| `run_fnr_stage` | Генерация конфигурации MCP в каталог прогона перед запуском `claude -p` | `worker/activities.py:977-994` |
| `_dev_prepare` | Тот же конфиг в каталог задачи разработки | `worker/activities.py:1056` |
| `develop.py` | Подключение одноразового контейнера к сети, где виден прокси | `shared/develop.py` |
| Новый промпт стадии | Правила ведения автономного диалога | `prompts/` |

**Плюсы:**
- Единственный концепт, закрывающий все пять шагов сценария демонстрации, включая веб-админку на отдельном домене и автономный диалог с публикацией артефакта.
- Индекс живёт дольше прогона и переиспользуется между Issue и между агентами — исходная проблема снимается по существу, а не по симптому стоимости.
- Транскрипт диалога получается механически из журнала прокси, а не записью силами модели. Класс отказов «шаг отработал, успех доложен, артефакта нет» на этот артефакт не распространяется.
- Кросс-репозиторные инструменты MCP в режиме workspace дают то, чего у плоского дампа нет в принципе: связи между репозиториями организации.
- Изоляция агента разработки не ослабляется: контейнер получает сетевой доступ к прокси, но по-прежнему не видит ни GitHub-токена, ни ключа модели (`shared/develop.py`, докстрока модуля).

**Минусы:**
- Самый дорогой концепт из предложенных: новый compose, новый прокси (собственный код), новый домен, новая учётная запись входа, отдельный раздел документации.
- Прокси — новая точка отказа ровно на пути, без которого стадия `task` больше не стартует. Отказ прокси останавливает всю аналитику, а не деградирует её.
- Постоянно работающий индекс — новая долгоживущая нагрузка на память и диск. На стенде свободно порядка 1.4 ГБ при выключенном swap.
- Требует поддержки: устаревший индекс опаснее отсутствующего, потому что агент отвечает уверенно и про код, которого нет.
- Веб-админка держит клоны всех репозиториев организации и ключ модели за одним паролем.

**Оценка усилий:** 2+ недели (архитектурное изменение, два репозитория, собственный сетевой компонент).

**Риски:**

| Риск | Вероятность | Митигация |
|------|------------|-----------|
| `repowise` требует облачной учётной записи для `mcp`/`serve` | Средняя | Проверить до начала работ; при подтверждении концепт отпадает целиком |
| Отказ прокси останавливает аналитику | Средняя | Стадия деградирует до пропуска с явной пометкой в артефакте вместо жёсткого падения |
| Первичная индексация не укладывается в память сервера | Высокая | Отладка и первичная индексация вне контура; выкладка отдельной задачей |
| Одновременная запись индексатора и чтение MCP блокируют друг друга | Средняя | Проверить режим журналирования SQLite; развести окна индексации и прогонов |
| Ключ z.ai не подходит как провайдер или эмбеддер | Средняя | Структурный индекс без модели работоспособен сам по себе; семантический поиск деградирует до поиска по ключевым словам |
| Рабочие копии с боевыми ключами попадают в индекс | Средняя | Явный запрет на уровне индексатора, проверка поиском по готовому индексу |

**Откат:** Стадия `repowise` убирается из `_fnr_stages`, вход стадии `task` возвращается к прежнему значению, сервис гасится. Артефакты прошлых прогонов остаются в ветках и вреда не наносят. Состояние конвейера возвращается к текущему одной правкой в одном файле.

## Концепт B: Repowise как stdio-MCP внутри существующих контейнеров на общем томе индекса [Категория: Прагматичное]

**Суть:** Отдельного сервиса нет. Пакет `repowise` ставится в образ воркера и в образ агента разработки, индекс лежит на общем именованном томе, а MCP поднимается по требованию как дочерний процесс через конфигурацию проекта — тем же способом, каким сейчас подключены `sentry`, `context7` и `temporal` (`.mcp.json`). Обновление индекса — периодическая задача внутри воркера рядом с существующим `consolidation_workflow`.

**Что менять:**

| Компонент | Изменение | Файл |
|-----------|----------|------|
| Образ воркера | Установка пакета `repowise` | `worker/Dockerfile` |
| Образ агента разработки | То же | `openhands/Dockerfile` |
| `.mcp.json` | Регистрация сервера `repowise` со ссылкой на каталог индекса | `.mcp.json` |
| Compose контура | Новый том индекса, монтируемый в воркер и раннер | `../poh-infra/harness/docker-compose.yml` (другой репозиторий) |
| Новая активность обновления | Периодический `repowise update` по расписанию Temporal | `worker/activities.py`, `worker/workflows.py` |
| `_fnr_stages` | Новая стадия `repowise` первой в цепочке | `worker/activities.py:648-660` |
| Новый промпт стадии | Правила ведения диалога и обязательная запись транскрипта | `prompts/` |

**Плюсы:**
- Не появляется ни нового домена, ни нового сетевого компонента, ни новой точки отказа на сетевом пути.
- Переиспользует уже работающий механизм подключения MCP к `claude -p` — тот же, что применяется в `.mcp.json` сегодня.
- Расписание обновления ложится на Temporal, где уже есть периодический workflow консолидации, — отдельного планировщика не нужно.
- Дешевле концепта A примерно вдвое и не требует доступа к панели хостера или новой записи DNS.

**Минусы:**
- Веб-админка на отдельном домене не появляется вовсе — требование сценария демонстрации не закрывается.
- Транскрипт диалога пишет модель. Механической гарантии полноты нет, и артефакт попадает ровно в тот класс отказов, что уже наблюдался в контуре.
- Пакет с зависимостями попадает в образ агента разработки — тот самый контейнер, который держали минимальным намеренно, потому что в нём исполняется произвольный код чужого репозитория.
- Том индекса монтируется в контейнер разработки. Это канал наружу из изолированного контейнера, и через него агент видит индекс всех репозиториев организации.
- Один процесс MCP на стадию против долгоживущего сервиса: холодный старт на каждой стадии, а SQLite получает конкурирующих писателей из нескольких контейнеров.
- Кросс-репозиторные инструменты требуют, чтобы все клоны лежали на общем томе, — то есть половина инфраструктуры концепта A всё равно возникает, только без её управляемости.

**Оценка усилий:** 1 неделя.

**Риски:**

| Риск | Вероятность | Митигация |
|------|------------|-----------|
| Конкурирующая запись в индекс из нескольких контейнеров | Высокая | Единственный писатель — активность обновления; остальные монтируют том только на чтение |
| Транскрипт неполон или отсутствует | Высокая | Guard на размер и число ходов; стадия падает при недоборе |
| Раздувание образа агента разработки | Средняя | Отдельный слой; измерить прирост до внедрения |
| Ослабление изоляции контейнера разработки | Средняя | Монтировать только на чтение и только каталог индекса, без клонов |

**Откат:** Стадия убирается из `_fnr_stages`, сервер снимается с регистрации в `.mcp.json`, том отцепляется. Образы пересобираются без пакета.

## Концепт C: Кэш выгрузки repomix между прогонами по SHA коммита [Категория: Быстрый костыль]

**Суть:** Механизм контекста не меняется вовсе. `_build_workspace` перестаёт быть безусловно разрушающим: выгрузка `repomix-output.xml` складывается на именованный том с ключом «репозиторий + SHA HEAD» и переиспользуется, пока коммит не изменился. Прогон по репозиторию, где ничего не поменялось, экономит полный проход `repomix`.

**Что менять:**

| Компонент | Изменение | Файл |
|-----------|----------|------|
| `_build_workspace` | Проверка кэша по SHA перед вызовом выгрузки | `worker/activities.py:697-703` |
| `_run_repomix` | Запись результата в кэш после успешной выгрузки | `worker/activities.py:750-759` |
| Compose контура | Том под кэш выгрузок | `../poh-infra/harness/docker-compose.yml` (другой репозиторий) |

**Плюсы:**
- Реализуется за часы, правкой одной функции, и проверяется существующими тестами конвейера.
- Не добавляет ни одной новой точки отказа: промах кэша означает текущее поведение, не отказ.
- Даёт немедленный выигрыш по времени прогона на повторных запусках по одному Issue — а они происходят при каждой переработке аналитики.

**Минусы:**
- Лечит симптом стоимости и не трогает корень. Контекст остаётся плоским и неадресуемым: вопрос ему задать по-прежнему нельзя.
- Ни один из пяти шагов сценария демонстрации не закрывается. Ни диалога, ни артефакта, ни админки.
- Знание по-прежнему не переносится между репозиториями и между разными Issue — переиспользуется байт-в-байт та же выгрузка, а не знание.
- Создаёт видимость закрытой задачи: `T5.6` формально «про контекст», и кэш можно ошибочно засчитать за него.

**Оценка усилий:** 0.5 дня.

**Риски:**

| Риск | Вероятность | Митигация |
|------|------------|-----------|
| Устаревший кэш при совпадении SHA и изменившихся исключениях repomix | Низкая | Включить в ключ кэша хеш настроек выгрузки |
| Рост тома без границы | Средняя | Ограничение по числу записей и возрасту |
| Задача считается закрытой, работа над корнем прекращается | Высокая | Явно зафиксировать в `docs/ROADMAP.md`, что `T5.6` остаётся открытой |

**Откат:** Условие переиспользования снимается, том отцепляется. Одна правка.

## Концепт D: Статический экспорт индекса в репозиторий [Категория: Креативный хак]

**Суть:** Repowise запускается не в контуре, а офлайн — на машине разработчика или в задаче CI — и результат экспортируется файлами прямо в репозиторий (`repowise export`, `repowise generate-claude-md`). Агенты не обращаются ни к какому сервису: они читают обычные файлы в свежем клоне, который у них уже есть. Индекс становится частью репозитория и ревьюится как код.

**Что менять:**

| Компонент | Изменение | Файл |
|-----------|----------|------|
| Задача CI в каждом репозитории | Периодический экспорт индекса и открытие PR с обновлением | `.github/workflows/` в каждом репозитории |
| Каталог индекса в репозитории | Экспортированные страницы вики | `docs/codebase/` в каждом репозитории |
| Новая стадия `repowise` | Чтение экспорта из клона; сетевых обращений нет | `worker/activities.py:648-660` |
| Промпт стадии | Правила работы с экспортом | `prompts/` |

**Плюсы:**
- Нулевая инфраструктура времени выполнения: ни сервиса, ни сети, ни домена, ни пароля, ни нового отказа.
- Работает в изолированном контейнере агента разработки без единого нового канала наружу — контекст приезжает вместе с клоном, который и так делается.
- Индекс версионируется вместе с кодом: видно, когда он обновлялся, и расхождение с кодом заметно в истории, а не только в поведении агента.
- Переживает падение чего угодно в контуре, включая сам контур.

**Минусы:**
- Диалог невозможен принципиально: файл не отвечает на вопросы. Шаги 3 и 5 сценария демонстрации не закрываются вовсе, а они и есть суть требования.
- Семантический поиск и кросс-репозиторные связи теряются — остаётся текст, то есть тот же плоский контекст, что и сейчас, только оформленный лучше.
- Экспорт нужно завести в каждом репозитории отдельно, и каждый начинает нести чужой сгенерированный каталог.
- Свежесть невидима: устаревший экспорт выглядит ровно как свежий.

**Оценка усилий:** 1-2 дня на первый репозиторий, далее по 1-2 часа на каждый следующий.

**Риски:**

| Риск | Вероятность | Митигация |
|------|------------|-----------|
| Экспорт устаревает незаметно | Высокая | Отметка времени и SHA в шапке каждого файла; предупреждение стадии при отставании |
| Шум в PR и в истории репозиториев | Высокая | Отдельная ветка и отдельный PR, не смешивать с содержательными изменениями |
| Требование диалога остаётся невыполненным | Достоверно | Не митигируется; концепт закрывает другую задачу, чем поставлена |

**Откат:** Каталог удаляется, задача CI снимается. Стадия убирается.

## Концепт E: «Не трогай»

**Обоснование:** Позиция отказа формулируется так. Конвейер аналитики работает и выдаёт документы; `repomix` со своей задачей справляется; корень проблемы — не отказ, а неэффективность и упущенная возможность. Взамен предлагается поставить в контур постоянно работающий сервис с индексом всех репозиториев организации, веб-входом под паролем и собственным прокси — на сервер, где свободно порядка 1.4 ГБ памяти при выключенном swap и где уже живут посторонние боевые сервисы. Новый компонент встаёт на критический путь стадии `task`, то есть его отказ останавливает аналитику целиком, тогда как сегодня останавливать её нечему. Добавляется поверхность: домен, пароль, токен, клоны всех репозиториев и ключ модели в одном контейнере.

Отдельный довод: задача заблокирована с июля формулировкой `T5.2` про Confluence и Jira (`specs/implementation-spec.md:184`), а фактический Repowise в организации работает по кодовой базе, а не по ним (`../poh-infra/mcp/poh-org/servers/repowise.yaml`). Прежде чем строить сервис, следует признать, что блокирующее условие поставлено к несуществующей зависимости, — и не исключено, что после переформулировки задача окажется меньше, чем кажется.

**Чем этот отказ опровергается:** ни один из шагов 3-5 сценария демонстрации без постоянного индекса не выполняется, а именно они и являются требованием. Отказ закрывает риск, но не задачу.

# Архитектурные дебаты

> **Метод:** три раунда, Архитектор против Адвоката Дьявола, вердикт формирует модератор.
> **Дата:** 2026-08-19

---

## Раунд 1: Защита

### Архитектор — выбор и обоснование

Выбираю **Концепт A** — Repowise отдельным сервисом с MCP-прокси и журналом сессий.

**Аргумент 1. Только он отвечает на поставленную задачу, остальные отвечают на соседнюю.**
Корень сформулирован как «контекст существует только как производная прогона» (`task.md`, раздел 4), а не как «контекст дорого строить». Концепт C переиспользует ту же выгрузку и оставляет её плоской; концепт D оформляет её красивее, но файл по-прежнему не отвечает на вопрос. Требование автономного диалога выполняет только живой сервис.

**Доказательство:** `worker/activities.py:706-712` — стадия либо получает `sa_documentation/repomix-output.xml` целиком, либо не стартует. Промежуточной формы «спросить о части» в guard'е нет и не может быть: он проверяет существование файла.

**Аргумент 2. Изоляция контейнера разработки сохраняется, а в концепте B — нет.**
Контейнер разработки намеренно минимален и не видит ни GitHub-токена, ни ключа модели (`shared/develop.py`, докстрока модуля). Концепт A даёт ему один сетевой адрес и токен на чтение индекса. Концепт B ставит в него пакет с зависимостями и монтирует том с клонами всех репозиториев организации — это шире по правам и хуже по радиусу поражения.

**Доказательство:** `worker/activities.py:1056-1080` — `_dev_prepare` собирает постановку и клон в каталог задачи; ничего сверх этого раннер не получает, и именно это свойство концепт B нарушает.

**Аргумент 3. Артефакт диалога получается механически, а не доверием к модели.**
Журнал ведёт прокси, транскрипт — производная журнала. В концепте B транскрипт пишет модель, и это тот же класс отказов, что уже наблюдался в контуре: шаг проходит, успех докладывается, артефакта нет.

**Доказательство:** `worker/activities.py:994-1000` — существующий guard умеет проверить только факт создания файла и его размер. Отличить полный транскрипт от правдоподобного пересказа он не может, потому что сравнивать не с чем.

**Аргумент 4. Стоимость растёт линейно от числа репозиториев, а не от числа прогонов.**
Сегодня `repomix` с потолком 600 секунд (`worker/activities.py:637`) выполняется на каждом запуске, включая повторные по одному Issue. Индекс обновляется инкрементально и от числа прогонов не зависит вовсе.

### Адвокат Дьявола — атака

**Контраргумент 1. Вы ставите новую точку отказа на путь, который сегодня не может остановиться.**
Стадия `task` в вашем проекте не стартует без артефакта диалога. Значит отказ прокси — или отказ MCP-контейнера, или пустой том сессий — останавливает аналитику целиком. Сегодня остановить её нечему: `_build_workspace` зависит только от `git` и `repomix` внутри того же контейнера (`worker/activities.py:697-703`). Вы меняете локальную зависимость на сетевую и делаете её обязательной.

**Контраргумент 2. Память сервера.**
На стенде свободно порядка 1.4 ГБ при выключенном swap, и рядом живут посторонние боевые сервисы. Индексация четырнадцати репозиториев с историей — самая тяжёлая нагрузка, которая на этой машине запускалась. Вы не деградируете свой сервис, вы роняете чужой прод.

**Контраргумент 3. Вы строите на непроверенном допущении.**
В разделе допущений концепта записано, что пакет работает без облачной учётной записи, и тут же сказано, что команды `login` и `whoami` в CLI присутствуют. То есть фундамент из двух недель работы стоит на предположении, которое не проверено ни одной командой. Если авторизация обязательна — концепт A отпадает целиком, и концепт B вместе с ним.

**Контраргумент 4. Прокси — ваш собственный код на горячем пути.**
Двести-триста строк сетевого компонента, который вы пишете, сопровождаете и версионируете сами. У него появятся свои сроки жизни сессий, своя уборка, свои утечки. Вы добавляете его, чтобы не патчить чужой пакет, — но чужой пакет хотя бы кто-то сопровождает.

**Контраргумент 5. Устаревший индекс хуже отсутствующего, и вы это сами написали.**
Между прогонами индексатора час. Агент, спросивший про функцию, удалённую сорок минут назад, получит уверенный ответ про неё. Сегодня такого класса ошибок нет вовсе, потому что `repomix` всегда выгружает текущий клон (`worker/activities.py:699-702`).

**Контраргумент 6. Два workspace до появления второго продуктового репозитория — преждевременно.**
В `product` у вас ровно один репозиторий. Вы разворачиваете вторую половину инфраструктуры под гипотетическое будущее, а платите за неё сейчас: второй контейнер, второй индекс, второе расписание, второй маршрут в админке.

## Раунд 2: Пересмотр

### Архитектор — ответ

**На 1 — принимаю и меняю контракт стадии.** Требование меняется с «артефакт диалога существует» на «артефакт диалога существует и в нём записан исход». Прокси недоступен — стадия пишет артефакт с пометкой о недоступности и списком незаданных вопросов, и конвейер идёт дальше. Guard остаётся на месте и по-прежнему ловит молчаливый пропуск (`worker/activities.py:994-1000` проверяет факт создания), но жёсткой остановки не создаёт. Сетевая зависимость становится мягкой, а её отказ — видимым в артефакте, а не только в логах.

**На 2 — не спорю, это уже решено.** Отладка и первичная индексация идут вне контура, выкладка на сервер выносится отдельной задачей и делается после решения по памяти. Концепт A не требует, чтобы сервис стоял рядом с харнессом: он общается по сети, и адрес — переменная.

**На 3 — принимаю целиком.** Проверка на облачную учётную запись становится блокирующей и выполняется до первой строки кода. Отрицательный результат закрывает и концепт A, и концепт B, и остаётся выбор между C, D и E — это надо признать заранее, а не обнаружить на второй неделе.

**На 4 — принимаю частично и сужаю прокси.** Прокси не разбирает семантику инструментов: он journalирует то, что проходит через него, на уровне транспорта. Это снимает главный источник сопровождения — привязку к именам и сигнатурам инструментов, которые в чужом пакете меняются между версиями. Что до альтернативы: у записи силами модели отказ тихий, у прокси — громкий и в одном месте. Из двух точек отказа я выбираю ту, которую видно.

**На 5 — принимаю и делаю возраст индекса видимым.** Отметка о времени последнего обновления индекса и о SHA, на котором он собран, попадает в шапку артефакта диалога. Стадия предупреждает, когда индекс отстал больше порога. Ошибка не исчезает, но перестаёт быть невидимой — а именно невидимость делает её опаснее отсутствия.

**На 6 — не принимаю, и вот почему.** Разделение нужно не под будущие репозитории, а под качество ответов сейчас: вопрос про целевой репозиторий не должен притягивать ответ про устройство самих агентов. Цена разделения — один контейнер в том же compose и один файл конфигурации, потому что механика индексации, прокси и админки общая. Рост при этом линейный: добавить репозиторий — строка в списке, добавить workspace — сервис в compose.

### Адвокат Дьявола — поверка усиленного варианта

Усиление по пунктам 1, 3 и 5 принимаю: мягкая деградация, блокирующая проверка и видимый возраст индекса снимают три моих главных возражения. По пункту 6 остаюсь при своём, но признаю, что цена названа честно и она невелика.

**Новая слабость.** Мягкая деградация создаёт свой риск: стадия, которая всегда «проходит», может проходить впустую месяцами, и никто этого не заметит — артефакт есть, конвейер зелёный. Тихий отказ вы прогнали в дверь и впустили в окно.

**А что если через 6-12 месяцев условие изменится?** Допустим, репозиториев станет сорок, а не четырнадцать. Индексатор с последовательным обходом и часовым интервалом перестанет успевать, и возраст индекса начнёт расти без всякого отказа — молча, тем самым механизмом, который вы только что признали опасным.

### Архитектор — ответ на поверку

**На новую слабость.** Доля прогонов, где диалог не состоялся, — наблюдаемая величина, и она должна быть наблюдаемой явно: исход стадии попадает в отчёт `run_fnr_stage` (`worker/activities.py:977-983` возвращает компактный отчёт, который Temporal фиксирует сам), а деградировавший прогон помечается отдельно. Молчаливым такой отказ остаётся ровно до тех пор, пока его никто не считает; считать его дешевле, чем возвращать жёсткую остановку.

**На горизонт 6-12 месяцев.** Возраст индекса — уже метрика по предыдущему пункту, и порог предупреждения ловит именно этот сценарий: индексатор не успевает — возраст растёт — предупреждение появляется до того, как ответы разъедутся с кодом. Обход, не укладывающийся в интервал, лечится параллелизмом или разными интервалами по репозиториям, и это правка конфигурации, а не архитектуры.

## Раунд 3: Вердикт

**Архитектор — итоговая позиция.** Концепт A остаётся единственным, закрывающим поставленное требование, и после введённых модификаций его отказ деградирует конвейер, а не останавливает; главное допущение проверяется до начала работ.

**Адвокат Дьявола — итоговая позиция.** Возражения по критическому пути, памяти сервера, непроверенному допущению и невидимости устаревания адресованы модификациями; остаётся несогласие по преждевременности второго workspace, но его цена названа и она не блокирующая.

### Вердикт модератора: **Принят с модификациями**

Концепт A принимается при обязательном выполнении следующих модификаций. Реализация без любой из них считается отклонением от вердикта.

| | Модификация | Откуда |
|---|---|---|
| **M1** | Недоступность Repowise **деградирует** стадию, а не останавливает конвейер: артефакт диалога создаётся всегда и несёт исход, включая исход «источник недоступен» | Контраргумент 1 |
| **M2** | Проверка того, что пакет работоспособен без облачной учётной записи, — **блокирующая** и выполняется до первой строки кода. Отрицательный результат закрывает концепты A и B | Контраргумент 3 |
| **M3** | Возраст индекса и SHA, на котором он собран, **видимы в шапке артефакта**; стадия предупреждает при отставании сверх порога | Контраргумент 5 |
| **M4** | Отладка и первичная индексация — **вне контура**; выкладка на сервер выносится отдельной задачей после решения по памяти | Контраргумент 2 |
| **M5** | Прокси журналирует **на уровне транспорта** и не разбирает семантику инструментов — чтобы не быть привязанным к версии чужого пакета | Контраргумент 4 |
| **M6** | Доля деградировавших прогонов и возраст индекса — **наблюдаемые величины**, а не свойство, о котором узнают по жалобе | Поверка раунда 2 |

**Не вошло в вердикт.** Возражение о преждевременности второго workspace (контраргумент 6) отклонено: разделение обосновано качеством ответов в текущем состоянии, а не будущим ростом, и его цена — один контейнер и один файл конфигурации.

**Условие пересмотра.** Отрицательный результат M2 отменяет вердикт целиком и возвращает выбор к концептам C, D и E.
