# FNR-6: Контур не помнит собственных ошибок; каждая итерация начинается с нуля

> **Тип:** Архитектурное изменение / Новая фича
> **Дата:** 2026-08-24
> **Статус:** Открыта

---

## 1. Постановка проблемы

Контур доводит Issue до пул-реквеста и на этом забывает всё. Прогон не оставляет
после себя ни записи о том, что агент собирался сделать, ни оценки того, чем это
кончилось. Следующая задача по тому же репозиторию начинается с чистого листа:
те же слепые зоны, те же потери времени, те же повторяющиеся отказы.

Знание об ошибках контура существует — но живёт в голове человека и в памяти
сессий Claude Code. Сам контур им не пользуется, потому что механизма, которым
он мог бы им воспользоваться, не существует.

## 2. Контекст

За две недели живых прогонов накоплен перечень отказов, каждый из которых
повторялся: агент разработки уходил писать в `/tmp` и докладывал успех, PR-агент
выходил нулём с заглушкой вместо ревью, ретрай долгой активности прогонял всю
работу заново, мусор рабочего каталога уезжал в коммит. Все они найдены человеком
при разборе конкретного прогона и записаны вне контура.

Контур при этом уже умеет главное, на чём такой механизм строится: он ведёт
состояние задачи в Temporal, собирает постановку задачи **дословно и файлом**
(`worker/activities.py:1636`, докстрока: «то, что уехало в работу, должно быть
видно дословно»), сохраняет диалог агента разработки
(`worker/activities.py:1888`) и знает исход пул-реквеста
(`worker/activities.py:2356`).

То есть сырьё для ретроспективы производится каждым прогоном и выбрасывается.

## 3. Текущее поведение (As-Is)

Фаза разработки начинается решением человека `build-me` либо автостартом и уходит
в `_start_development` (`worker/workflows.py:1759`), который вызывает единственную
активность `trigger_openhands_resolver` (`worker/activities.py:2021`) с потолком
времени 3600 секунд и **одной** попыткой.

Внутри активности: `_dev_prepare` (`worker/activities.py:1636`) сносит рабочий
каталог, клонирует репозиторий и собирает постановку из свежего тела Issue, плана
декомпозиции, подзадач и артефактов аналитики; `_dev_run_agent`
(`worker/activities.py:1853`) исполняет прогон агента; `_collect_dev_dialog`
(`worker/activities.py:1888`) собирает транскрипт; `_dev_tests`
(`worker/activities.py:1940`) гоняет тесты; `_dev_publish`
(`worker/activities.py:1959`) публикует результат и возвращает номер PR либо
`None`.

Далее фаза уходит в `pr-review` (`worker/workflows.py:1847`), где круги правок
ведёт `run_pr_fix_round` (`worker/activities.py:2389`), а исход круга фиксирует
`finish_pr_fixing` (`worker/activities.py:2458`).

**Что происходит с накопленным знанием на каждом шаге:**

| Что произведено | Где живёт | Что с ним дальше |
|---|---|---|
| Постановка задачи дословно | файл в рабочем каталоге | каталог сносится следующим прогоном (`worker/activities.py:1636`) |
| Намерения и допущения агента | нигде — не запрашиваются | не существует |
| Диалог агента разработки | собирается `_collect_dev_dialog` | публикуется в Issue, дальше не читается |
| Результат тестов | `_dev_tests` | влияет на текущий прогон, не сохраняется как факт |
| Число кругов правок | счётчик в теле `_phase_pr_review` | уходит в `finish_pr_fixing`, наружу как метка |
| Исход PR (слит / закрыт) | `pr_is_merged` | двигает фазу, не связывается с прогоном, который его породил |
| Правки человека поверх диффа | GitHub | никем не читается |
| Событие Sentry после слияния | Sentry | не связывается с прогоном |

Ни одна строка этой таблицы не переживает прогон в форме, которой мог бы
воспользоваться следующий прогон.

**Цепочка событий (от симптома к корню):**

1. Агент разработки совершает ошибку определённого вида.
2. Человек замечает её при разборе конкретного прогона.
3. Человек правит промпт либо ставит проверку — вручную, по памяти.
4. Связь «правка сделана ради этой ошибки» нигде не фиксируется.
5. Через месяц неизвестно, помогла ли правка: сравнивать не с чем.
6. Ошибка повторяется в другом виде, и цикл начинается заново с шага 2.

## 4. Корень проблемы

**У контура нет объекта «итерация» с собственным жизненным циклом.** Прогон —
это последовательность активностей Temporal, а не сущность, о которой можно
задать вопрос «чем она кончилась и почему».

Три следствия, и все три наблюдаемы:

1. **Намерение не фиксируется.** Постановка сохраняется дословно, а то, что
   агент из неё понял и какие допущения принял, не запрашивается вовсе.
   Реконструировать это постфактум по артефактам — задача, на которой сильные
   модели дают около 11% точности (TRAIL); атрибуция до конкретного шага —
   около 40%.
2. **Оценка не выводится.** Факты об исходе рассыпаны по GitHub, Temporal и
   Sentry и нигде не сводятся вместе. Кода, который собрал бы их в одну таблицу
   по одному прогону, не существует.
3. **Правка не связана с причиной.** Изменение промпта — обычный коммит,
   неотличимый от предметного. Вопрос «эта правка устранила ту ошибку?» не имеет
   в контуре представления, в котором на него можно ответить.

**Доказательство:** активность разработки возвращает `int | None`
(`worker/activities.py:2021`) — номер PR либо его отсутствие. Это весь объём
знания, который контур сохраняет об итерации разработки. Всё остальное — диалог,
постановка, допущения, ход рассуждения — остаётся в рабочем каталоге и сносится
`_dev_prepare` при следующем прогоне (`worker/activities.py:1636`).

Второй слой корня — методологический. Попытка закрыть эту дыру самым дешёвым
способом — попросить модель разобрать собственный транскрипт — в контуре уже
предпринята и уже провалилась: вердикт стадии `validate` в пайплайне БФТ пишет
сама же модель, и аудит показал, что якоря на код при этом не сверяются с
репозиторием (`po-helper-org/poh-issue-agents#78`). Механизм, построенный так же,
произведёт отчёты о росте и ноль роста.

## 5. Ожидаемое поведение

Каждая итерация проработки оставляет после себя запись, которая переживает
прогон, оценивается по фактам и влияет на следующие итерации.

- В конце итерации фиксируется **горячая запись**: что агент собирался сделать,
  какие допущения принял, где сомневался, какие уроки ему были подсыпаны.
- Когда факты созревают — пул-реквест слит либо закрыт, прошёл срок, — по записи
  выносится **холодный вердикт**: детерминированная свёртка объективных сигналов
  плюс разбор с обязательной ссылкой на факт.
- Из вердикта извлекается **урок** — одно правило с указанием сигнала, по
  которому проверяется его действие.
- Урок влияет на контур одним из трёх способов: подсыпается в постановку,
  приезжает правкой промпта пул-реквестом, становится исполняемой проверкой.
- Последующие прогоны **подтверждают или опровергают** урок арифметикой на тех
  же объективных сигналах, без участия модели.
- Урок, опровергнутый или устаревший, вытесняется, но остаётся читаемым.

## 6. Зона воздействия

**Прямое воздействие:**

| Компонент | Характер изменения |
|---|---|
| `worker/activities.py`, `trigger_openhands_resolver` | добавляется вызов записи эпизода перед возвратом |
| `worker/activities.py`, `_dev_prepare` | в постановку добавляется блок уроков и требование написать файл намерений |
| `worker/workflows.py`, `_start_development` | старт отложенного прогона рефлексии |
| Список мусора рабочего каталога | пополняется файлом намерений |
| `prompts/system_*.md` | становятся объектом управляемого изменения |
| Новый репозиторий `po-helper-org/poh-reflection` | память и библиотека рефлексии |

**Косвенное воздействие:**

- Расход ключа модели: появляется новый потребитель того же единственного ключа
  z.ai, который уже является главным источником нестабильности контура.
- Память сервера стенда: около 8 ГБ, из них 2.4 ГБ занимает посторонний
  `temporal-postgresql`.
- История Temporal: добавляется отдельный тип прогона с временем жизни до недели.

**Не затрагивается:**

- Приёмный шлюз, классификация, проверка дублей, приоритизация.
- Конвейер аналитики FNR и пайплайн БФТ.
- Фазы Issue и Delivery — вне объёма настоящей задачи.
- Канал докладов о фазах между агентами и его общий секрет.

## 7. Ограничения

1. **Оценка не может исходить от той же модели, что работала.** Прецедент `#78`
   в контуре уже есть; повторение недопустимо.
2. **Ключ модели один на весь контур.** Рефлексия обязана быть отложенной и
   разведённой по времени с разработкой.
3. **Недетерминированная активность имеет ровно одну попытку.** Правило
   установлено после прогона `#39`, где ретрай трижды прогнал агента заново.
4. **Воркфлоу не читает окружение напрямую** — иначе смена настройки роняет
   реплей недетерминизмом.
5. **Артефакт проверяется по результату, а не по коду возврата процесса.**
   `claude -p` и `pr-agent` выходят нулём, не сделав работы.
6. **Мусор контура не попадает в коммит.**
7. **Изменения едут пул-реквестом**, прямой пуш в `main` запрещён.
8. Первый срез ограничен фазой Develop. Issue и Delivery требуют других мерил
   качества и выносятся отдельными задачами.
