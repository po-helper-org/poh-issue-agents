# FNR-6: История работ по Issue не восстанавливается из Temporal — дорогие стадии спрятаны активностями внутри родителя

> **Тип:** Архитектурное изменение
> **Дата:** 2026-08-19
> **Статус:** Открыта

---

## 1. Постановка проблемы

Дорогие недетерминированные стадии контура (разработка агентом OpenHands, круг
правок по ревью) исполняются как обычные Temporal-активности внутри
родительского `IssueLifecycle`, а не как дочерние воркфлоу. Из-за этого в
Temporal нет строки, по которой видно, что по Issue шла разработка: операционная
история задачи восстанавливается только грепом логов воркера и `docker ps` по
имени контейнера.

## 2. Контекст

Целевая модель демонстрации контура — три поверхности, каждая отвечает на свой
вопрос: **GitHub Issue** — что просили (требования, подзадачи), **Temporal** —
что и как делала система (операционная работа), **GitHub PR** — что получилось
(код). Третья поверхность работает, первая работает, вторая — наполовину.

Обнаружено при живом разборе прогона `po-helper-org/poh-demo-checkout#39`
(2026-08-19). В `temporal workflow list` за всё время не нашлось ни одного
прогона, относящегося к OpenHands, хотя PR по задачам открывались и правились.
Разбор занял час и потребовал SSH на стенд: диагноз (два срыва `git push` подряд
и OOM на третьей попытке) собирался из логов контейнера воркера, а не из истории
воркфлоу.

Прецедент решения в том же коде уже есть: аналитика (`/analyze`) и оценка
(`/estimate`) переведены на дочерние воркфлоу — и именно поэтому видны в списке
отдельными строками.

## 3. Текущее поведение (As-Is)

`IssueLifecycle` — один долгоживущий воркфлоу на Issue, id `issue-<repo>-<n>`
(`shared/workflow_ids.py:12`). Стадии пути вызываются из него двумя разными
способами, и выбор способа не следует ни из какого правила: часть стадий —
дочерние воркфлоу, часть — активности.

**Цепочка событий (от симптома к корню):**

| Шаг | Компонент | Что происходит | Доказательство |
|-----|-----------|---------------|----------------|
| 1 | `IssueLifecycle._start_development` | Разработка вызывается как активность: `execute_activity(trigger_openhands_resolver, …)` | `worker/workflows.py:1347-1374` |
| 2 | `trigger_openhands_resolver` | Внутри одной активности последовательно исполняются четыре шага: клон и постановка, прогон агента, тесты, публикация | `worker/activities.py:1214-1260` |
| 3 | `_dev_prepare` / `_dev_run_agent` / `_dev_tests` / `_dev_publish` | Обычные функции Python, НЕ `@activity.defn`; в истории воркфлоу собственных событий не порождают | `worker/activities.py:1056,1142,1172,1191` |
| 4 | `_run_with_heartbeat` | Различимость шагов существует только как текстовая метка heartbeat (`dev:prepare`, `dev:agent`, `dev:tests`, `dev:publish`) — она видна в `describe`, но не в истории и не в списке | `worker/activities.py:846-860` |
| 5 | Temporal | Активность не имеет своего WorkflowId. В `workflow list` строки нет; в `describe` родителя видна лишь строка `Pending Activities`, и только пока активность выполняется | — |
| 6 | Оператор | После завершения (успешного или нет) операционных следов в Temporal не остаётся: диагноз собирается `docker logs <worker>` и `docker ps` по имени `dev-<owner>__<repo>-<n>` | `shared/develop.py:131-134` |

Ровно так же устроен круг правок по ревью: `run_pr_fix_round`
(`worker/activities.py:1464`) вызывается активностью из `_phase_pr_review`
(`worker/workflows.py:1399-1430`) и поднимает такой же одноразовый контейнер.

## 4. Корень проблемы

В контуре нет правила, по которому стадия становится дочерним воркфлоу.
Аналитику и оценку вынесли в дочерние прогоны по частным поводам — аналитику
ради переиспользования кода между автономным и цикловым запуском
(`worker/workflows.py:745-750`), оценку ради того, что цикл к моменту команды
мог уже завершиться (`worker/workflows.py:1799-1806`). Разработка ни под один
из этих поводов не попала и осталась активностью, хотя по своим свойствам
идентична аналитике: минуты-десятки минут работы, недетерминизм, денежная
стоимость, побочные эффекты, видимые человеку.

Следствие второго порядка: раз шаг разработки — одна активность, её retry
повторяет ВСЕ четыре внутренних шага. На прогоне #39 падал только последний
(`git push`), а повторялся весь, включая двадцатиминутный прогон агента; контур
трижды объявил в Issue о передаче задачи в разработку.

**Доказательство:** `worker/workflows.py:1347-1368` — один `execute_activity` с
`start_to_close_timeout=3600` на всю разработку; `worker/activities.py:1214-1260`
— четыре шага внутри одного тела активности; `worker/workflows.py:1357-1367` —
комментарий о том, что политика ретраев снижена до `maximum_attempts=1` именно
потому, что ретрай гонит агента заново (обход, а не устранение причины).

## 5. Ожидаемое поведение

Каждая дорогая стадия, относящаяся к Issue, исполняется дочерним воркфлоу с
детерминированным id вида `<стадия>-<repo>-<n>` и остаётся видимой в Temporal
после завершения. По одному Issue оператор восстанавливает полную операционную
историю: какие стадии запускались, в каком порядке, сколько шли, какая упала и
на каком внутреннем шаге — не открывая ни логов контейнера, ни `docker ps`.

Внутренние шаги дорогой стадии — самостоятельные активности со своими
таймаутами и своими политиками ретраев: срыв публикации PR повторяет публикацию,
а не прогон агента.

## 6. Зона воздействия

**Прямое воздействие:**

| Компонент | Тип | Файл |
|-----------|-----|------|
| `IssueLifecycle._start_development` | метод воркфлоу | `worker/workflows.py` |
| `IssueLifecycle._phase_pr_review` | метод воркфлоу | `worker/workflows.py` |
| `trigger_openhands_resolver` | активность | `worker/activities.py` |
| `_dev_prepare` / `_dev_run_agent` / `_dev_tests` / `_dev_publish` | функции → активности | `worker/activities.py` |
| `run_pr_fix_round` | активность | `worker/activities.py` |
| `shared/workflow_ids.py` | конфиг идентификаторов | `shared/workflow_ids.py` |
| `worker/worker.py` | регистрация воркфлоу и активностей | `worker/worker.py:38-90` |

**Косвенное воздействие (зависимые компоненты):**

| Компонент | Зависимость | Риск |
|-----------|------------|------|
| Прогоны `IssueLifecycle`, идущие на момент выкладки | Реплей истории по новому коду | Недетерминизм: изменение решений воркфлоу без маркера патча роняет живой прогон |
| `_dev_announce` | Гвард от повторного объявления по метке `in-development` | При дедупе на уровне id воркфлоу гвард становится избыточным, но снимать его до подтверждения нельзя |
| `collect_dev_followups` | Читает файл находок из рабочего каталога после прогона агента | Порядок шагов обязан сохраниться: находки снимаются ДО тестов и публикации |
| `scripts/demo_e2e.py` | Ждёт метку `in-development` и PR | Метки и комментарии не меняются, скрипт продолжает работать |
| Стенд (память ~8 ГБ) | Одновременные дочерние прогоны | Больше параллельных прогонов — быстрее исчерпание памяти; `max_concurrent_activities=3` остаётся ограничителем |

**Защищённые компоненты (не должны быть затронуты):**

- `shared/lifecycle.py` — таблица фаз и переходов. Видимость операций в Temporal не меняет модель состояний Issue.
- `shared/develop.py` — контракт активности Develop (режимы, имена, uid раннера). Модуль намеренно чистый: ни сети, ни Temporal.
- Протокол агентов (`shared/labels.py`, `shared/agent_events.py`) — межсервисный контракт с PR-Agent и PR-Closer, у них свой релизный цикл.
- Метки и комментарии в Issue — то, что видит человек, менять не требуется.

## 7. Ограничения

- Прогоны, начатые на прежнем коде, обязаны пережить выкладку: любое изменение
  решений воркфлоу — только под `workflow.patched(...)`, как это уже сделано для
  `issue-lifecycle-phase-loop` (`worker/workflows.py:452`).
- Родитель делает continue-as-new при 800 событиях истории
  (`worker/workflows.py:74`), и после этого RunId меняется. Дерево дочерних
  прогонов в UI привязано к конкретному RunId — способ восстановления истории
  обязан это учитывать.
- Дочерний прогон не должен умирать вместе с родителем: аналитика уже
  использует `ParentClosePolicy.ABANDON` (`worker/workflows.py:773-777`).
- Разработка и круг правок поднимают контейнер через docker-сокет воркера;
  изоляция раннера (нет GitHub-токена, uid 10001) сохраняется без изменений.
- Память стенда ~8 ГБ, из них 2.4 ГБ занимает сосед: рост параллелизма
  недопустим.
