# Концепты решений — FNR-6

> **Задача:** История работ по Issue не восстанавливается из Temporal — дорогие стадии спрятаны активностями внутри родителя
> **Дата:** 2026-08-19
> **Статус:** Дебаты проведены, вердикт вынесен

---

## Резюме проблемы

В контуре нет правила, по которому стадия становится дочерним воркфлоу:
аналитику и оценку вынесли по частным поводам, разработка и круг правок
остались активностями внутри `IssueLifecycle`. Дорогая стадия без своего
WorkflowId не даёт строки в `workflow list` и не оставляет операционного следа
после завершения — история работ по Issue собирается логами контейнера.
Побочно: retry такой активности повторяет все её внутренние шаги, включая
двадцатиминутный прогон агента.

## Концепт A: Дочерний воркфлоу на каждую дорогую стадию + внутренние шаги как активности [Категория: Правильное]

**Суть:** Ввести правило — стадия, которая идёт минутами, недетерминирована и
стоит денег, исполняется дочерним воркфлоу с детерминированным id. Развернуть
`trigger_openhands_resolver` в `IssueDevelopment` из четырёх активностей
(`prepare` / `run_agent` / `tests` / `publish`), круг правок — в `IssuePrFix`.
Оба по образцу уже работающего `IssueAnalysis`.

**Что менять:**

| Компонент | Изменение | Файл |
|-----------|----------|------|
| `IssueDevelopment` | ADD: новый `@workflow.defn`, оркестрирует четыре активности | `worker/workflows.py` |
| `IssuePrFix` | ADD: новый `@workflow.defn` для круга правок | `worker/workflows.py` |
| `_start_development` | MODIFY: `execute_activity` → `execute_child_workflow` под маркером патча | `worker/workflows.py:1347` |
| `_phase_pr_review` | MODIFY: то же для круга правок | `worker/workflows.py:1399` |
| `_dev_prepare`/`_dev_run_agent`/`_dev_tests`/`_dev_publish` | MODIFY: функции → `@activity.defn` | `worker/activities.py:1056,1142,1172,1191` |
| `trigger_openhands_resolver` | MODIFY: тело переезжает в воркфлоу, активность остаётся только для режима `dispatch` | `worker/activities.py:1214` |
| `development_workflow_id` / `pr_fix_workflow_id` | ADD: форматы id рядом с существующими | `shared/workflow_ids.py:36` |
| `worker/worker.py` | MODIFY: регистрация новых воркфлоу и активностей | `worker/worker.py:38` |

**Плюсы:**
- Закрывает требование целиком: каждая дорогая стадия — строка в `workflow list`, история остаётся после завершения.
- Retry становится осмысленным: срыв `publish` (случай #39) повторяет публикацию, а не прогон агента. `maximum_attempts=1` на всю стадию перестаёт быть нужен как обход.
- Дедуп через `WorkflowAlreadyStartedError` по id — тот же механизм, что уже спасает аналитику от тройного запуска; ручной гвард в `_dev_announce` становится избыточным.
- Шаги видны в истории событиями `ActivityTaskScheduled/Started/Completed` с именами — heartbeat-метки перестают быть единственным различителем.
- Правило воспроизводимо: следующая дорогая стадия попадёт в ту же форму без отдельного решения.

**Минусы:**
- Самый большой объём: два новых воркфлоу, четыре новые активности, правка двух методов родителя.
- Сериализация между шагами: `_dev_prepare` возвращает текст постановки, шаги обмениваются путями — данные проходят через payload Temporal, размер надо контролировать (постановка на #39 — 1780 символов, приемлемо).
- Реплей: два изменённых решения воркфлоу требуют маркеров патча и аккуратной выкладки при живых прогонах.

**Оценка усилий:** 2–3 дня.

**Риски:**

| Риск | Вероятность | Митигация |
|------|------------|-----------|
| Недетерминизм на живых прогонах при выкладке | Высокая | `workflow.patched()` на обоих изменённых решениях; проверка `docker logs \| grep -i nondetermin` после выкладки |
| Рост числа одновременных прогонов исчерпает память стенда | Средняя | `max_concurrent_activities=3` не меняется; дочерний воркфлоу не добавляет параллелизма — он лишь переупаковывает ту же работу |
| Потеря порядка «находки снимаются до тестов и публикации» | Средняя | Порядок фиксируется явными шагами воркфлоу и покрывается тестом |
| Payload между шагами упрётся в лимит Temporal (2 МБ) | Низкая | Между шагами передаются пути и номера, не содержимое; тела читает активность из общего тома |

**Откат:** Вернуть `_start_development`/`_phase_pr_review` на прямой
`execute_activity` (ветка маркера патча уже содержит старый путь), новые
воркфлоу оставить зарегистрированными и неиспользуемыми. Данных решение не
трогает — откат чисто кодовый.

**Суть:** Не менять структуру. Проставлять на родителе search attribute с

|-----------|----------|------|

**Плюсы:**
- Часы работы, не дни.
- Нулевой риск недетерминизма: решения воркфлоу не меняются (upsert — детерминированная операция).
- Search attribute уже используется в проекте (`TEMPORAL_SEARCH_ATTRIBUTES` в compose), инфраструктура готова.

**Минусы:**

- Не чинит retry: активность по-прежнему повторяется целиком, обход `maximum_attempts=1` остаётся навсегда.
- Не даёт дедупа по id — ручные гварды остаются и множатся.
- Прямо противоречит требованию заказчика: демо-сценарий требует видеть операционную работу в Temporal, а не искать её в логах.

**Оценка усилий:** 3–4 часа.

**Риски:**

| Риск | Вероятность | Влияние |
|------|------------|---------|
| Ложное ощущение решённости | Высокая | Задача закрывается, проблема остаётся |

## Концепт D: Отдельный воркфлоу-«журнал» на Issue [Категория: Креативный хак]

**Суть:** Поднять на каждый Issue второй долгоживущий воркфлоу-журнал, в который
все стадии шлют сигналы о своих шагах. Журнал ничего не исполняет — он хранит
хронологию и отдаёт её query.

**Что менять:**

| Компонент | Изменение | Файл |
|-----------|----------|------|
| `IssueJournal` | ADD: воркфлоу-приёмник сигналов с query `history` | `worker/workflows.py` |
| Все дорогие активности | MODIFY: слать сигнал на каждый шаг | `worker/activities.py` |

**Плюсы:**
- История в одном месте и переживает continue-as-new родителя — привязка к Issue, а не к RunId.
- Формат истории свой, а не навязанный деревом Temporal.

**Минусы:**
- Дублирует то, что Temporal делает сам: история воркфлоу — это и есть журнал. Второй журнал поверх первого расходится с ним при первом же сбое доставки сигнала.
- Активность, шлющая сигналы, должна знать адрес журнала — активности начинают зависеть от топологии воркфлоу.
- Ещё один долгоживущий прогон на каждый Issue: вдвое больше строк в списке и вдвое больше того, что может зависнуть.
- Не чинит ни retry, ни дедуп.

**Оценка усилий:** 3–4 дня.

**Риски:**

| Риск | Вероятность | Митигация |
|------|------------|-----------|
| Расхождение журнала с фактической историей | Высокая | Не митигируется структурно |

**Откат:** Снять воркфлоу и отправку сигналов.

# Архитектурные дебаты

> **Формат:** 3 раунда, Архитектор ↔ Адвокат Дьявола, модератор структуру не оценивает по сторонам.

## Раунд 1: Защита

### Архитектор — выбор и обоснование

**Выбираю Концепт A.**

1. **Форма уже проверена в этом же коде.** `IssueAnalysis` — дочерний воркфлоу
   с фиксированным id, `ParentClosePolicy.ABANDON` и `maximum_attempts=1`
   (`worker/workflows.py:767-777`). Он пережил переход от автономного запуска к
   цикловому без раздвоения кода. Концепт A не изобретает форму, а
   распространяет работающую.

2. **Retry сейчас вредит, и это доказано прогоном.** Комментарий в
   `worker/workflows.py:1357-1367` описывает случай #39 дословно: пуш падал на
   последнем шаге, а повторялась вся активность вместе с прогоном агента, и
   контур трижды объявил о передаче задачи. Лечение снижением до
   `maximum_attempts=1` — отказ от ретраев вообще, включая те, где они уместны
   (сеть при публикации PR). Разделение на активности возвращает ретраи туда,
   где они дёшевы.

3. **Дедуп по id снимает класс ручных гвардов.** В `_run_analysis_child`
   (`worker/workflows.py:752-765`) описан отдельный флаг `_analysis_running`,
   заведённый потому, что метка контура возвращалась вебхуком как новая команда
   и давала три прогона подряд. Для разработки тот же дефект чинился гвардом в
   `_dev_announce` (`worker/activities.py:1318-1340`). Оба — обходы отсутствия
   ключа идемпотентности на уровне прогона.

4. **Круг правок идентичен разработке по свойствам.** `run_pr_fix_round`
   (`worker/activities.py:1464-1500`) поднимает тот же образ раннера, тем же
   `develop.runner_command`, с тем же таймаутом 2700 с. Оставлять его
   активностью — значит заранее знать о втором заходе на тот же файл.

### Адвокат Дьявола — атака

1. **Дерево дочерних прогонов привязано к RunId, а родитель делает
   continue-as-new.** `HISTORY_EVENT_THRESHOLD = 800` (`worker/workflows.py:74`),
   после порога RunId меняется. Дочерние прогоны, запущенные до перезапуска,
   останутся детьми старого RunId. Заявленная цель «по одному Issue вижу всю
   историю» деревом в UI не достигается — она достигается только поиском по
   префиксу id. Тогда зачем дочерние воркфлоу, если работает соглашение об
   именах?

2. **`ParentClosePolicy.ABANDON` разрывает связь, которую вы строите.** Он
   обязателен (иначе continue-as-new убьёт сорокаминутный прогон), но
   брошенный прогон — сирота: родитель завершится, а он останется. Вы получаете
   не дерево, а набор одинаково названных прогонов.

3. **Риск недетерминизма реален и уже стоил контуру простоя.** В README
   зафиксирован отказ «Issue не реагирует ни на метки, ни на команды» с
   диагностикой `grep -i nondetermin`. Концепт A меняет ДВА решения воркфлоу
   сразу, при восьми живых прогонах на стенде.

4. **Четыре активности вместо одной — четыре точки сериализации.** Сейчас шаги
   обмениваются питоновскими объектами внутри процесса. После разделения между
   ними payload Temporal, и `_dev_prepare` возвращает текст постановки (1780
   символов на #39, но потолка на него нет — постановка собирается из
   системных требований, `worker/activities.py:1063-1072`). Требования на
   большой задаче могут дать сотни килобайт.

5. **Стенд на 8 ГБ.** Больше воркфлоу — больше событий, больше истории в
   Postgres, который и так делит хост с чужим продом.

## Раунд 2: Пересмотр

### Архитектор — ответ

**На (1) — RunId и continue-as-new.** Контраргумент верный по механике и
неверный по выводу. Дерево в UI — не единственная и не главная форма
восстановления истории; главная — `workflow list` с фильтром по префиксу id,
и именно она сегодня не работает, потому что для разработки НЕТ id вообще.
Соглашение об именах без отдельного прогона не даёт ничего: называть нечего.
Дополнительно: `IssueAnalysis` живёт с этим же ограничением с момента
внедрения, и оно ни разу не помешало — прогон находится по
`analysis-<repo>-<n>`. Требование формулируется точнее: **привязка к Issue
через id, а не через дерево родителя**; дерево — приятное следствие, пока
родитель не перезапустился.

**На (2) — ABANDON и сироты.** Сирота — это прогон, о котором некому спросить.
Здесь спросить есть о чём: id детерминирован и выводится из номера Issue.
Альтернатива (`TERMINATE`) хуже на порядок: она убивает сорокаминутный прогон
агента по причине, к нему не относящейся, — ровно то, от чего аналитику
защищали комментарием `worker/workflows.py:770-773`.

**На (3) — недетерминизм.** Принимаю как ограничение, а не как возражение
против концепта. Митигация — маркеры патча (механизм в проекте отработан:
`issue-lifecycle-phase-loop`, `issue-lifecycle-awaiting`,
`issue-lifecycle-clear-queue-on-work`, `issue-lifecycle-absolute-park-deadline`
видны в `TemporalChangeVersion` живого прогона) плюс выкладка двумя этапами:
сначала Develop, проверка живым Issue, затем круг правок. Это меняет ПЛАН, а
не концепт.

**На (4) — сериализация.** Усиливаю концепт: между шагами передаются номера,
пути и слаги, но НЕ содержимое. Постановка пишется на диск в
`.task.md` (`worker/activities.py:1063`) — она уже файл в общем томе; активность
`prepare` возвращает длину и путь, а не текст. Тот же приём для вывода агента:
хвост лога уходит в лог воркера, а не в payload.

**На (5) — память.** Число одновременных прогонов агента не растёт: их
ограничивает `max_concurrent_activities=3` (`worker/worker.py:106`) и один
раннер на задачу по имени контейнера (`shared/develop.py:131`). Дочерний
воркфлоу переупаковывает ту же работу, а не добавляет новую. Рост истории в
Postgres реален, но это события по 200–400 байт против гигабайтов образов.

### Адвокат Дьявола — поверка

Усиление по (4) принимаю: передача путей вместо содержимого снимает риск
payload'а и заодно возвращает симметрию с тем, как уже работает общий том.

Усиление по (1) принимаю с уточнением: если история восстанавливается поиском
по префиксу id, то **формат id обязан быть единственным источником правды** и
жить в `shared/workflow_ids.py` вместе с остальными — иначе через полгода
появится второй формат и поиск перестанет быть полным.

**Вопрос на 6–12 месяцев:** если стадий станет шесть-восемь (декомпозиция,
диагностика бага, ревью безопасности), не превратится ли `workflow list` в
шум, где родителя не видно за детьми?

**Ответ Архитектора:** Это довод ЗА единый формат id, а не против концепта.
`workflow list` фильтруется по префиксу: `issue-` даёт только родителей,
`develop-` — только разработки. Сегодня фильтр невозможен, потому что часть
стадий не существует как прогоны. Шум лечится фильтром, слепота — нет.

## Раунд 3: Вердикт

**Архитектор:** Концепт A в усиленном виде — дочерний воркфлоу на каждую дорогую
стадию, шаги как отдельные активности, обмен между шагами путями и номерами, все
форматы id в `shared/workflow_ids.py`, выкладка двумя этапами под маркерами
патча.

**Адвокат Дьявола:** Возражений по существу не остаётся. Критика по payload'у и
по формату id учтена в решении; риск недетерминизма реален, но переведён в план
выкладки, а не отрицается.

### Вердикт модератора

**Принят с модификациями — Концепт A.**

Обязательные модификации, вошедшие в решение:

1. **Между шагами передаются пути, слаги и номера, не содержимое.** Тексты
   (постановка, вывод агента, вывод тестов) остаются в общем томе и в логе.
2. **Все форматы id — только в `shared/workflow_ids.py`.** Второго места, где
   собирается id стадии, быть не должно.
3. **Выкладка двумя этапами:** сначала `IssueDevelopment` и проверка живым
   Issue на стенде, затем `IssuePrFix`. Каждое изменённое решение воркфлоу — под
   своим маркером патча.
4. **`ParentClosePolicy.ABANDON` обязателен** для обеих новых стадий: дорогой
   прогон не должен умирать от continue-as-new или завершения родителя.
5. **Ручные гварды (`_dev_announce`, `_analysis_running`) не снимаются в этой
   работе.** Дедуп по id их делает избыточными, но снятие — отдельное решение
   после подтверждения живым прогоном.
