# Коробка БФТ — автономная проработка требований (Temporal + Gitea + GLM)

Сервис берёт запрос в Inbox и сам доводит его до **БФТ** (бизнес-функциональных требований), затем до **СТ**
(системных требований), готовых к передаче в разработку. Человек подключается только там, где без него нельзя:
ответить на вопросы CustDev, принять БФТ, разобрать упавшую стадию.

Статус: **в разработке**. Веха 1 (автономный контур без интерфейса) собирается по тикетам с меткой `bft-harness`;
скелет стенда (Gitea + Temporal) смержен, дальше — драйвер Gitea, фазы, исполнитель стадий, переписка в Element, стадия СТ, отдача.
Спецификация и порядок поставки — [`docs/BFT-HARNESS.md`](docs/BFT-HARNESS.md), решения — [`docs/DECISIONS.md`](docs/DECISIONS.md) (ADR-20…26).

> **Контур «issue → разработка → PR → релиз» заморожен.** Раньше здесь жил полный конвейер: разработка агентом (OpenHands),
> FNR-анализ кода, оценка, релиз, приёмка по HowToDemo, консолидация бэклога. Решениями владельца 2026-10-09 и 2026-10-16
> эти стадии вырезаны из сборки. Они не поддерживаются: код остаётся в истории и под тегом **`contour-v1`**,
> прежний README — [`docs/contour/README-contour-v1.md`](docs/contour/README-contour-v1.md), документы замороженных
> соседних репозиториев — [`docs/contour/`](docs/contour/).

## Как это выглядит для PO

1. Запрос падает в **Inbox** — задачу в Gitea заводят вручную, ботом из Element или синхронизацией из Jira команды.
2. Для старта в карточке нужны email заказчика, PO и аналитика и команда; пока их нет, карточка ждёт, а в ней написано, чего не хватает.
3. Дальше без PO: триаж → глубокий разбор БФТ (`bft-deep`) и скрипт CustDev-интервью → вопросы сообщением в Element,
   в треде карточки → БФТ дорабатывается по ответам → ревью БФТ (тоже в треде) → СТ по методологии `poh-sysreq-agent` →
   отдача БФТ и СТ в источник команды через PO-агента команды.
4. Человек нужен, только если вышел срок ответа после напоминания (`needs-human:*`) или стадия упала (`phase:failed` с причиной).
5. Веха 2 — доска `/bft-harness`: где каждая карточка, кого ждём и сколько. Доска только показывает и подталкивает, логика — в контуре.

## Из чего состоит

```
Inbox: задача Gitea  ◀── бот @bft (Element) · синхронизация Jira · вручную
        │ webhook (HMAC)
        ▼
webhook (FastAPI) ──signal-with-start──▶ Temporal (start-dev, SQLite) ──▶ worker
                                                                         ├─ GLM напрямую: гейты, стадии БФТ, СТ
                                                                         ├─ Hermes A2A → PO-агент команды: чтение контекста, отдача
                                                                         └─ Matrix: тред карточки — вопросы, ответы, ревью
        ▼
Gitea: комментарии, метки phase:*, коммиты артефактов   ──▶  доска /bft-harness (веха 2)
```

| Что | Где хранится |
|---|---|
| Карточки, вводные и ответы, метки фаз | Gitea (self-hosted), org `bft`, repo `requests` |
| Артефакты (БФТ, СТ, письма, страницы ревью), по коммиту на шаг | Gitea, `bft/<N>/…` |
| Какая стадия идёт, ожидания, таймеры, повторы | Temporal, жизненный цикл `BftLifecycle` (`shared/bft_lifecycle.py`) |

Temporal нужен ради долгих ожиданий: воркер упал посреди прогона — он продолжит с последнего завершённого шага,
а карточка, которая неделями ждёт ответа заказчика, — штатное состояние workflow, а не обходной путь.
На сервере контура нет `claude -p` и продуктов Anthropic: стадии идут через GLM (Z.AI) напрямую или через Hermes.

## Что осталось от прежнего контура

Триаж Issue (предфильтры, intake-gate с циклом уточнений, классификация, поиск дублей — только метка, приоритет по формуле
`config/priority-weights.toml`) переиспользуется как стадия «Триаж» харнесса. Код вырезанных стадий (разработка, релиз, оценка, FNR-анализ,
консолидация, `openhands/`) убирается тикетом T3 «вырезать лишнее» и пока лежит рядом; запускать и развивать его не нужно.

## Запуск и тесты

```bash
make setup   # preflight + venv + .env (интерактивно)
make test    # pytest с порогом покрытия (.coveragerc)
```

Стенд харнесса (Gitea + Temporal + webhook + worker) разворачивается скриптами из [`deploy/bft-harness/`](deploy/bft-harness/);
порядок установки и проверка — в [`docs/BFT-HARNESS.md`](docs/BFT-HARNESS.md). Тесты идут в GitHub Actions
(`.github/workflows/tests.yml`) на каждый push и PR.
